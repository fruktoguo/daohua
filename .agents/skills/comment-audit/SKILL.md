# 全局注释检查分析与生成

对指定范围做注释审计与补全：公共 API 补齐中等详细度的中文 XML 注释，非自明的方法内实现补行间注释，修正低质量注释。**只改注释，绝不改代码逻辑。**

## 范围与优先级

1. 用户指定了范围（项目/目录/文件）→ 只处理该范围。
2. 未指定 → 默认全仓，按优先级推进：`src/Domain` → `src/Ecs` → `src/Server` → `src/Protocol` → `src/ComputeNode` → `frontend/src` → `tools/`。
3. `tests/` 不要求 XML 注释（测试名即文档），只给复杂 Arrange/Act/Assert 段补行间注释。
4. `vendor/` 是固定 submodule，**永不修改**。
5. 自动生成的代码（如 `obj/`、`*.g.cs`、序列化产物）跳过。

## 中等详细度标准

「中等详细度」= 说清「做什么 + 为什么 + 关键约束」，不写废话，不写论文。

### XML 注释（C# 用 `///`，前端 TS 用 `/** */`）

| 成员 | 要求 |
| --- | --- |
| 类型/接口 | `<summary>` 2~3 句：职责 + 关键不变量/约束 + 线程或生命周期语义（如有） |
| 方法 | `<summary>` 1~2 句：做什么 + 为什么/边界；`<param>` 语义不自明的参数都写，一句话；`<returns>` 非 void 且不自明才写 |
| 属性 | 一句话：业务含义 + 单位/量纲（如「每 5 秒回复量，1 点 = 4 点预算」） |
| `<remarks>` | 仅当存在性能取舍、确定性要求、调用顺序约束、安全假设时才加，不堆砌 |

好例子：

```csharp
/// <summary>
/// 按境界等级在锚点表间线性插值，得到 12 项基础属性的基准值。
/// 是全部预算量化的唯一入口，保证数值可推导、可复现。
/// </summary>
/// <param name="level">境界等级（1~127）。</param>
/// <returns>各项基础属性基准值，键为属性编号。</returns>
public IReadOnlyDictionary<int, double> ResolveBaseFlat(int level)
```

坏例子（废话注释，禁止）：

```csharp
/// <summary>
/// 这个方法用来获取名字。/ 返回名字。
/// </summary>
public string GetName()
```

### 行间注释（`// 中文`）

只给**无法一眼看出作用**的实现加，解释「为什么」而不是「做什么」：

- 必须加：魔法数与配表换算关系、顺序依赖（「必须先 X 再 Y，否则…」）、确定性/随机通道约束、绕过某抽象的原因、与配表/协议字段的对应、看似多余实则必需的防御。
- 禁止加：逐行复述代码（`// 遍历列表`）、与代码重复的自明注释、被注释代码的翻译。

好例子：

```csharp
// 先按攻击方、受击方各派发一条 pending trigger，未命中也派发，
// 由处理器自行判断资格；顺序不能颠倒，威胁值依赖原始命中侧。
foreach (var trigger in pending) { ... }
```

## 执行流程

1. **确定范围**：按「范围与优先级」圈定文件清单。
2. **扫描缺失**：
   - 公共 API 缺 XML 注释清单（利用编译器警告，不落盘文档文件）：
     ```bash
     dotnet build src/Domain/Domain.csproj -c Release -p:GenerateDocumentationFile=true 2>&1 | grep CS1591
     ```
     逐项目替换 csproj 路径执行；也可直接读文件，检查 `public`/`internal` 成员上方是否有 `///`。
   - 低质量注释清单：英文注释、废话注释、与代码行为不符的过期注释、该加行间注释却没有的复杂方法体。
3. **分析**：写注释前先读懂上下文（调用点、配表、协议、设计文档 `docs/design/总纲/`），确保注释描述的是**真实行为与设计意图**，不是望文生义。
4. **生成**：按「中等详细度标准」补齐与修正。发现注释与代码行为矛盾时，以代码为准改注释；若疑似代码本身是 bug，**停下报告用户**，不顺手改逻辑。
5. **验证**：
   ```bash
   dotnet build <被改动的 csproj> -c Release
   ```
   确认注释未引入语法/XML 结构错误（如未闭合标签）；前端改动跑 `npm --prefix frontend run build`。
6. **汇报**：按文件列出——新增 XML 注释数、补行间注释数、修正/中文化注释数、跳过原因（生成代码/测试/超范围）。

## 硬性约束

- 只增删改注释行，diff 中不得出现任何代码逻辑变更；重构、改名、调整结构一律不做也不建议在本次做。
- 不删除既有有效注释；英文注释中文化而不是删除重写。
- 遵守仓库注释规范：注释只解释设计意图、业务约束、安全假设、边界或性能取舍，默认中文；标识符、类型名、文件名保持英文。
- 修仙等专用词汇用中文原词（气、灵根、功法），对应代码标识符用拼音（`Qi`/`Linggen`/`Gongfa`），以 `docs/design/总纲/19-名词术语对照表.md` 为准。
- 不为凑数给自明代码加注释；宁缺毋滥，注释密度服务于可读性。
