# 合并门禁审计与精简

目标：让门禁集合保持「每个门禁都对应一个真实故障边界，且没有两个门禁防同一个故障」。删除不防真故障的仪式性检查，精简重复或过贵的检查，保留真正兜底的检查。

## 门禁盘点来源

- `scripts/verify.sh`：逐步骤盘点（工具链检查、npm ci、Release 构建、PostgreSQL 集成测试库供给、Domain/Ecs/Server 三套测试、DataTool strict 校验、Compose config 校验、前端 tsc+build、`VERIFY_DOCKER=1` 镜像构建）。
- `AGENTS.md` 中记录的门禁与验证要求（§5 命令表及各节「门禁」相关条目）。
- 独立门禁脚本：`scripts/check-frontend-contracts.mjs`（被 Server.Tests 调用）、`scripts/capacity-target.sh`、`scripts/smoke-production.mjs`、`scripts/migrate-local-db.sh` / `reset-outdated-players.sh` 启动链。
- `frontend/package.json` scripts（`build` = i18n 导出 + `tsc -b` + `vite build`）。
- git hooks（当前无自定义钩子；如出现需纳入盘点）。

## 逐条评估维度

每个门禁必须能回答五个问题，答不上来的就是删除候选：

1. **防什么真实故障**：指出具体故障场景与后果。说不出具体故障的，是仪式性门禁。
2. **是否重复**：是否有另一个更便宜的门禁覆盖同一故障？断言同一件事的两个门禁，留便宜的。
3. **成本**：运行时长、环境依赖（DB/Docker）、易碎性（偶发失败率）。
4. **误报与漏报**：经常挡路但从不抓真 bug → 精简或删除；声称防 X 但实际抓不到 X → 修正或删除。
5. **维护成本**：需要人工同步的配置、文档、环境。

## 判定分级

- **保留**：防真实高风险故障、无重复、成本可接受。
- **精简**：防真实故障但范围过大/成本过高/部分重复 → 收窄范围、合并步骤、降频（合并必跑 → 发布前跑）、加环境开关。
- **删除**：仪式性（说不出防什么）、完全被其他门禁覆盖、防的场景在本仓库架构下不可能发生、纯重复。

## 分层建议

不是所有门禁都要每次合并跑。输出分层方案：

- **合并必跑（快）**：构建 + 三套测试 + 前端契约 + DataTool strict + 前端 tsc/build。
- **发布/容器变更前跑**：Compose config、烟测、镜像构建。
- **定期或架构变更后跑**：PostgreSQL 容量门禁、压测基准。

## 硬性约束

- **删除必须经用户确认**：先出审计报告（门禁清单 + 判定 + 证据），用户确认删除/精简清单后才动手。
- **兜底检查**：每个删除决定必须写明——该故障由哪个剩余门禁兜底，或为什么该故障在本仓库架构下不可能发生。两者都答不出 → 不许删。
- **默认保留类**：数据安全（备份/恢复/迁移链）、鉴权、生产部署（`deploy-prod.sh`、烟测）、容量门禁。动这些需要用户逐项明确确认。
- **文档先行**：删除/精简后同步更新 `AGENTS.md` 的门禁描述与脚本头注释；门禁脚本头部描述必须与实际步骤一致。
- **验证**：改完门禁脚本后实际跑一遍精简后的门禁确认可用；被删门禁如被其他脚本/文档引用，全仓 grep 清理残留调用点。
- 不借机重构门禁脚本本身；只做删除/精简相关的最小修改。

## 执行流程

1. **盘点**：按「门禁盘点来源」列出全部门禁及入口。
2. **评估**：填审计表（门禁 | 防什么故障 | 重复覆盖 | 成本 | 判定 | 证据）。
3. **提案**：输出删除/精简/保留三张清单，等用户确认。
4. **执行**：最小 diff 修改脚本与文档。
5. **验证**：跑精简后的门禁 + 全仓 grep 确认无残留引用。
6. **汇报**：执行结果 + 精简后门禁清单 + 每次合并节省的时间。
