# 文档优化治理

对 `docs/` 做可量化治理：先取证，再按权限分层处置，最后复核。**判据必须由 `scripts/doc-audit.mjs` 复现**，禁止凭「感觉啰嗦」删改。

## 1. 先跑体检

```bash
node scripts/doc-audit.mjs          # 人读报告
node scripts/doc-audit.mjs --json   # 机器读，逐条处置
node scripts/doc-audit.mjs --top 40 # 放大样本条数
```

退出码 `1` 表示存在硬缺陷（坏链、看板编号重复、看板详情死链）。脚本**不在 `scripts/verify.sh` 内**，文档质量是渐进目标，不阻塞代码提交。

脚本未覆盖的文档包括：`docs/design/战斗演武画廊/`（HTML 沙盘，非 markdown）。**时点证据库**——`docs/archive/` 与 `docs/audits/`、`docs/tasks/archive/`——记录的是当时源码状态，只参与「索引可达性」判据，不参与重复度、路径引用与形态判据。这些文档中的源码路径与行号允许失效：**不得**据此改写它们，也不得把它们当作现行真源引用；按它们订正实现前必须重新取证。

## 2. 阈值表（改脚本必须同步改此表）

| 判据 | 阈值 | 含义 |
| --- | --- | --- |
| 真源重复（8-gram 占较短篇） | ≥15% 告警 / ≥25% 必须合并 | 两篇正式文档在讲同一件事 |
| 正文单行 | >400 字符 | 长句、无分行的连续说明 |
| 表格行 | >320 字符 | 单元格里塞了整段需求描述 |
| 加粗密度 | >10 对 / KB | 通篇高亮等于没有高亮 |
| 看板表格行 | >400 字符 | 任务名把实现细节搬进了看板 |
| TASK 详情体量 | >12 KB 或时间戳 >10 处 | 过程日志未压缩 |
| 真源单篇体量 | >60 KB | 应拆分为同族分篇 |

## 3. 权限分层（硬规则）

### 可自主执行（表达层）

- 索引补全：把零入链文档登记进 `docs/README.md`（本仓唯一入口，不再逐目录造 README 造成重复索引）。
- 坏链修复：改正相对路径、补全指向的目录或文件、把死链替换为现存等价文档。
- 重复内容处理：**保留权威篇的正本，把重复段改写为一句要点 + 指向真源的链接**；禁止两边各删一半。
- 排版规范化：长段拆行、超长单元格改成分点列表、清理装饰性加粗、统一表格与代码块形态。
- 看板瘦身：把 `docs/tasks.md` 中堆砌的实现细节压缩为一句任务摘要，详情留在 `docs/tasks/TASK-*.md`。
- TASK 详情压缩：合并连续时间戳日志段为阶段性节点，保留任务提出/完成时间与关键决策。
- 归档迁移：已完成任务详情按 `docs/tasks.md` 维护规约并入 `docs/tasks/archive/archive-YYYY-MM.md`。

### 必须报告用户确认（语义层）

- **删除任何文档**，包括合并后的废弃稿与重复篇。
- **修改任何事实**：数值、公式、字段名、协议字段、阈值、状态枚举、时限。
- **修改任何规则或设计意图**：设计取舍、优先级、红线。
- **判定真源归属冲突**：重复率超阈但无法从文档自身判断哪篇权威时，报候选与证据（重复段落位置），不自行取舍。
- **变更索引分类**：把文档移入 `archive/`、`future/` 或改变其真源地位。

取证要求：涉及事实订正必须先读对应源码/配表/`config/game-data`，并在报告中给出证据路径。**禁止**用文档互相印证——文档之间一致不代表与实现一致。

## 4. 处置顺序（成本从低到高）

1. **索引与链接**（纯结构，零风险）：零入链、缺目录 README、坏链、看板详情死链。
2. **形态规范**（不动语义）：长行、加粗过密、超宽表格行。
3. **看板与任务文档**（守 `docs/tasks.md` 维护规约）：重复编号、超宽行、详情压缩、归档。
4. **真源重复合并**（最慢、需判真源）：按重复段逐段处理，合并后立即跑 `doc-audit` 复核重复率下降。
5. **事实与路径引用订正**（需取证 + 报审）：失效的 `src/...` 路径、过期数值。

同一轮内不要跳过 1、2 直接改 4，否则后续合并会基于错误索引做判断。

## 5. 项目文档红线（优化时不得破坏）

- `docs/README.md` 是唯一入口，新增/移动文档必须同步更新该索引。
- `docs/tasks.md` 只做轻量看板：任务编号、单行摘要、分类、提出时间、状态、详情链接；实现方案与过程日志一律进 `docs/tasks/TASK-YYYYMMDD-XX-任务简称.md`。
- `docs/DESIGN.md` 是「为什么这样设计」的意图索引层，不是第二真源；不得在其中复制数值表与规则细则。
- `docs/design/总纲/` 是设计真源；实现与文档冲突时先改文档对齐意图，再改代码。
- `docs/临时设计讨论/` 为未定稿草稿，纯文档修改**严禁自动提交 Git**，定稿后沉淀或移入 `docs/archive/discussions/`。
- 文档中的源码路径、类名、协议字段必须与实现一致；发现不一致且无法取证时报告，不猜测。
- 中文行文：术语按 `docs/design/总纲/19-名词术语对照表.md`，修仙专有词用拼音而非生造英文。

## 6. 收尾

- 每轮处置后重跑 `node scripts/doc-audit.mjs`，报告前后指标对比（零入链数、坏链数、超阈重复对、看板超宽行、超重详情篇数）。
- 纯文档改动按仓库规则**不自动 git 提交**；不得夹带代码改动。
- 若某条指标因合理设计原因无法下降（例如有意保留的双层索引），在报告中说明原因，**不要**改脚本阈值来「消化」它——阈值调整须单独讨论。
