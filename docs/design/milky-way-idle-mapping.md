## 已确认的玩法结构

### 行动与技能

原游戏把采集、生产、炼制和战斗都视为持续行动；行动有固定基础耗时、技能经验、输入材料、产出和可使用的消耗品。修仙版继续使用一个服务端权威行动队列，战斗也只是队列中的一种行动类型。

### 物品使用

公开数据将物品的可用行动类型、冷却、恢复量和临时增益放在物品定义中，而不是写死在界面。原游戏战斗消耗品分为食物和饮料两组、每组 3 个独立槽位和独立冷却；修仙版已合并为 3 个通用消耗品格，槽位不再限制品类（灵食、灵饮、符箓均可放入），运行时按物品类别决定恢复或增益分支。公开战斗配置包含 5 个功法槽，修仙版按界面密度调整为 4 个功法槽。修炼、探索、炼丹各有 3 个按行动类型配置的自动使用格（生产类不带触发器），`set_auto_use` 命令按 `actionType + slotIndex` 寻址。

消耗品和功法的默认触发器采用同一数据形态：`dependency + condition + comparator + value`，一个槽位内多条条件按 AND 判定；例如生命缺口达到恢复量、目标当前生命大于等于 1、或某个增益未激活。修仙版允许每个槽位最多保存 4 条自定义条件，空列表回退到目录默认条件；当前还支持生命/灵力当前值与缺口的百分比条件，百分比统一使用 0 到 100 的数值，避免把客户端的小数比例误当成绝对资源。

### 战斗数值基线

公开战斗模拟器使用事件队列推进攻击、施法、恢复、持续伤害、控制效果、狂暴和敌人重生，不按固定帧逐秒结算。首批修仙实现采用相同的事件边界模型，并将数值重命名为修仙术语。

已核对的计算结构：

1. 生命和灵力基线：`10 * (10 + stamina/intelligence level) + flat bonus`。
2. 命中率：`accuracy^1.4 / (accuracy^1.4 + evasion^1.4)`。
3. 物理与五行抗性减伤：正抗性使用 `100 / (100 + effective resistance)`；负抗性使用 `(100 - resistance) / 100`。
4. 穿透：正抗性先除以 `1 + penetration`。
5. 攻击间隔：基础间隔先除以 `1 + attack level / 2000`，再除以 `1 + attack speed`。
6. 防御、命中、伤害和闪避都由等级与装备/增益修正得到；不会在客户端重复计算。
7. 敌人可以拥有技能、掉落表、稀有掉落表和逐步增强的狂暴效果；修仙版已同时支持单敌人与多敌人遭遇、自动攻击、多个可触发功法、普通掉落和独立稀有掉落，并保留敌人死亡、整组胜利和重生边界。

控制效果的基础概率还会经过目标韧性修正：`effectiveChance = baseChance * 100 / (100 + tenacity)`。韧性使用百分比点数（例如 100 韧性将 70% 定身降为 35%），而不是客户端小数比例；定身、致盲和沉默都共享这一公式。

公开模拟器还明确了两个低频事件基线：生命/灵力每 10 秒恢复最大值的 1%，敌人每 60 秒检查一次狂暴层数；低阶敌人的狂暴计时为 180 秒，每达到一个计时周期获得 10% 命中和伤害倍率，最多 10 层。修仙版按遭遇独立计时，敌人死亡并重生时清零狂暴层数；恢复、狂暴和攻击共享同一相对时间轴。掉落率、稀有发现和掉落数量分别使用 `1 + bonus` 倍率，数量的小数部分用同一确定性随机源取整。

低阶 Jerry 的公开数据基线为 70 生命、100 灵力、约 3.49 秒攻击间隔、15 命中、15 闪避、15 普攻伤害和 15 经验。其普通掉落逐项独立投掷（例如货币 0.8、粗糙皮 1.0、麦子/糖 0.3），稀有宝箱另表约为 `0.0001923833`；修仙版将这些字段映射为灵石、聚气兽核、灵草、云糖和小聚气宝匣，数量按最小/最大区间使用服务端确定性随机数。

公开模拟器的多敌人区域使用带权独立抽取，因此允许同类敌人重复出现；每次抽取同时受 `maxSpawnCount` 与 `maxTotalStrength` 约束。玩家默认攻击第一名存活敌人，`allEnemies` 功法遍历全部存活敌人；只有整组敌人全部死亡才计一次胜利并在 3 秒后刷新。配置首领的区域每完成 10 组进入一次首领战。修仙版“暮影谷”按这一结构映射公开 Twilight Zone：阴尸/邪修/妖修强度分别为 70/80/100，最大 3 名、总强度上限 250；生命分别为 1,800/2,200/2,500，攻击间隔为 3,119/2,933/2,780 毫秒；第十组“暮影谷主”生命 8,800、攻击间隔 3,043 毫秒。名称、ID、掉落物和题材均使用修仙版自己的目录。

功法现在按“开始施法 → 施法完成 → 扣除灵力并结算效果”推进，冷却从完成边界开始；敌方功法也执行相同的灵力检查。功法槽等级会按目录中的每级伤害成长参与结算，避免出现“等级只显示、不影响战斗”的空字段。当前修仙目录包含 0 灵力聚气冲击、参考 Fireball 量级的 10 灵力离火弹、参考 Heal 量级的 60 灵力回春术，以及参考公开控制功法的缠丝诀（10% 定身 2 秒）、青木迷雾（50% 致盲 5 秒）、禁言符（60% 沉默 5 秒）和震山击（70% 定身 3 秒）。焚天风暴沿用公开 Firestorm 的 75 灵力、2 秒施法、15 秒冷却、0.6 倍直接伤害、6 秒持续伤害，并按 3 秒事件边界拆分持续伤害。公开消耗品的 `recoveryDuration` 采用 5 秒恢复事件分摊，冷却到点本身会触发一次条件重评估；修仙版已以 30 秒“回春灵露”作为首个持续恢复样本，并保留旧快照的战斗开始触发兼容字段。

这些公式来自公开实现的可读代码，属于本项目的参考基线；正式平衡仍以修仙版自己的数据和测试为准。

### 官网直接核对的交互边界

官网 Game Guide 对以下行为有明确说明，修仙版按同一行为建模但使用自己的名称和目录：

- 行动队列由玩家主动加入，队列项完成后继续处理下一项；离线时仍推进角色行动，官网公开默认离线进度上限为 10 小时。
- 战斗配置在原游戏中包含 5 个按优先级排列的功法槽、3 个食物槽和 3 个饮料槽；食物负责生命/灵力恢复，饮品提供有限时长增益。修仙版已调整为 4 个功法槽加 3 个通用消耗品格（不限品类），触发器模型保持一致。
- 功法需要消耗灵力，战斗中每次使用会获得功法经验；自动使用条件在进入战斗前配置。
- 战斗状态包括致盲、沉默和定身；官网公式页同时列出命中、抗性、穿透、吸血、再生和控制命中率计算，服务端事件队列按这些边界推进。

官网页面只作为玩法与交互参考，不作为运行时依赖；修仙版支持完全离线快进，且不引入官网的公会与房屋系统。

### 装备与减益映射（修仙版）

公开数据中的装备词缀已归一到服务端装备目录，客户端只提交 `ItemId + EnhancementLevel`，不接受客户端自定义属性：

| 目录项 | 修仙名称 | 基础词缀 | 强化总倍率表 |
| --- | --- | --- | --- |
| `equipment.cursed-spirit-bow` | 蚀心灵弓 | `curse 0.02`，双手、符箓/物理 | 0 到 20 级；20 级总倍率 50 |
| `equipment.furious-spirit-spear` | 沸血灵枪 | `fury 0.03`，主手、剑道/物理 | 同上 |
| `equipment.griffin-spirit-bulwark` | 玄狮重盾 | `weaken 0.03`，65 护甲、三系抗性 30 | 同上 |
| `equipment.sundering-spirit-crossbow` | 破阵灵弩 | `pierce 0.25`，主手、符箓/物理 | 同上 |

`fury` 命中叠层、未命中减半，`curse` 受击叠层并提高后续承伤，`weaken` 使攻击方后续伤害降低；每组状态最多 5 层，15 秒无刷新即过期，死亡/复活清空。多目标遭遇已经接入，但当前 `pierce` 仍表示一次无视目标抗性的穿透触发；公开版本中是否还存在目标转移语义需要继续核对后再独立建模，不能与群体功法混为一个字段。

### 市场

公开 Wiki 和客户端工具共同显示：市场同时存在买单和卖单，订单簿按物品和强化等级区分，列表包含订单 ID、价格、总量、已成交量、创建时间和状态。普通物品卖出税为 2%，特殊的 Cowbell Bag 为 18%；修仙版只保留普通物品的 2% 规则，暂不引入对应的特殊货币。

修仙版市场核心采用：

- 价格优先、同价时间优先（FIFO）。
- 买卖双方以挂单方价格成交，支持部分成交和撤单。
- 价格和数量使用整数 `long`，税后卖方收入使用向下取整。
- 挂牌价格按官方客户端的 1/2/5 数量级档位归一化，并且不能低于物品商店回收价；修仙版通过 `XiuxianMarketPricePolicy` 在服务端再次校验，客户端只做输入提示。
- 官方更新说明中的挂牌有效期为 30 天；修仙版账本已保存创建/过期时间，并以每个订单簿的到期时间索引执行分钟级低频回收。扫描只访问已到期时间桶，不遍历全部订单，未成交物品或灵石转入待领取结算。
- 每个物品/品阶是独立订单簿；订单簿不放进玩家 Fiber 状态，按品类分片。
- 订单簿核心单线程可驱动，外层市场分片负责并发；命令使用请求 ID 保证幂等。
- 推送只发送盘口/订单变化，不做全市场全量刷新。
- 盘口、市场指标和玩家挂单读取使用账本/盘口版本生成 `ETag`；浏览器按 3/5/10 秒分别重验证盘口、挂单和指标，页面不可见时暂停轮询，未变化时不生成或传输 JSON 正文。
- 当前 `local-json` 原型通过 `IXiuxianMarketLedgerStore` 在 `data/snapshots/market-owner.lock` 上取得进程级单写者租约，并在提交前检查 revision CAS；已有实例持有租约时，后续实例拒绝启动市场，避免两份内存订单簿同时写同一账本。市场分片使用 `fnv1a64-utf16-v1` 稳定哈希，不使用 .NET 进程随机哈希。

## 分阶段落地

1. **第一批（已落地）**：通用物品/消耗品目录；事件边界战斗模拟器；妖兽历练行动；可测试的高性能订单簿。
2. **第二批（已落地）**：战斗结果接入玩家快照与协议，增加灵食/灵饮槽和 5 个功法槽的可编辑命令。
3. **第三批（已落地）**：市场分片宿主、库存/灵石托管、幂等订单 ID、我的挂单索引、盘口与交易协议、账本快照恢复。
4. **第四批（已落地）**：按公开数据结构扩充采集、炼制、装备、强化和掉落表；战斗触发器、治疗功法、持续伤害、定身/致盲/沉默控制、韧性修正、普通/稀有掉落表和四类装备词缀均已进入目录与事件队列。
5. **第五批（已落地）**：加权多敌人生成、整组胜利、首存活目标、`allEnemies` 群攻、每十组首领、战区目录协议与复用敌情面板；同批补齐万人一小时多敌人快进基线和事件时间单调保护。
6. **第六批（进行中）**：继续扩充装备/区域/任务目录，补齐实时战场状态流、Release/P95 容量门槛和市场多实例事务边界；每一批都用离线快进与逐步推进一致性测试锁定结果。

## 待验证项

- Wiki 页面与游戏客户端会随版本更新；本项目不把某个公开快照当成永久真值，数据目录必须带版本号和来源。
- 公开工具可核对客户端字段和计算结构，但无法证明服务器内部所有边界规则；税费舍入、订单过期时长和特殊掉落规则在接入真实服务前需要单独验算。
- 战斗随机数必须使用服务端可重放的种子，不能调用客户端随机数；离线快进和在线推进必须共享同一事件处理器。

## 当前实现边界

- `XiuxianCombatSimulator` 已使用玩家、行动开始时间和遭遇 ID 派生的确定性种子；相同边界输入不会因在线或离线推进方式不同而改变战斗结果。功法施法完成、消耗品冷却、5 秒持续恢复、基础恢复（10 秒/1%）和遭遇狂暴（60 秒检查、180 秒一层、每层 10%、上限 10 层）均在同一事件队列中推进。控制命中按 `100 / (100 + tenacity)` 修正，韧性字段通过战斗配置协议持久化。
- 多敌人事件轴为每名敌人独立保存攻击、施法、灵力、控制、词缀、持续伤害和狂暴状态；玩家锁定第一名存活敌人，群体功法对所有存活目标逐一做命中和减伤结算，整组清空后统一进入刷新。区域完成数持久化在玩家快照中，用于跨行动和离线快进保持第十组首领轮次。
- 事件调度器要求时间戳严格单调推进；敌群清空后的攻击时间和控制到期不会覆盖刷新边界。离线状态仍记录 40 条历史日志，但不会积压只供在线 WebSocket 使用的待推送事件。
- 持续伤害以 3 秒为默认事件粒度，控制效果的过期时间也进入同一事件队列；定身会暂停攻击/施法，沉默只阻止功法选择，致盲只使普攻落空。控制命中使用目标韧性修正，且到期事件的同一时间边界仍可被状态触发器观察到；控制状态在死亡/复活时清理，避免离线快进把旧状态带入下一只妖兽。
- 每个战斗功法槽和消耗品格都可以保存最多 4 条 AND 条件；默认条件由目录返回，前端通过复用的 `CombatTriggerEditor` 修改后走同一个 `set_combat_loadout` 命令。条件支持绝对生命/灵力、生命/灵力百分比、缺口百分比、增益层数和三种控制状态。
- 聚气兽掉落已由单一掉落字段扩展为 `DropTable` 与 `RareDropTable` 两张表，结果返回逐物品数量字典；普通掉落率、稀有发现和掉落数量倍率均来自战斗配置并由服务端确定性随机结算；旧单掉落字段仍保留读取兼容，正式结算优先使用新表。
- 探索和炼丹也已接入同一自动使用槽：`寻灵香`提高灵草产出，`地火引`提高引气丹产出；倍率在行动完成边界向上取整，避免客户端显示与库存结算不一致。
- `XiuxianOrderBook` 已实现整数价格/数量、价格优先与同价 FIFO、部分成交、撤单权限和税后收入；税率在订单入簿前完成校验，`XiuxianMarketEngine` 以固定分片隔离品种锁。
- `XiuxianMarketCoordinator` 已提供并测试挂卖冻结物品、买单冻结最高价灵石、部分成交退款、卖方税后待领取和撤单解冻；市场账本包含活动订单、冻结和待领取资产，可在服务重启后恢复。
- `/api/actions`、`/api/items`、`/api/combat/abilities` 与 `/api/combat/encounters` 是前端行动详情、市场品种、功法选择和战区敌情的权威目录，避免 UI 复制输入、产出、生成权重、首领轮次和战斗规则。实时战场状态通过 `queueProgress.expedition` 下发，玩家跨遭遇资源通过 `combatResources` 下发；静态敌情面板仍只展示目录基线。
- `/api/combat/equipment` 是装备名称、槽位、基础词缀和强化奖励的权威目录；`set_combat_loadout` 的 `Equipment` 字段只接受目录 ID 与 0 到 20 级强化等级，服务端校验双手/主手互斥和重复槽位。
- 市场已开放 `market_place`、`market_cancel`、`market_claim` WebSocket 命令，以及对应的 HTTP 订单接口；玩家状态只发送库存增量补丁，盘口和我的挂单按局部请求刷新。
- 无会话玩家在 30 秒无访问后会从 ECS Fiber 转为序列化冷快照；重连或 API 访问会在同一 Fiber 内恢复并按 `LastSimulatedAt` 做离线快进，在线玩家集合不会因冷账号数量扩大。
- 玩家快照可通过 `Storage:DurableOutboxEnabled` 切换到 YuoCore 文件 WAL；写回成功后才 ack，启动 replay 未确认序列，避免进程在异步队列出队后丢失最新状态。该模式目前只覆盖玩家快照，市场账本仍需数据库事务化。
- 当前账本使用本地原子 JSON 快照（`data/snapshots/market-ledger.json`），并以存储契约统一 revision CAS 和进程级单写者租约，用于原型和恢复验证；`GET /api/market/topology` 返回主分片拓扑。正式多实例部署仍需接入带 Outbox/事务边界的数据库存储：账本 CAS、玩家快照和 Outbox 必须同事务提交，再由网关按稳定哈希把品种路由到唯一主分片。
