# 第二十六篇 全服排行榜与整点快照投影

> 状态：设计中（TASK-20261113-08）。本文是全服排行榜的唯一权威设计真源。
> 规约锚点：`docs/backend/commercial-persistence-architecture.md` §31/§117——排行榜只允许是**派生读模型**，绝不反向成为权威真相；本系统全部数据可由玩家分段与关系表确定性重建。

## 26.1 定位与红线

- 全服横向荣誉展示：为在线与离线全体账号提供可公开查阅的名次投影。
- **整点快照语义**：榜单反映「结算时刻的最近落盘态」，不追求实时；玩家在线产生的未落盘增量最迟随下一整点入榜。小时粒度天然吸收分段刷盘窗口差。
- **零读放大**：任何客户端请求不得触发解码/排序/聚合查询；读路径只命中内存预序列化字节。
- **不引新组件**：不引入 Redis/二级缓存/独立排行服务；单进程内存 + PostgreSQL 物化表即满足 2c4g/5000+ 账号容量目标。
- **只读派生**：榜单数据绝不参与行动结算、入队裁决、撮合或任何奖励发放；排行结果回写领域状态是被禁止的。
- 封禁/停用账号（`identity.players.status ≠ 1`）不入榜；未产生过 section 的新注册号自然缺席。

## 26.2 榜单清单（12 榜）

| 榜 ID | 名称 | 主排序 | 次序裁决（并列时） | 数据源 | 行内副字段 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `realm` | 境界榜 | `realmLevel` 降序 | `lifetimeExperience` 降序 → `player_seq` 升序 | projection 扩列 | 当前层修为 `experience`/`expToNext` |
| `technique.{id}` ×7 | 技艺榜（炼丹 `alchemy`/炼器 `forging`/制符 `talisman`/强化 `enhancement`/阵法 `formation`/采集 `gathering`/挖掘 `mining`） | 技艺等级降序 | 技艺经验降序 → `player_seq` 升序 | loadout 分段 `TechniqueExperiences` + `TechniqueCatalog.LevelFor` | 等级 + 累计经验 |
| `valuation` | 身家榜 | 身家总值降序 | `player_seq` 升序 | loadout 分段 + `PartyValuationService` 同口径估值 | 装备/功法/工具三分项 |
| `spirit-stone` | 灵石榜 | 灵石余额降序 | `player_seq` 升序 | `economy.player_asset_balances`（`currency.spirit-stone`/`variant=''`） | 余额 |
| `zongmen` | 宗门榜 | 成员数降序 | 大殿等级降序 → 宗门创建时刻升序 | `social.zongmen_members`+`social.zongmen`+`game.node_buildings` | 宗门名/前缀/成员数/大殿等级 |
| `duel` | 斗法榜 | `duelWins` 降序（生平击破同道） | `duelLosses` 升序 → `realmLevel` 降序 → `player_seq` 升序 | projection 扩列 | 胜/负场 |

- 每榜对外展示 **Top 50**；个人名次对全部参与者精确（含榜外）。
- **入榜门槛**：主排序值 ≤0 者不占名次（如灵石 0、技艺 0 级、斗法 0 胜），名次表不写零分行；`participantCount` 仍统计全部活跃账号。
- 技艺榜枚举以 `TechniqueCatalog.All` 为准；新增技艺自动成榜，无需改代码结构。
- 宗门榜行实体为宗门而非玩家，`playerId` 字段置空、以 `zongmenId` 标识；已解散宗门（`disbanded_at` 非空）剔除。

## 26.3 生涯击破同道（斗法榜数据前置）

斗法胜负目前仅存于行动/离线/每日三账本（每日 rollover、归档上限 10 条），无生涯持久计数。新增：

- `PlayerProgressionState` 增 `DuelWins`/`DuelLosses`（wire `duelWins`/`duelLosses`，可缺省解码为 0）——**生平击破同道 / 生平败于同道**。
- `PlayerAggregate.Progression` 暴露同名累计属性；记账点与 `TotalDefeats` 同模式就地累加并 `MarkDirty(Progression)`：
  - `CombatActionRules` 斗法回放落点 `duel.won`（`DuelWins=1` 处）与 `duel.lost` 非弃战分支（`DuelLosses=1` 处）；
  - `PlayerDuel.ApplyDuelForfeit` 弃战判负路径（`DuelLosses=1` 处）。
- 存档标签：`SectionCodec.CurrentSchemaVersion` +1（新字段可缺省解码，`MinReadableSchemaVersion` 不抬）；`PostgresSchema.Version` 同步 +1 并在迁移文件内嵌标签推进。
- 三账本语义不变：账本 `DuelWins`/`DuelLosses` 仍为周期统计口径；生涯计数与之并存、互不推导。

## 26.4 数据装配口径

物化输入四类来源，全部为「最近已落盘/已排队落盘态」：

| 类别 | 来源 | 说明 |
| :--- | :--- | :--- |
| 花名册 | `identity.players` | `player_id/display_name/player_seq`，过滤 `status=1` |
| 境界/斗法/展示 | `game.player_projection` 扩列 | `realm_rank`（已有）+ 新增 `experience/lifetime_experience/duel_wins/duel_losses/avatar`，由 `UpsertProjectionAsync` 同事务提取（progression/settings 载荷本就被解析，扩列零新增解码） |
| 技艺/身家 | `player_state_sections` `loadout` 分段批量解码 | 走 `PostgresSectionRepository.LoadSectionsAsync` 同口径（落盘行 + 刷盘队列较新版本叠加）；`TechniqueExperiences` 定级、`Equipment`+`AbilityExperiences` 估值 |
| 灵石/宗门 | `economy.player_asset_balances` / `social.zongmen*` / `game.node_buildings` | 纯 SQL 聚合 |

- 身家估值必须与 `PartyValuationService.Compute` **同一实现**（装备按 `itemId:+N` 变体的坊市参考价→回收价兜底；功法经验 ÷500 折算残卷×残卷单价；工具单列）：抽取共享纯计算入口（如 `ValuationMath.Evaluate(loadout, priceLookup, catalog)`），社交服务与榜单纯化共用，禁止复制口径。
- 投影列缺失（新列启用前的旧行）按 0/缺省处理；`avatar` 缺省回落 `player`。
- 不做在线运行时内存态覆盖：统一「落盘态」口径保证在线/离线同基准，小时粒度下内存-落盘窗口差无业务意义。

## 26.5 物化管线（`LeaderboardSnapshotWorker`）

单例 `BackgroundService`，整点对齐：

1. **触发**：周期 tick（~15s）检测跨过整点边界即物化；启动时若库内最新快照 `computed_at` 早于当前整点，立即补跑一次（冷启动/停机恢复即得有榜可看）。
2. **装配**：只读连接按 §26.4 拉取全部输入；5000 账号预算下 loadout 批量解码为最大头（Brotli+JSON ≈ 百毫秒级）。
3. **排序**：每榜按 §26.2 裁决链内存排序；次序含 `player_seq`（注册先后）兜底，保证同一输入集产出位级一致榜单（确定性可回放）。
4. **物化**：每榜生成 `entries`（Top 50，行内字段见 §26.7 DTO）+ `participantCount` + `computedAt`，预序列化为 JSONB；同时产出全部 `score>0` 玩家的 `(player_id, board_id, rank, score)` 名次行。
5. **落库**：单事务内 `game.leaderboard_snapshots` upsert + `game.leaderboard_ranks` 按榜整组重写（先 DELETE 该榜旧行再 INSERT，无陈旧残留）；同事务保证两表一致性。
6. **发布**：不可变快照对象原子交换进 `LeaderboardRuntime`（榜单 payload 预序列化字节 + `(board,playerId)→rank` 字典）；读路径零锁。
7. **失败**：物化异常保留旧快照、记错误日志，下一 tick 重试；不做指数退避（小时尺度足够宽松）。从未成功物化过且库内无快照时，端点返回 `503 Retry-After`。

预算（2c4g / 5000 账号）：装配 <400ms，排序+物化写 <1s，全程 <2s；10 万账号外推 ~40s 仍在整点预算内，届时再评估分批。

## 26.6 存储（schema v53）

```sql
ALTER TABLE game.player_projection
  ADD COLUMN experience double precision NOT NULL DEFAULT 0,
  ADD COLUMN lifetime_experience double precision NOT NULL DEFAULT 0,
  ADD COLUMN duel_wins double precision NOT NULL DEFAULT 0,
  ADD COLUMN duel_losses double precision NOT NULL DEFAULT 0,
  ADD COLUMN avatar varchar(64) NOT NULL DEFAULT 'player';

CREATE TABLE game.leaderboard_snapshots (
  board_id varchar(64) PRIMARY KEY,
  computed_at timestamptz NOT NULL,
  participant_count integer NOT NULL CHECK (participant_count >= 0),
  payload jsonb NOT NULL
);

CREATE TABLE game.leaderboard_ranks (
  player_id uuid NOT NULL REFERENCES identity.players(player_id),
  board_id varchar(64) NOT NULL,
  rank integer NOT NULL CHECK (rank > 0),
  score double precision NOT NULL CHECK (score > 0),
  updated_at timestamptz NOT NULL,
  PRIMARY KEY (player_id, board_id)
);
CREATE INDEX ix_leaderboard_ranks_board ON game.leaderboard_ranks(board_id, rank);
```

- `progression` 载荷 `duelWins`/`duelLosses` 为可缺省新增 → 存档标签 +1，表结构随上列 DDL；`migrations/0053_v52_to_v53.sql` 内嵌 `platform.schema_version` 标签推进。
- 名次行仅 `score>0` 参与者；预计行数 ≈ 账号数 × 命中榜数（远低于 6 万上限）。
- 快照表只保留最新一份（按 `board_id` upsert）；历史榜单不留存（无业务诉求，留存治理零负担）。

## 26.7 协议与端点

HTTP 拉取式（整点数据无推送诉求，WebSocket 不引入新消息）：

| 端点 | 语义 |
| :--- | :--- |
| `GET /api/v1/leaderboards` | 榜单元数据：`{ computedAt, boards: [{ boardId, kind, techniqueId?, participantCount, topScore? }] }`，驱动前端二级 Tab 与「下次结算」倒计时 |
| `GET /api/v1/leaderboards/{boardId}` | 单榜快照：`{ boardId, computedAt, participantCount, entries[50], myRank? }` |

- `entries` 元素 `LeaderboardEntryDto`：`rank / playerId? / displayName / avatar / realmLevel? / score` + 榜别副字段（`experience`/`expToNext`、`techniqueLevel`/`techniqueExp`、`valuationBreakdown`、`wins`/`losses`、`zongmenId`/`zongmenName`/`zongmenPrefix`/`memberCount`/`hallLevel`）；玩家行可附带 `zongmenPrefix`（若有宗门，前端冠名渲染）。
- `myRank` 仅已认证请求附带（本人名次+本人分数）；未上榜时为 `null`（前端显「未上榜」而非「榜外」）。
- 认证口径与 `players` 组一致（`RequireAuthorization`）；榜单不对匿名开放。
- **缓存头**：`ETag`（`computedAt` 派生）+ `Cache-Control: private, max-age=60`；整点内重复拉取命中 304/内存字节，响应体为预序列化 `ReadOnlyMemory<byte>` 零再编码。
- 运维旁路：ops 面板挂 `POST {ops}/api/leaderboards/rebuild`（立即重跑物化，供发布/修复后手动刷新）与最近物化时刻/耗时指标展示。

## 26.8 前端

- 新顶级页签 `leaderboard`（与「同道」同级入口）：`LeaderboardPage`。
- 二级榜 Tab：境界 / 技艺（下拉或七子页签，名称复用技艺既有 i18n 键）/ 身家 / 灵石 / 宗门 / 斗法。
- 行形态：名次徽标（1~3 名强化样式）+ 形象头像 + 道号（冠宗门前缀）+ 境界徽章 `RealmBadge` + 主数值与榜别副字段；点击玩家行弹 `PlayerCardModal`（已有名片体系，禁止另建）。
- 「我的名次」条：吸底/吸顶常驻显示本人在当前榜名次与分数；榜页顶注「结算于 HH:00，每小时整点更新」。
- 拉取策略：入页拉一次 + `visibilitychange` 复验 + 手动刷新按钮；ETag 自动 304。
- i18n：`leaderboard.*` 域词条登记（标题/榜名/列名/未上榜/结算时刻），遵守 `check-i18n-keys.mjs`。
- 公共组件红线：实体/名片/徽章一律复用既有组件；新增样式入独立 `leaderboard.css`，不私造已有模式。

## 26.9 性能预算

| 路径 | 量级 | 目标 |
| :--- | :--- | :--- |
| 读 | 500 并发峰值 | O(1) 内存 + 304；零 DB、零分配热点 |
| 整点物化 | 5000 账号 | <2s 全程；不写热路径（独立 worker，与市场/战斗事务无争用面） |
| 名次表写 | ≤6 万行/小时 | 单事务整组重写 <1s |
| 内存 | 12 榜 | 预序列化 payload ~10-20KB/榜 + 名次字典 <10MB |
| 快照表 | 12 行 JSONB | ~10-20KB/行 |

## 26.10 不变量与验收

- 排序确定性：同一输入集产出逐位一致榜单（tiebreak 必含稳定键 `player_seq`）。
- 派生红线：删除 `game.leaderboard_snapshots`/`leaderboard_ranks` 与投影扩列后，游戏权威行为零变化；排行数据可整表重建。
- 生涯斗法计数与三账本账本计数在单机自检场景可对账（生涯 ≥ 每日）。
- 测试口径：
  - 排序/裁决纯函数单测（并列、零分剔除、宗门并列人数、稳定键次序）；
  - 投影提取单测（progression/settings 载荷 → 扩列值，缺省/缺列容错）；
  - 端点契约测试（DTO 字段、ETag/304、myRank 鉴权行为、503 首启路径）；
  - 斗法生涯计数：胜/负/弃战三路径 + 导出恢复往返（Domain.Tests 同 `TotalDefeats` 既有模式）。
