# 第二十一篇 同道与组队系统

> **定位**：本篇是「同道」社交入口与完整组队系统的唯一设计真源。第十四篇 §14.5.2 的邀请制队伍仅描述最早的入队通道，本篇在其上扩展队伍档案、招募匹配、组队大厅与聊天队伍链接；传音频道机制本身仍以第十四篇为准。

---

## 21.1 定位与边界

1. **队伍是招募组织层**：目标类型/目标节点/身家门槛均为招募标签；「同图并肩作战」的战斗协同结算由 [§21.13](#2113-同图共战组队讨伐) 定义，队伍频道与成员在线态是已有的协作基础。
2. **同道 Tab**：左侧顶级导航「同道」是社交入口容器，本期只有「队伍」一个子页；好友管理仍留在聊天面板内，后续子页以同一子 Tab 结构扩展。
3. **服务端权威**：队伍档案、成员关系、匹配登记、大厅结果与身家数值全部由服务端产出；前端不本地推演成员/门槛/匹配结果，只保存最近一次服务端视图。
4. **存在感与持久化通知分离**：上线/下线/换节点只改变附近成员及在线位，主服按会话最近一次已入队的社交视图重新投影，禁止为纯存在感事件反复加载整套 PostgreSQL 社交关系。持久化社交变更仍从数据库构建完整视图；新会话尚无视图时由握手全量下发建立基线，可丢弃推送失败不前移基线。异步多订阅通知必须逐个等待，所有通知共享并行上限，不能只等待多播委托的最后返回值；协议仍使用同一 `SocialStateDto`。

## 21.2 队伍档案（Party Profile）

每支队伍除 `party_id`/`leader_id` 外持有一组档案字段，全部落 `social.parties`：

| 字段 | 协议字段 | 口径 |
| :--- | :--- | :--- |
| 队伍名称 | `name` | 1~32 字符；为空时服务端生成「{队长道号}的小队」 |
| 目标类型 | `activityKind` | `any`（不限）/`combat`（讨伐战斗）/`exploration`（历练采集）/`cultivation`（吐纳修炼）+ 五门技艺 `alchemy`（炼丹）/`forging`（炼器）/`talisman`（符箓）/`formation`（阵法）/`enhancement`（强化） |
| 目标节点 | `nodeId` | 空串 = 不限；否则必须是世界图已知节点 ID（`WorldGraph.ContainsNode`）；前端表单按「区域 → 地点」级联选择（区域不限即地点不限，协议无区域级任意节点语义），展示标签为「区域 · 地点」，创建/匹配表单默认当前地点 |
| 身家门槛 | `minValuation` | ≥0；0 表示不设门槛；加入者与自动匹配均按它裁决 |
| 公开性 | `isPublic` | true 进组队大厅；false 只能被邀请或经聊天队伍链接进入 |
| 斗法开关 | `pvpEnabled` | 队伍级 PVP 撮合开关（§7.10.4）；仅 `activityKind='combat'` 可为 true、仅队长可改、队员只读；改离讨伐自动归位 false |

- 队伍上限恒为 5 人（含队长，`SocialRuntime.MaxPartyMembers`）。
- 一名玩家最多属于一个队伍（`social.party_members.player_id` 主键）。
- 每名玩家最多一条待处理队伍邀请；加入任何队伍时邀请与匹配登记同步清除。

## 21.3 身家（valuation）口径

> 「身家」是招募用的量化参照，**不是战斗属性**；名称刻意不锁死——协议与代码统一用 `valuation`，界面文案集中在 i18n 词条（`social.valuation`），后续改名只动词条。

```
身家 = 战斗装备价值 + 功法价值 + 技艺工具价值
战斗装备价值 = Σ 每件已穿戴战斗装备（slot 非 tool-*）的单价（强化 +N 按变体 "+N" 独立计价）
技艺工具价值 = Σ 每件已穿戴技艺工具（slot 为 tool-*）的单价（强化 +N 按变体 "+N" 独立计价）
功法价值 = Σ 每门已参悟功法：max(1, 累计经验 / 500) × 对应残卷单价
装备单价(itemId, variant) = 坊市市场参考价 ?? 包含强化折旧的商店回收价（总纲 §4.6） ?? 0
残卷单价(ability.X) = item.fragment.X 坊市参考价 ?? item.fragment.X 配表回收价 ?? 0
构成结构 = ValuationBreakdownDto { Equipment, Abilities, Tools }，随各处身家字段下发供前端 Hover 展示

- **经验残卷折算**：游戏内 1 本残卷固定注入 500 点经验（全本秘籍注入 10,000 经验 = 20 本残卷）。身家功法估值严格按消耗的残卷资财总量结算，不再采用荒谬的「等级 × 全本秘籍单价」。已习得功法底线按 1 本残卷计。
- **六维/技艺不计入**：它们没有可交易的市场锚定价，身家保持「可支配资源口径」而非全角色强度。
- **数据源**：在线玩家取运行时聚合快照（`PlayerAggregateState.Loadout`）；离线玩家读 `loadout` 持久化分段（含刷盘队列叠加）。入队裁决与匹配自动并入使用实时值；列表展示允许 ≤30s 的估值缓存。
- **不可用兜底**：坊市分片未就绪/品种不在本进程分片 → 回落回收价；新玩家无 loadout 分段 → 身家 0。

## 21.4 无队伍四入口

| 入口 | 语义 |
| :--- | :--- |
| 自主选择 | 三模式页签：「组队大厅」「队伍匹配」「创建队伍」任选其一，一次只显示所选模式面板 |
| 队伍匹配 | 填目标类型/目标节点/队友最低身家 → `party.match.set`：服务端**先尝试自动并入**满足条件的公开队伍，未命中则登记入「匹配中」散人池 |
| 组队大厅 | 同类筛选 + 列表展示：公开队伍（含成员预览、门槛、加入按钮）与匹配中散人 |
| 创建队伍 | 填队名（可空→默认名）/目标类型/目标节点/身家门槛/是否公开 → 创建者任队长 |

## 21.5 匹配语义

1. `party.match.set {activityKind?, nodeId?, minValuation?}`：仅无队伍玩家可用；先写/更新 `social.party_seekers` 行，再扫描公开队伍尝试自动并入。
2. 自动并入条件（全部满足）：队伍 `is_public` 且未满员；活动类型与目标节点须与我方条件一致——`any`/空串为「不限」，筛选侧与被筛侧任一为不限即放行（不限目标的队伍对所有筛选可见，不限筛选的散人匹配全部队伍）；我方身家 ≥ 队伍 `min_valuation`；**每名在队成员身家 ≥ 我方申报的队友最低身家**。命中多队时取人数最多、其次创建最早者。
3. 未命中：保持「匹配中」状态（`SocialStateDto.seeking` 下发），可随时 `party.match.clear` 撤下；加入队伍时登记自动清除。
4. 散人池不自建队伍、不反向强拉：大厅里队长可对散人发 `party.invite`（走既有邀请-接受流程）。

## 21.6 组队大厅

- 拉取式：`PartyLobbyRequest(25) {requestId, activityKind?, nodeId?, minValuation?}` → `PartyLobby(26) {requestId, myValuation, parties[], seekers[]}`。
- `activityKind`/`nodeId` 筛选沿用「不限双向通配」口径（同 §21.5）；`minValuation` 筛选语义：公开队伍按「成员最低身家 ≥ 阈值」、散人按「本人身家 ≥ 阈值」。
- 公开队伍条目含成员预览（道号/在线/身家），前端据此展示加入可行性（我的身家 < 门槛时置灰但可见）。
- 散人条目含道号/在线/身家/目标/队友门槛；本人是队长时提供「邀请」按钮。
- 上限：各类列表最多返回最近 50 条，按创建时间倒序。

## 21.7 队伍管理与权限

| 操作 | 权限 | 说明 |
| :--- | :--- | :--- |
| `party.update` | 队长 | 档案补丁：name/activityKind/nodeId/minValuation/isPublic 任一非空字段即生效 |
| `party.invite` | 队长 | 按道号/ID 邀请；未满员、对方未组队 |
| `party.kick` | 队长 | 移除成员（不能踢自己，队长离队走 leave/移交） |
| `party.disband` | 队长 | 解散整队：成员行随 `ON DELETE CASCADE` 清除，聊天链接置空失效 |
| `party.leave` | 全体成员 | 队长离开时按加入序移交最早成员；最后一人离队删队 |
| `party.share` | 全体成员 | 把队伍卡片发布到世界/附近/好友频道 |
| `party.join` | 无队伍者 | 按 `partyId` 加入：公开队伍大厅加入与不公开队伍链接点击共用；校验未满员 + 身家 ≥ 门槛 |

队伍 ID 是不可猜的 UUID，链接本身即加入凭据：不公开队伍不进入任何列表，但持有链接者点击即可加入（仍受满员与身家门槛约束）。

## 21.8 聊天队伍链接

- `party.share {channel, targetPlayerId?}` 是社交动作，由服务端借 `ChatRuntime` 生成一条 `party_ref` 指向本队的传音消息；正文为服务端规范文本（不消耗 200 字输入），走与发言相同的频道作用域解析与限频。
- `ChatMessageDto.partyLink` 携带队伍卡片快照字段（队名/目标/门槛/成员数），由历史回放与实时广播统一供给。
- 队伍解散 → `party_ref` 外键 `ON DELETE SET NULL`，消息正文保留为普通文本，卡片消失。
- 前端在 `ChatRow` 渲染卡片：队名 + 目标徽标 + 门槛 + 「加入」按钮（已在队伍中/不满足条件时服务端拒绝并以错误帧提示）。

## 21.10 服务端组件

- `SocialRuntime`：新动作分发、档案校验、匹配自动并入、大厅构建（`BuildLobbyAsync`）、成员身家投影进 `BuildStateAsync`。
- `PartyValuationService`：身家计算唯一口径——在线读运行时快照、离线读 `loadout` 分段（刷盘队列叠加），单价经 `MarketRuntime.TryGetBestAskPrice`（本进程分片才查，否则回落回收价）。
- `ChatRuntime.SendPartyShareAsync`：队伍卡片发言（限频/作用域解析与文本发言同口径）。
- `OrderBook.BestAskPrice`：卖一档价只读出口（`_askIndex` 队首即最低挂售）。
- `SectionCodec.DecodeLoadout` / `PostgresSectionRepository.LoadSectionAsync`：单分段读取，避免大厅批量估值拉全量快照。
- 社交/队伍依旧不进玩家级单写者门禁；加队并发用 `social.parties` 行级 `FOR UPDATE` 串行化，满员判队友好地落在事务内。

## 21.12 邀请系统与功德占位（schema v13）

邀请关系属「同道」域：每名玩家持唯一邀请码，注册时可填邀请码结成邀请关系，按被邀请者
境界里程碑双向发放绑定功德奖励。

### 21.12.1 邀请码与链接

- 邀请码为服务端权威生成的玩家级常量：注册时写入 `identity.players.invite_code`
  （10 位大写字母数字，唯一索引 `ux_players_invite_code`，撞码整体重试新码），
  不变更不回收；邀请接口按 `player_id` 会话声明读回，前端不参与生成。
- 邀请链接为 `https://<host>/?invite=<code>` 静态入口；前端启动时读 `invite` 查询参数
  自动切到注册页并预填邀请码输入框，用户仍可手动修改。注册请求 `invitationCode` 可选。

### 21.12.2 邀请关系与奖励

- `social.player_invitations`：`invitee_id` 主键（一个被邀请者终身至多一条关系）、
  `inviter_id`、`invitation_code` 快照、`highest_realm_level`、
  `qi_rewarded`/`foundation_rewarded` 领取标记；CHECK 禁止自邀（新码入库前先解析
  邀请者，结构上不可能命中自己）。
- 奖励口径（一次性，全部走 `economy` 幂等事务）：
  - 注册：被邀请者 +1000 `item.gongde-bound` + 10000 `currency.spirit-stone`，
    邀请者 +1000 `item.gongde-bound`；同事务随注册落库，幂等键 `invitation.signup:{inviteeId}`。
  - 被邀请者突破至练气期（境界等级 19）：双方各 +1000 `item.gongde-bound`，
    幂等键 `invitation.milestone.qi:{inviteeId}`。
  - 被邀请者突破至筑基期（境界等级 31）：双方各 +2000 `item.gongde-bound`，
    幂等键 `invitation.milestone.foundation:{inviteeId}`。
- 里程碑触发点唯一：`progression.breakthrough` 命令成功后由运行时调
  `IInvitationRepository.GrantMilestonesAsync`；Serializable 事务内对邀请行
  `FOR UPDATE` 后逐里程碑经济入账并翻转标记，钱与标记同生同灭；崩溃留幂等键重放，
  重复突破不重复发奖。在线邀请者经钱包失效 + 结构化日志通知，离线者下次加载读到余额。
- 新增失败码：`INVALID_INVITATION_CODE`（邀请码不存在，注册失败）。

### 21.12.3 功德物品（本期占位）

- `item.gongde`：功德（可交易占位），`kind=category=currency`，`sellPrice=0`，
  可进坊市挂单、不可系统回收；本期无产出与消耗入口。
- `item.gongde-bound`：功德·绑定，`isTradable=false`、`sellPrice=0`，不可挂单、
  不可回收；邀请奖励唯一产出。`market.place` 服务端按目录 `isTradable` 拦截绑定物挂单。
- 后续功德的实际消耗/兑换玩法另立设计，本节只固化占位与发放口径。

### 21.12.4 协议与前端

- HTTP：`RegisterRequest` 增 `invitationCode`（可选）；新增 `GET /api/v1/invitation`
  返回 `{inviteCode, inviteeCount, invitees:[{displayName, highestRealmLevel,
  qiRewarded, foundationRewarded, createdAt}], invitedByName}`。邀请视图走低频 REST，
  不进 WebSocket 社交帧。
- 同道二级入口依次为「队伍、宗门、邀请」；PC 侧栏可展开/收起，移动端保留顶部二级页签。宗门规则见[第二十五篇](./25-宗门与专属驻地.md)。
- `SocialSubTab` 含 `party`、`zongmen`、`invite`；`SocialPage` 子页「邀请」：专属邀请码/邀请链接展示 +
  一键复制（Clipboard API 降级 execCommand）、奖励规则说明、被邀请人境界进度列表。
- 注册页邀请码输入框（`app.login.regInvite*`）；物品名走既有 `game.item.<id>` 词条链。
- 里程碑日志采用 `{{item:id|名称|数量}}` 结构化模板，双方各一条 system 频道战报。

## 21.13 同图共战（行动参与讨伐）

> **定位（TASK-20261009-05）**：组织只决定参与者、准备与开战/散场条件；一次行动参与会话持有唯一权威战斗态，同一场战斗只推演一次。成员行动仅引用会话并消费个人结算。队伍、团队、宗门身份不得进入战斗规则与表现分支。

### 21.13.1 组织条件与参与会话

- 队伍持有 `openSlots`（2~5，默认 3）；成员数等于开启槽位、全员准备、全员位于目标节点才开战。档案目标优先，未指定时取队长驻留节点。
- 开打冻结真实行动 ID、参与者顺序、各成员属性/功法槽/装备/气血灵力/跨战技能状态/持续消耗品 Buff、遭遇、公共种子与寻敌速度；会话内不接受实时装配面板变化。阵法类持续消耗品（`subCategory=formation`）的定格 Buff 全队生效——注入全部成员而非仅携带者（§7.9.5 作用范围条目）。已装载成员经其所有权通道定格最新内存态；未装载成员直接解码持久化真源（与装载对账同一事务快照口径），不触发实体装载与离线补算；若其收件箱仍压着未消费会话结算，定格前先在临时聚合上按装载对账同口径重放结算投影——冻结消费后的有效面板（散场复活回血等随之生效，不能从旧状态开下一场），收件箱本身不消费，挂机收益仍在其上线补算时生效。
- **战斗消耗品统一库存**：冻结启用的战斗槽位、槽序、触发条件与时钟，不冻结数量。范围为 `category=consumable`、适用 `combat`、`durable=false` 的全部自动使用物品，覆盖 potion/general、即时与持续；药品不是独立资产路径。在线模式按各成员真实可用余额工作钱包判定，余额不足只跳过对应物品，不清槽、不停战、不透支。买入成交后从后续合法边界自动使用；已生效限时效果不因卖空而撤销。合法判定边界与单人同口径（总纲 §7.8.3「自动激活边界」）：战斗入场同刻、每个战斗自然边界收尾落地后、槽位冷却/持续到期唤醒；战外相位不判定，判定读写会话存活战斗实时态。
- **在线资产顺序与原子结算**：任何影响冻结消耗品的资产变更须先在会话门内把在线会话推进到有效时刻，再按新余额验证和提交资产操作。检查点、成员消耗实扣和各成员 inbox 同事务提交，读集包含零余额键，冲突须丢弃整批结果重算；成员消费 inbox 不二次扣除。开场即时判定与初始检查点及实耗同事务提交，恢复不重演开场。交易或零时长同步不能凭空增加一次判定。
- **离线储备与模式切换**：全员离线时在同事务结清在线实耗、将冻结槽位对应非 durable 战斗消耗品可用数量按成员/物品/variant 去重划入储备并保存 Offline 模式。默认一小时批算只减储备、不逐件写库；储备空后继续战斗。离线入账只进普通钱包，不回填历史；实际批算末端才按净变动补入下一段储备，本批掉落下批可用。储备不可售用。有人回线先按旧储备结清至切换时刻，退回未耗量并原子切 Online；散场/指纹失配只退未耗储备。切换不重建战斗、不重置冷却、持续时间或随机序列。durable 持有型物品仅保留冻结资格，不锁件、不入储备；手动消耗品不参与自动使用。
- 在线/离线后台扫描的存在感快照仅用于筛选候选会话；最终模式必须在会话门内读取当前真实连接与握手中成员。等待查询或会话门期间已完成的上线/下线同步，不能被旧扫描结果反向覆盖；检查点模式、普通余额与离线储备仍同事务切换。
- 队伍斗法开关（`pvpEnabled`，§7.10.4）随会话创建冻结进参与规格；存续期间档案值与冻结值漂移即散场重建，与目标漂移同口径。勾选斗法的会话整队作为一个匹配单位进入斗法撮合，斗法战斗由会话权威相位回放共享剧本。
- 成员原队首挂起，参与行动作为引用锚点插队；结束后按权威时刻恢复原队首。无限重复不因波次完成自动出队。
- 参与引用不占个人行动容量：最多保留 256 项个人行动和 1 个参与引用。迁地命令插队前先按当前权威时刻散场并消费末批，不能把参与引用挂在赶路之后。
- 成员变动、取消准备、槽位失效、目标漂移、解散及原有离线超时逐出终止会话。断开连接本身不散场；离线超时仍按既有窗口裁决。
- 散场先推进会话到权威结束时刻，再投递终态。倒地成员以 1 点气血起身，灵力不恢复；未装载成员由散场流程强拉消费相同终态后卸载（总纲18 §14.6），不能从旧状态开下一场。就绪位跨会话常驻：散场不复位名册 ready，仅成员本人取消准备清除；散场后组织条件再次齐备时，下一次仲裁按常驻就绪直接重开新会话。

### 21.13.2 唯一权威执行上下文

- 会话独立持有搜索、波次、战斗、复活、事件顺序与全部成员战斗态，复用既有多盟友战斗规则；成员不再恢复、挂接或推进自己的同场遭遇。
- 会话有独立所有权与推进锁，不依附队长在线态。玩家仍按 PlayerId 哈希分片；同节点不意味着同分片，会话与成员之间只传不可变文档/结算。
- 任一成员在线（含断线宽限期）即实时推进，离线成员实体常驻装载并实时消费个人结算，收件箱不积压；全员离线时按 §1.2 三态主旨转入离线挂机批算——挂起游标是批算边界间的持久形态，按批算间隔（默认 1 小时）由主服推进，推进后逐成员强拉消费结算，不逐 tick 实时消耗；成员回线未轮到批算点时，由会话统一按墙钟即时补算一次，其他成员直接读取已推进状态（执行口径见总纲18 §14.6）。
- 成员离线不从冻结参战阵列移除；全员离线期间仍服从离线超时逐出等显式散场边界，补算不得越过该时刻。离线时长以成员断线时刻（`offline_since`）起算，强拉装载与结算消费不重置该锚点。
- 成员序是稳定身份，观察者 selfIndex 只决定本人标记、日志称谓与个人结算投影，不改变随机顺序、事件归因与战斗结果。
- 成员个人行动管线遇到参与引用时等待权威状态；搜寻/战间回复、冷却和战中血蓝均由会话计算，不重复消耗成员战斗预算。
- 自然回复余数按成员冻结并持续保存；各成员搜寻/战间回复保持自己的五秒进度，散场与血蓝一起交付，不能重置个人回复周期。战斗入场预扣灵力和吟唱须在同一边界进入全部成员投影；未首次交付的开场事件须随首批交付且只交付一次。
- 模式、模式生效时刻、批次边界、独立自动使用判定游标及离线储备随唯一检查点持久化。服务恢复先恢复会话与参与关系再接收相关资产写入；Offline 停机段只用已提交储备，Online 停机段按已提交在线规则恢复到恢复边界后再切模式，不虚构历史储备。未知提交查持久化版本与幂等事实，未确认时隔离会话，不发布不确定药效或战果。
- 首次装载一律从持久化真源对账；常规命令和周期推进仅对已有参与引用或会话宿主已发现的活跃/待消费成员查询结算，未参战玩家不承担逐人会话查询。成员提示不作为检查点或收益真源，开场、恢复与投递均更新提示。
- 并发上线/迁地触发的同一玩家社交刷新合并为单次在途通知；构建期间再次变更时继续发送最新状态。通知不逐条保存中间状态，主动社交指令回执仍必达，推送失败向调用方报告。
- **组队波次威胁度与怪物数量动态缩放（TASK-20261031-06）**：
  - 组队讨伐时，随队伍参战人数动态提升遭遇波次的最终威胁度（总预算），并解除单人单排 3 只的怪量封顶；
  - **威胁度加成倍率**：以单人 1 名玩家为基准（100% 威胁度，即 $1.0\times$）。队伍中每多一名玩家，最终威胁度增加 15%，最高封顶 160%（即 $\text{ThreatMultiplier} = \min(1.60, 1.0 + 0.15 \times \max(0, N - 1))$）；2人队伍 115%、3人队伍 130%、4人队伍 145%、5人队伍 160%；
  - **遭遇预算与怪量上限联动**：遭遇的 `[minBudget, maxBudget]` 危险度区间与 `maxTotalStrength` 同步乘以威胁度倍率；单人维持单波最多 3 只（`MaxWaveSize = 3`），组队（$N > 1$）波次怪物上限扩容至九宫格满编 9 只（`MaxAlliedWaveSize = 9`），使增加的战力预算充分具现为更多敌怪，由前端 3x3 九宫格自适应排布呈现。

### 21.13.3 收益与成员单写者

- 经验按参与人数平分后叠个人等级惩罚（MWI Level Malus）；共享掉率按全员掉落增幅放大，再按个人权重决定归属；每人只入账自己的份额。
  - **免罚门槛取大**：成员境界低于队内最高 20%（`level × 0.2`）或低于 12 级以内（两者取更高/更宽容的一方免罚），避免前期组队小号体验严重受挫；
  - **超额平滑惩罚**：超出免罚差距后每超 1 级罚 3%（`malus = min(0.9, 0.03 × (gap - exemptGap))`），惩罚封顶 90%；
  - **透传与角标呈现**：队伍成员条目透传当前境界等级与等级惩罚比率，触发惩罚时在队伍角色卡右上角显示惩罚角标（如 `-90%`）与提示说明。
  - **内功随成员快照冻结**：0 号内功位的功法与参悟等级进入冻结输入（内功不进施放序列，故不在冻结技能槽内），六维经验按该成员心法的 `rootExpMultipliers × eff` 逐人重分配，修为份额乘 `cultivationExpBonusPoints`；会话只投递增幅后的份额，修为瓶颈与底蕴兑换仍在成员单写者内结算。未装内功的成员维持「六维各得全额」口径。
- 会话产生个人经验、功法经验、掉落资产、击杀/死亡/轮次、战斗统计与战报增量，以及最终血蓝/技能状态。结算不覆盖成员实时设置、装备、社交状态或其他无关字段。
- 释放参与引用时回到个人属性上限，按既有个人面板规则夹取终态血蓝；参与期间的冻结上限不会继续覆盖散场后的实时装备面板。
- 成员只能在自己的玩家 gate 与 ECS Fiber 内消费，消费游标、资产、个人分段和收件箱回执必须原子提交；重复投递不重奖，失败不得先确认回执。
- 开场和散场通知只请求成员所有权内对账；活动引用由成员适配器读取权威会话行建立。社交层不得在已消费终局后依据旧开场规格再次入队。
- 行动账本、每日账本与离线账本继续使用现有统计入口；事件发生时刻决定自然日和离线口径。结算投影只消费既定结果，不重新运行战斗。
- 领取会话投影前，成员仍通过原资源管线推进个人暂存物品、Buff 到期与道龄；参与引用阻止个人战斗/原行动推进。该区间资产增量与会话份额、消费游标一并原子提交，投影本身不直接跳过个人模拟时钟。
- 成员等待期间不排个人五秒回复边界，冻结余数只由会话推进和交付；个人 Buff 到期、暂存入账及散场边界照常保留。配表删行动后的终局补投依据结算本身识别终态，不受消费前临时屏蔽散场的绑定影响。
- 同一推进生成的会话检查点与全部成员结算须原子持久化；逐帧展示读取当前会话投影，持久化收件箱只保留必要结算增量，避免离线成员复制完整战斗轨迹。

### 21.13.4 表现与协议

- 保留通用 `participation`、`expedition.allies`、波次、相位、战报与动画结构；盟友阵列固定序，成员读取会话当前状态的本人视角，不在回线后重演整场。
- 盟友属性与装配继续走 `UnitInspect` 按需冻结投影，本人属性面板沿用原通道；组织身份不进入 CombatArena 分支。
- 成员所见事件顺序、倒地/复活、敌方状态与结果必须一致；只有本人称谓、个人收益和 selfIndex 有视角差异。
- **复活时机策略（`respawnPolicy`，§7.9.4.1）**：每名成员在组队信息里设定**自己的**倒地起身时机——直接复活 / 全员可复活或存活 / 指定队友存活。该设置属于玩家个人数据（随 `settings` 分段持久化，开打时随成员冻结快照进入会话规格 `ActionParticipantSnapshot.RespawnPolicy` / `RespawnTargetPlayerId`，由会话在成员下标域解析为 `RespawnTargetIndex`），任何人不得代替他人设定；但它依赖「当前与谁同队」这一前提，故**队伍归属一变即重置为直接复活**：本人离队/换队/被踢/超时逐出/队伍解散/加入新队伍时重置本人；被指名队友发生上述情形时，指名了他的成员同样重置。与本人无关的成员离队不触发重置。会话内不受理实时改动（与冻结面板同口径），重置在下一场会话生效。等待有硬上限（阵亡时刻 + 2 × 读条），到点强制起身，等待不得冻结战场时钟。

### 21.13.5 持久化与恢复契约

- 冻结规格为会话输入，当前远征/战斗态、业务时钟和递增检查点版本为会话恢复真源；成员持有会话引用和已消费游标，不存可自行推进的冻结剧本副本。
- PostgreSQL 原子保存会话状态和各成员收件箱；会话记录及未消费结算独立于队伍生命周期，解散队伍不得级联删除。
- 重启恢复最新会话检查点，不再无条件散场；游戏配表指纹不一致等无法安全续算的明确边界必须保留证据并按最后确定时刻收尾，禁止静默重算/重复发奖。
- 恢复推进先核对持久化成员关系、就绪、槽位与目标驻留条件；发现已失效但缺少确定散场时刻时，保留原因和版本证据，按最后已提交检查点收尾，不补算不确定区间。
- 组织恢复的位置校验从同一事务快照读取最新 `world` 分段（durable 队列叠加已落库段），迁地 `edgeId` 视为不驻留；不使用可能滞后的 `player_projection` 判定会话成立。开场冻结完成后先强制提交已装载成员脏分段，再创建会话检查点；未装载成员以同一事务快照口径的持久化真源定格，无脏分段可提交。
- 确定未提交的会话推进恢复检查点；提交结局未知须通过原版本/幂等标识核验，不能继续覆盖不确定终态。成员消费复用既有经济事务确认与隔离语义：账本事务类型 `participation.settlement`，幂等键 `participation:{sessionId}:{playerId}:{sequence}`（sequence 为会话结算序号），事务 ID 取 SHA-256(幂等键) 前 16 位，随 `ParticipationInboxReceipt` 与成员分段在同一事务内原子提交。
- 单个会话的检查点冲突、未知提交或个人消费失败只隔离其自身，健康会话与其他玩家仍完成当批推进；批次最后报告故障，不能在玩家推进开始前冻结全服。
- 本地库版本同步升级，迁移只放 `migrations/`；新库由权威 DDL 建表。旧模型切换使用该目录内的离线一次性工具解压并移除成员旧参与行动、保留已结算收益及终态血蓝，再由 SQL 收尾旧会话和推进标签；自动 SQL 链遇到未转码载荷必须中止，禁止假升级或清库，不新增运行时兼容路径。
- 离线转码按运行时相同边界验证实际载荷大小、解压长度与 SHA-256；`stored_bytes` 为统计元数据，转码按实际新载荷长度重算。长度统计漂移不触发清库，原始长度或校验和不一致必须中止。

### 21.13.6 宗门累计任务边界

- 宗门累计采集/击杀/贡献任务订阅成员行动结果，维护独立贡献聚合，不创建同场战斗会话。
- 宗门共同讨伐可由组织适配器创建相同参与规格；本任务只落地现有队伍入口，不预建未来组织框架。

### 21.13.7 验收不变量

- 三名成员同场只有一份战斗推进预算，成本为一次推演加成员结算投影；单人普通讨伐规则不变。
- 不同观察者、在线/离线/回线顺序、检查点恢复产生相同战斗结果；成员回线不重新推演已完成区间。
- 散场到边界、倒地复活、资产幂等、个人账本与原行动恢复均保持；崩溃不得留下半结算或重复收益。
- 验证包括确定性与跨分片回归、PostgreSQL 原子失败/恢复、完整门禁、真实容量门禁、健康/WebSocket及本地三人队伍浏览器验收。

（`identity.players.player_seq`）、境界牌匾、身家、六维等级与经验进度、战斗经验、
战斗装备/技艺装备/功法技能，以及「战斗用品」详情页（丹药栏 3 槽 + 通用栏 3 槽
`autoUseSlots` 战斗栏域配置）。

- **查询通道**：`PlayerCardRequest{playerId}` → `PlayerCard`，一次按需查询应答，
  不随社交状态常驻下发（成员详情体量大、打开率低，常驻快照带宽不划算）；应答帧必达。
- **授权边界**：全域修士公开名片检视放行（支持队伍成员、附近同道、传音聊天道号点击等按需查询修士公开配置）；目标身份不存在时返回 `error="not-found"`，统一以 `error` 字段随 `PlayerCard` 应答下发。
- **数据源**：已装载玩家读运行时内存态，未装载玩家读持久化分段真源
  （`LoadAsync` + `DecodeAggregate`，与身家估值同一展示口径——不投影未消费会话结算）。
- **六维口径**：等级经 `PlayerCoreAttributes.Levels(RealmProgression)` 服务端派生，
  与 loadout 分段 `coreAttributes` 投影同形（exp + level + totalLevel），前端不重复换算。
- **序号口径**：`player_seq` 为注册自增编号，经社交仓储 `identity.players` 直查，
  不进入玩家聚合与快照分段。

## 21.15 队伍对弈：斗地主

> 独立表现原型：`tools/doudizhu-demo.html`。该单文件离线 Demo 使用本地角色图片及本地模拟余额，先验证洗发牌、叫抢/牌型反馈、选牌命中与逐步托管的整体表现；不连接正式社交或资产结算。角色不带背景框，余额只展示图标与数字；AI/托管每步至少一秒。正式对弈仍以服务端权威规则为准。

原型表现约束：洗牌依次呈现分堆、交错、拱桥收拢和收齐；发出的牌须沿连续轨迹到达接牌处后才进入对应手牌，发完后再统一理牌，禁止提前显示到手牌中。牌面使用统一矢量花色、双端点数和人物/王牌图案，牌背沿用墨绿金纹。本人形象朝向手牌。点击其他角色可打开本地互动菜单，支持番茄、鲜花、请茶、鼓掌的飞行/命中表现及快捷话语气泡；本地互动不消耗真实资产、不触发外部消息。

### 21.15.1 定位与牌桌

- 「对弈」是队伍内的休闲玩法，不进入行动队列、斗法或组队讨伐结算；玩法先落地斗地主。
- 仅队伍当前恰好 3 名成员时可开局，不提供观战位；三名成员按队伍加入顺序对应固定座次，斗地主准备状态独立于组队讨伐准备状态。
- 开局前三名成员必须全部准备，且队长发起开局；牌局期间队伍成员变化不得替换已冻结的玩家名册。
- 队长作为牌桌房主，可在开局前设置底注；默认 10 灵石，最小值 0，不设置业务上限。服务端拒绝负数、NaN、Infinity 与无法安全计算的金额。
- 底注修改只影响下一局；一局开始时冻结底注与参与者。每名参与者开局前必须持有不少于底注的可用灵石；底注为 0 时不要求持有灵石。
- 洗牌、发牌、叫/抢地主、出牌、超时策略、倍率和终局结果都由服务端产生；私有牌面只下发给牌主本人，公共状态对本队成员一致。

### 21.15.2 发牌与叫/抢地主

- 使用 54 张标准扑克牌，牌面排序为 3 至 A、2、小王、大王。洗牌由服务端安全随机源完成，牌序与牌局检查点一起持久化，不能由客户端指定。
- 每名玩家先发 17 张，余下 3 张作为底牌；地主确定后将底牌加入地主手牌。
- 房主启动前由 3 名玩家入座并准备。首位叫地主的玩家按洗牌结果确定；任一叫分后，其他未确定玩家可以选择不抢或抢地主。首次叫地主倍率为 1，每次成功抢地主将本局基础倍率翻倍；无人叫地主则本局作废并重新洗牌发牌。
- 地主身份、底牌、叫/抢过程与叫分倍率在开局定格；叫/抢操作不能由观战者或非当前操作玩家提交。

### 21.15.3 出牌与牌型比较

- 地主先出牌，其后按固定座次轮转。每轮玩家可出牌或不出；连续两名玩家不出后，最后出牌者重新获得自由领出权。手牌清空立即终局。
- 合法牌型包括：单张、对子、三张、三带一、三带二、顺子（至少 5 张）、连对（至少 3 对）、飞机（至少连续 2 个三张，可不带翅膀或带等量单牌/对子）、四带二（两张单牌或两对）、炸弹（四张同点）、王炸（大小王）。顺子/连对/飞机序列不得包含 2 或王；带牌不得重复使用牌张。
- 普通牌型只能由相同类别、相同牌张数/连续组数的更高主牌压过；炸弹压过任意非炸弹并按点数比较，王炸压过炸弹与其他牌型。选择不完整、重复、非本人手牌或不能压过当前牌的出牌由服务端拒绝，牌局状态保持不变。
- 断线重连恢复服务端当前检查点；操作必须带牌局 ID 与单调版本，旧状态/重复请求不得重复出牌或结算。成员离队或队伍解散不改变座次；牌局进入明确的终止/托管处理，不能静默换人。

### 21.15.4 底注结算与倍率

- 终局基础分为队长设置的底注；抢地主每次翻倍，炸弹和王炸各翻倍一次。地主胜时记为地主对两位农民各赢取一份；农民胜时地主分别向两位农民各支付一份。
- **春天**：地主获胜且两位农民整局均未出过牌，终局倍率再翻倍。**反春**：农民获胜且地主整局只出过一手，终局倍率再翻倍。春天与反春互斥。
- 每名输家分别承担其应付份额；若终局时可用灵石不足，按当前可用余额全额扣至 0（all-in），只将实际扣得金额记入赢家；结算在单个 PostgreSQL 事务内完成且不得凭空增发、不得出现负余额。每局终局写幂等结算键，重复提交不重复扣款或入账。
- 底注为 0 时仍完整记录和显示倍率、输赢及牌型，不产生灵石分录。

### 21.15.5 持久化、协议与验收

- 队伍底注随队伍档案持久化；活跃牌局检查点独立持久化完整牌序、座位、私有手牌、出牌历史、当前阶段/操作人、倍率、状态版本与终局结果，以支持服务重启和玩家重连。
- WebSocket 契约区分牌桌指令、公共牌局快照和玩家私有手牌；服务器按成员身份过滤私有信息。队长权限只用于设置底注和开始牌局，普通成员仅能操作自己的座位。
- 关键回归覆盖牌型分类/压制边界、抢地主与倍率、炸弹/王炸、春天/反春、非法操作不变更状态、断线恢复、并发版本冲突、资产不足与终局幂等。
- UI 在同道队伍信息中提供「对弈」视图，显示座位、状态、公共出牌区、本人手牌、叫/抢/出牌/不出操作及倍率与终局结算；队长可编辑底注。沿用现有修仙设计 tokens、浮层与表单组件，兼顾桌面和移动端。

### 21.15.6 页面入口、独立准备与托管

- 「队伍」和「对弈」不新增为应用主导航项，均位于「同道」的「队伍」面板中；队伍面板顶部以两个页签切换「队伍」与「对弈」。宗门与邀请仍由同道现有导航承载。
- 对弈页签未开局时显示独立的准备与设置页面：游戏类型选择目前仅提供斗地主，展示所有队员的名称、角色、准备状态及可用灵石。斗地主准备只写 `doudizhu_ready`，与组队讨伐准备 `ready` 完全独立。
- 牌局进入叫/抢地主或出牌阶段后切换为完整斗地主牌桌，牌桌铺满应用中间内容列（主内容区），保留应用顶栏、左右侧栏与整体导航；结束结算继续留在中间牌桌视图。牌桌围绕三座位、公共出牌区与本人手牌布局，不呈现队伍管理文本面板。
- 三个座位复用队伍名册的角色头像与道号，并展示手牌数量、地主身份、轮次与托管状态。队内可见各成员 `currency.spirit-stone` 当前可用余额，由服务端从资产账本投影，不以身家代替灵石。
- 左上对手依次展示名称、角色与手牌数、灵石，所出牌紧邻其右侧；右上对手镜像布局，出牌在其左侧。本人名称、角色和灵石位于牌桌右下角，本人手牌居中靠下，操作按钮在手牌附近。各座位分别展示当前轮最近一次出牌或不出，不显示底部牌局记录。
- 牌桌受中间主内容区边界约束，保留底部日志/聊天停靠区，不能覆盖聊天或输入区域。
- 开局与结算不自动取消斗地主准备；结算后在牌桌内显示结果及「再来一把 / 结束」菜单，全员仍准备时队长可发起下一局，其他成员等待队长。任一成员选择结束或取消准备即取消本人的准备，并原子移除已结束牌桌，所有成员返回准备页；其他成员已有准备保持不变。进行中禁止取消准备，避免中途退出绕过结算。
- 本人手牌以扑克牌面横向扇列展示；鼠标悬停牌张时抬起预览，点击后选中并保持抬起状态，再次点击取消；触屏点击使用相同选牌状态。所有有效牌张均可读、可操作，不以纯文本手牌替代牌面。
- 牌桌在桌面与窄屏下都保持三座位、公共出牌区和本人手牌可见；窄屏允许手牌横向滚动，操作区固定在手牌附近且不得遮挡牌面。
- 每次叫/抢地主或出牌操作后，当前操作座位获得 30 秒服务端时限。有效操作结束或超时自动操作后，下一操作重置时限；客户端倒计时只负责展示，服务端时钟是准入依据。
- 玩家可随时主动开启/取消本人托管。主动开启后，当前座位至少思考 1.1 秒再进行一次操作；否则在本人下次轮到时按同样节奏操作。托管状态随牌局检查点持久化，可在断线恢复后继续。
- 当前座位在 30 秒内没有有效操作时，服务端将该座位切换为托管并立即执行一次合法操作；不能由客户端提前触发超时。托管操作沿用牌型判定与牌局结算的同一领域状态机。
- 托管叫牌策略：尚无人叫地主时叫地主；已有地主后不再抢地主。托管按普通牌、连续牌、飞机、四带二与炸弹等标准牌型生成合法候选，优先能一次出完的组合，其次减少剩余拆分手数并保留炸弹；队友领牌时除能直接获胜外不压制。所有选择仍须经过标准规则校验。
- 多名座位同时托管时，服务端每次只处理一个已到操作时刻的座位，逐步保存和广播，严禁在一次循环中执行完整牌局。状态与完整出牌记录按版本比较交换落盘，避免离线机器人停滞或并发重复结算。
- 到期扫描由服务端后台任务负责，重启后从活跃牌局检查点继续；座位托管标记、当前回合截止时间和自动操作与牌局版本共同持久化。

### 21.15.7 正式牌桌表现与同桌互动

- 将 `tools/doudizhu-demo.html` 已认可的表现迁入正式 React 前端，使用真实角色、道号、准备状态和灵石；横屏牌桌只占中间区域，保留应用聊天停靠区。竖屏对局面板铺满游戏视口并保留队伍/对弈页签，本人手牌最多三排，角色缩小，按钮与多排触控选牌不互相遮挡。
- 服务端持久化发牌开始时刻和操作开放时刻。开局/无人叫地主重发牌预留 9 秒洗发牌及理牌；定地主后预留 2.4 秒翻底牌、派底牌和理牌。后续操作间保留 350 毫秒表现时间，30 秒操作倒计时从开放时刻计算。后台、重连和切回牌桌按服务端时刻恢复，不回放过期动画、不推迟权威时限。
- 仅向本人投影其 17 张初始发牌顺序，不下发其他玩家的牌或完整牌序。牌逐张飞行到固定牌槽后才显示为手牌，完成后平滑理牌；地主的三张底牌同样单独飞入。牌面采用原型矢量美术，花色映射遵循服务端编号。
- 大小王的 `JOKER` 角标与中文名称固定竖排，字形保持正立；手牌、底牌、出牌与飞牌共用该规则，不随界面缩放或响应式断点改变排版方向。
- 正式牌面以固定 SVG 坐标统一布局，数字、花色、人物图案和王字仅随整牌等比缩放，所有分辨率、缩放与牌面用途均不改变内部构图。理牌保持卡牌标识与选中状态，仅在手牌顺序或槽位变化时做一次连续位移，不重复叠加动画；触控命中与发牌落点使用同一多排槽位坐标。
- 牌局时间投影须附带同一权威时钟读取的服务端当前时刻，客户端以此同步动画年龄、操作开放和倒计时；浏览器与服务端系统时钟不要求一致。手动操作失败须显示服务端拒绝原因。
- 牌桌提供全屏进入/退出按钮，优先使用浏览器 Fullscreen API，受限环境使用页面全屏布局回退。横竖屏均按当前方向响应排版，切换全屏不锁定设备方向，退出恢复队伍面板与既有聊天布局。
- 叫/不叫/抢/不抢记录显式下发，初叫者在其他人抢地主后保留一次最终抢回机会。出牌显示标准牌型名称；提示在本人的合法候选间轮换，仅用于选牌，最终出牌仍由服务端校验。
- 点击其他角色，通过公共浮层打开番茄、鲜花、请茶、鼓掌及固定快捷话语。服务端校验发送者与目标属于同一牌桌，按发送者限频 1 秒，给同桌广播短暂互动事件；各端按事件标识去重播放飞行/命中与话语气泡。互动不改变牌局版本、不持久化、不扣灵石；重连不重放过期互动，不伪造其他真实玩家的回复。
- 同桌互动浮层仅在本地发送成功后关闭；离线、限频与服务端拒绝均给出可见反馈。成功表现只以服务端确认事件为准，且发起者也会收到确认事件。
