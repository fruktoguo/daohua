# 第二十一篇 同道与组队系统

> **定位**：本篇是「同道」社交入口与完整组队系统的唯一设计真源。第十四篇 §14.5.2 的邀请制队伍仅描述最早的入队通道，本篇在其上扩展队伍档案、招募匹配、组队大厅与聊天队伍链接；传音频道机制本身仍以第十四篇为准。

---

## 21.1 定位与边界

1. **队伍是招募组织层**：目标类型/目标节点/身价门槛均为招募标签；「同图并肩作战」的战斗协同结算由 [§21.13](#2113-同图共战组队讨伐) 定义，队伍频道与成员在线态是已有的协作基础。
2. **同道 Tab**：左侧顶级导航「同道」是社交入口容器，本期只有「队伍」一个子页；好友管理仍留在聊天面板内，后续子页以同一子 Tab 结构扩展。
3. **服务端权威**：队伍档案、成员关系、匹配登记、大厅结果与身价数值全部由服务端产出；前端不本地推演成员/门槛/匹配结果，只保存最近一次服务端视图。

## 21.2 队伍档案（Party Profile）

每支队伍除 `party_id`/`leader_id` 外持有一组档案字段，全部落 `social.parties`：

| 字段 | 协议字段 | 口径 |
| :--- | :--- | :--- |
| 队伍名称 | `name` | 1~32 字符；为空时服务端生成「{队长道号}的小队」 |
| 目标类型 | `activityKind` | `any`（不限）/`combat`（讨伐战斗）/`exploration`（历练采集）/`cultivation`（吐纳修炼）+ 五门技艺 `alchemy`（炼丹）/`forging`（炼器）/`talisman`（符箓）/`formation`（阵法）/`enhancement`（强化） |
| 目标节点 | `nodeId` | 空串 = 不限；否则必须是世界图已知节点 ID（`WorldGraph.ContainsNode`）；前端选项按「区域 · 地点」展示，创建/匹配表单默认当前地点 |
| 身价门槛 | `minValuation` | ≥0；0 表示不设门槛；加入者与自动匹配均按它裁决 |
| 公开性 | `isPublic` | true 进组队大厅；false 只能被邀请或经聊天队伍链接进入 |

- 队伍上限恒为 5 人（含队长，`SocialRuntime.MaxPartyMembers`）。
- 一名玩家最多属于一个队伍（`social.party_members.player_id` 主键）。
- 每名玩家最多一条待处理队伍邀请；加入任何队伍时邀请与匹配登记同步清除。

## 21.3 身价（valuation）口径

> 「身价」是招募用的量化参照，**不是战斗属性**；名称刻意不锁死——协议与代码统一用 `valuation`，界面文案集中在 i18n 词条（`social.valuation`），后续改名只动词条。

```
身价 = 装备价值 + 功法价值
装备价值 = Σ 每件已穿戴装备的单价（强化 +N 按变体 "+N" 独立计价）
功法价值 = Σ 每门已参悟功法：参悟等级 × 对应秘籍单价
单价(itemId, variant) = 坊市当前最低挂售（卖一档）价
                      ?? 配表回收价（ItemDefinition.SellPrice）
                      ?? 0（物品不在配表时）
```

- **功法↔物品映射**：`ability.X` → `item.tome.X`；配表无该秘籍时回落 `item.fragment.X`（残卷）；两者皆无按 0 计。
- **参悟等级**由功法经验经 `AbilityExpCurve.LevelFor` 导出（与面板同式）。
- **六维/技艺不计入**：它们没有可交易的市场锚定价，身价保持「可支配资源口径」而非全角色强度。
- **数据源**：在线玩家取运行时聚合快照（`PlayerAggregateState.Loadout`）；离线玩家读 `loadout` 持久化分段（含刷盘队列叠加）。入队裁决与匹配自动并入使用实时值；列表展示允许 ≤30s 的估值缓存。
- **不可用兜底**：坊市分片未就绪/品种不在本进程分片 → 回落回收价；新玩家无 loadout 分段 → 身价 0。

## 21.4 无队伍四入口

| 入口 | 语义 |
| :--- | :--- |
| 自主选择 | 三模式页签：「组队大厅」「队伍匹配」「创建队伍」任选其一，一次只显示所选模式面板 |
| 队伍匹配 | 填目标类型/目标节点/队友最低身价 → `party.match.set`：服务端**先尝试自动并入**满足条件的公开队伍，未命中则登记入「匹配中」散人池 |
| 组队大厅 | 同类筛选 + 列表展示：公开队伍（含成员预览、门槛、加入按钮）与匹配中散人 |
| 创建队伍 | 填队名（可空→默认名）/目标类型/目标节点/身价门槛/是否公开 → 创建者任队长 |

## 21.5 匹配语义

1. `party.match.set {activityKind?, nodeId?, minValuation?}`：仅无队伍玩家可用；先写/更新 `social.party_seekers` 行，再扫描公开队伍尝试自动并入。
2. 自动并入条件（全部满足）：队伍 `is_public` 且未满员；活动类型与目标节点须与我方条件一致——`any`/空串为「不限」，筛选侧与被筛侧任一为不限即放行（不限目标的队伍对所有筛选可见，不限筛选的散人匹配全部队伍）；我方身价 ≥ 队伍 `min_valuation`；**每名在队成员身价 ≥ 我方申报的队友最低身价**。命中多队时取人数最多、其次创建最早者。
3. 未命中：保持「匹配中」状态（`SocialStateDto.seeking` 下发），可随时 `party.match.clear` 撤下；加入队伍时登记自动清除。
4. 散人池不自建队伍、不反向强拉：大厅里队长可对散人发 `party.invite`（走既有邀请-接受流程）。

## 21.6 组队大厅

- 拉取式：`PartyLobbyRequest(25) {requestId, activityKind?, nodeId?, minValuation?}` → `PartyLobby(26) {requestId, myValuation, parties[], seekers[]}`。
- `activityKind`/`nodeId` 筛选沿用「不限双向通配」口径（同 §21.5）；`minValuation` 筛选语义：公开队伍按「成员最低身价 ≥ 阈值」、散人按「本人身价 ≥ 阈值」。
- 公开队伍条目含成员预览（道号/在线/身价），前端据此展示加入可行性（我的身价 < 门槛时置灰但可见）。
- 散人条目含道号/在线/身价/目标/队友门槛；本人是队长时提供「邀请」按钮。
- 上限：各类列表最多返回最近 50 条，按创建时间倒序。

## 21.7 队伍管理与权限

| 操作 | 权限 | 说明 |
| :--- | :--- | :--- |
| `party.update` | 队长 | 档案补丁：name/activityKind/nodeId/minValuation/isPublic 任一非空字段即生效 |
| `party.invite` | 队长 | 按道号/ID 邀请；未满员、对方未组队 |
| `party.kick` | 队长 | 移除成员（不能踢自己，队长离队走 leave/移交） |
| `party.disband` | 队长 | 解散整队：成员行随 `ON DELETE CASCADE` 清除，聊天链接置空失效 |
| `party.leave` | 全体成员 | 队长离开时按加入序移交最早成员；最后一人离队删队 |
| `party.share` | 全体成员 | 把队伍卡片发布到世界/附近/好友频道 |
| `party.join` | 无队伍者 | 按 `partyId` 加入：公开队伍大厅加入与不公开队伍链接点击共用；校验未满员 + 身价 ≥ 门槛 |

队伍 ID 是不可猜的 UUID，链接本身即加入凭据：不公开队伍不进入任何列表，但持有链接者点击即可加入（仍受满员与身价门槛约束）。

## 21.8 聊天队伍链接

- `party.share {channel, targetPlayerId?}` 是社交动作，由服务端借 `ChatRuntime` 生成一条 `party_ref` 指向本队的传音消息；正文为服务端规范文本（不消耗 200 字输入），走与发言相同的频道作用域解析与限频。
- `ChatMessageDto.partyLink` 携带队伍卡片快照字段（队名/目标/门槛/成员数），由历史回放与实时广播统一供给。
- 队伍解散 → `party_ref` 外键 `ON DELETE SET NULL`，消息正文保留为普通文本，卡片消失。
- 前端在 `ChatRow` 渲染卡片：队名 + 目标徽标 + 门槛 + 「加入」按钮（已在队伍中/不满足条件时服务端拒绝并以错误帧提示）。

## 21.10 服务端组件

- `SocialRuntime`：新动作分发、档案校验、匹配自动并入、大厅构建（`BuildLobbyAsync`）、成员身价投影进 `BuildStateAsync`。
- `PartyValuationService`：身价计算唯一口径——在线读运行时快照、离线读 `loadout` 分段（刷盘队列叠加），单价经 `MarketRuntime.TryGetBestAskPrice`（本进程分片才查，否则回落回收价）。
- `ChatRuntime.SendPartyShareAsync`：队伍卡片发言（限频/作用域解析与文本发言同口径）。
- `OrderBook.BestAskPrice`：卖一档价只读出口（`_askIndex` 队首即最低挂售）。
- `SectionCodec.DecodeLoadout` / `PostgresSectionRepository.LoadSectionAsync`：单分段读取，避免大厅批量估值拉全量快照。
- 社交/队伍依旧不进玩家级单写者门禁；加队并发用 `social.parties` 行级 `FOR UPDATE` 串行化，满员判队友好地落在事务内。

## 21.12 邀请系统与功德占位（schema v13）

邀请关系属「同道」域：每名玩家持唯一邀请码，注册时可填邀请码结成邀请关系，按被邀请者
境界里程碑双向发放绑定功德奖励。

### 21.12.1 邀请码与链接

- 邀请码为服务端权威生成的玩家级常量：注册时写入 `identity.players.invite_code`
  （10 位大写字母数字，唯一索引 `ux_players_invite_code`，撞码整体重试新码），
  不变更不回收；邀请接口按 `player_id` 会话声明读回，前端不参与生成。
- 邀请链接为 `https://<host>/?invite=<code>` 静态入口；前端启动时读 `invite` 查询参数
  自动切到注册页并预填邀请码输入框，用户仍可手动修改。注册请求 `invitationCode` 可选。

### 21.12.2 邀请关系与奖励

- `social.player_invitations`：`invitee_id` 主键（一个被邀请者终身至多一条关系）、
  `inviter_id`、`invitation_code` 快照、`highest_realm_level`、
  `qi_rewarded`/`foundation_rewarded` 领取标记；CHECK 禁止自邀（新码入库前先解析
  邀请者，结构上不可能命中自己）。
- 奖励口径（一次性，全部走 `economy` 幂等事务）：
  - 注册：被邀请者 +1000 `item.gongde-bound` + 10000 `currency.spirit-stone`，
    邀请者 +1000 `item.gongde-bound`；同事务随注册落库，幂等键 `invitation.signup:{inviteeId}`。
  - 被邀请者突破至练气期（境界等级 19）：双方各 +1000 `item.gongde-bound`，
    幂等键 `invitation.milestone.qi:{inviteeId}`。
  - 被邀请者突破至筑基期（境界等级 31）：双方各 +2000 `item.gongde-bound`，
    幂等键 `invitation.milestone.foundation:{inviteeId}`。
- 里程碑触发点唯一：`progression.breakthrough` 命令成功后由运行时调
  `IInvitationRepository.GrantMilestonesAsync`；Serializable 事务内对邀请行
  `FOR UPDATE` 后逐里程碑经济入账并翻转标记，钱与标记同生同灭；崩溃留幂等键重放，
  重复突破不重复发奖。在线邀请者经钱包失效 + 结构化日志通知，离线者下次加载读到余额。
- 新增失败码：`INVALID_INVITATION_CODE`（邀请码不存在，注册失败）。

### 21.12.3 功德物品（本期占位）

- `item.gongde`：功德（可交易占位），`kind=category=currency`，`sellPrice=0`，
  可进坊市挂单、不可系统回收；本期无产出与消耗入口。
- `item.gongde-bound`：功德·绑定，`isTradable=false`、`sellPrice=0`，不可挂单、
  不可回收；邀请奖励唯一产出。`market.place` 服务端按目录 `isTradable` 拦截绑定物挂单。
- 后续功德的实际消耗/兑换玩法另立设计，本节只固化占位与发放口径。

### 21.12.4 协议与前端

- HTTP：`RegisterRequest` 增 `invitationCode`（可选）；新增 `GET /api/v1/invitation`
  返回 `{inviteCode, inviteeCount, invitees:[{displayName, highestRealmLevel,
  qiRewarded, foundationRewarded, createdAt}], invitedByName}`。邀请视图走低频 REST，
  不进 WebSocket 社交帧。
- `SocialSubTab` 增 `invite`；`SocialPage` 子页签「邀请」：专属邀请码/邀请链接展示 +
  一键复制（Clipboard API 降级 execCommand）、奖励规则说明、被邀请人境界进度列表。
- 注册页邀请码输入框（`app.login.regInvite*`）；物品名走既有 `game.item.<id>` 词条链。
- 里程碑日志采用 `{{item:id|名称|数量}}` 结构化模板，双方各一条 system 频道战报。

## 21.13 同图共战（行动参与讨伐）

> **定位**：本节定义「组织接入一次行动参与会话」与讨伐执行的边界。Party/Team/Guild 只负责成员、权限、准备、容量和开战条件；讨伐行动只消费通用参与上下文，不识别组织类型。当前落地仍采用「共享剧本、各自推演」，不引入跨分片共享战斗实体。

### 21.13.1 组织条件与参与会话

- 队伍仍持有 `openSlots`（开启槽位数，2~5，默认 5），全员准备且位于目标节点时创建一次 `ActionParticipationSpec`。
- 会话规格包含实际行动 ID、固定参与者顺序、冻结参与者面板、遭遇 ID、公共种子、目标节点和统一寻敌速度；规格不包含 Party/Team/Guild 类型。
- 组织关系只决定谁可以参与以及何时创建/结束会话；同一参与规格可由队伍、团队或宗门适配器创建。
- 会话期间每名成员的行动队首挂载通用 `ActionParticipationBinding`，原行动挂起；结束后按权威结束时刻推进到边界并恢复原行动。
- 队伍成员变动、取消准备、离队、被踢、槽位失效或离线超时会结束会话；会话结束只改变参与绑定，不改变讨伐行动的执行规则与表现数据。

### 21.13.2 讨伐执行上下文

- 讨伐执行器接收 `ActionParticipationSpec` 的冻结战斗输入，继续复用普通讨伐的搜索、波次、战斗、死亡、复活、事件和盟友投影路径。
- 单人讨伐是参与者数量为 1 的同一条多盟友执行路径；参与者数量上限由组织适配器裁决，不由战斗内核硬编码。
- 成员序是内部稳定身份；观察者的 `selfIndex` 只影响协议中「本人」标记，不得改变随机侧位、事件归因 ID、成员顺序或战斗结果。
- 参与会话的开始/结束命令按 `sessionId + seq` 幂等持久化投递；装载时按事件时刻分段推进，先处理会话终止边界，再处理后续状态，不能先结算越过散场时刻的收益。
- 队列暂停不能阻挡参与会话到期清理；服务重启结束全部活跃参与会话，成员装载或周期对账负责收尾残留绑定。

### 21.13.3 收益策略

- 讨伐结算读取参与者集合和会话种子，不读取 Party/Team/Guild 身份。
- 当前默认策略保持既有组队语义：经验按参与人数平分并叠加个人等级惩罚；掉率按全员增幅放大，掉落按参与者权重归属；每名玩家只入账自己的份额。
- 收益策略与参与会话分离。团队/宗门若需要不同分配方式，新增策略或组织侧结算适配，不复制讨伐执行器。
- 持续消耗品、即时消耗品和资源费用必须由参与策略明确声明；不能因为来源是 Party 而在行动执行层散落特殊分支。

### 21.13.4 表现与协议

- 战斗协议只下发通用 `participation` 和 `expedition.allies`，盟友阵列按参与者固定顺序生成；不下发或解析 `partySession`。
- 队伍面板仍通过社交状态读取队伍和队伍会话；战斗面板只读取行动参与状态。未来团队/宗门无需修改 `CombatArena`。
- 行动名称、阶段、盟友阵列、战报和动画继续使用原讨伐行动表现；组织类型不进入表现分支。

### 21.13.5 实现契约

- 通用参与模型位于 `Domain/Player/ActionParticipation.cs`：`ActionParticipantSnapshot`、`ActionParticipationSpec`、`ActionParticipationBinding`。
- `QueuedAction`、ECS 行动上下文和 `QueuedActionState` 只携带通用参与绑定；存档不再携带 `PartySession` 字段。
- 社交层负责把队伍条件适配为参与规格；讨伐执行、协议映射和前端战斗展示只依赖通用参与模型。
- 当前本地开发阶段允许一次性废弃旧 `party.expedition` 伪行动和旧字段，不保留兼容别名、双读双写或 fallback。

### 21.13.6 宗门累计任务边界

- 宗门累计采集/击杀/贡献任务不是一次多人同场行动，不创建多人盟友阵列；它订阅成员行动结果并维护独立贡献聚合。
- 宗门共同讨伐才创建同一类 `ActionParticipationSpec`，复用本节讨伐执行器。

### 21.13.7 现阶段固定口径

- 当前参与会话仍采用冻结面板和持续消耗品冻结输入，以保证各成员独立推演逐位一致；即时消耗品暂不在参与会话中自动触发。
- 经验、掉落、等级惩罚和成员容量沿用现有队伍规则，但实现必须挂在参与上下文或策略上，不得回挂组织类型。
- 旧本地存档与旧协议字段一次性废弃；schema v21 只负责新参与绑定载荷的版本标签，不实现历史兼容路径。
