# 第二十四篇 系统商店与每日限购

> 状态：随 TASK-20261020-05 落地。本文档为《道化太初》系统商店（NPC 直售）与每日限购规则的唯一权威设计真源。
> 前端页面：`frontend/src/components/ShopPage.tsx`，位于主界面顶级页签「万象图鉴」之后；服务端入口为命令 `shop.buy` 与只读接口 `GET /api/v1/players/{playerId}/shop`。

---

## 24.1 定位与边界

1. **系统商店 ≠ 坊市**：坊市（`market`）是玩家之间的挂单撮合与自由定价交易行；商店是系统以固定官价直售物资的货架，**不参与撮合、不产生玩家间流水**，功德与货物均由系统侧吞吐。
2. **唯一权威在服务端**：商品目录来自服务端配表（`config/game-data/shop/offers.json`），价格、限购额度与库存规则由服务端裁决；客户端只做展示与意图提交，不得自行扣减或加发任何资产。
3. **与系统回收对称**：回收口径见第四篇 §4.6（`item.sell` 按 `sellPrice` 折价回收）；本篇为买入方向，二者共同构成灵石的单向阀门。

---

## 24.2 商品目录与定价

### 24.2.1 配表结构

商品条目落在 `config/game-data/shop/offers.json`，根节点为数组，每条：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 商品标识，必须以 `shop.` 前缀开头，全局唯一 |
| `itemId` | string | 是 | 发放的物品 ID，必须存在于物品配表 |
| `unitPrice` | number | 是 | 单价（功德），正整数 |
| `dailyLimit` | number | 否 | 每日限购数量，正整数；缺省或 `null` 表示不限购 |
| `sortOrder` | number | 否 | 货架排序权重，升序；缺省按配表读取顺序 |

配表在 `GameDataCatalog.Parse` 中按 `shop.` 前缀归集为 `ShopOffers`，加载期即校验：`id` 前缀与唯一性、`itemId` 存在、`unitPrice` 为正整数、`dailyLimit` 为正整数（若给出）。任何一条不合法都令服务端启动失败，不允许带病上架。

### 24.2.2 首批商品（内测期）

| 商品 ID | 物品 | 单价 | 限购 |
| --- | --- | --- | --- |
| `shop.awakening-stone.daily` | 觉醒石（`item.awakening-stone`） | 100 功德 | 每日 1 个 |
| `shop.awakening-stone.open` | 觉醒石（`item.awakening-stone`） | 1,000 功德 | 不限购 |

两档同物不同价：限购档是每日一次的折扣配额，不限购档是常驻原价供给。

## 24.3 每日限购规则

1. **自然日口径**：与行动统计每日账本完全一致，采用 **UTC+8 自然日**：
   $\text{DayIndex} = \left\lfloor \dfrac{\text{unixSeconds} + 28800}{86400} \right\rfloor$。
   同一 `DayIndex` 内累计购买量不得超过 `dailyLimit`，跨日自动归零（无需定时任务，读路径按当日行查询）。
2. **累计口径**：限购按**件数**累计，不按交易笔数。一次购买 `quantity` 件即占用 `quantity` 个配额；限购商品只允许单次购买 1 件（`quantity` 必须为 1）。
3. **不限购商品不写限购行**：没有 `dailyLimit` 的商品不占用任何配额，也不产生限购流水行。
4. **原子裁决**：配额认领与资产增减在**同一个 Serializable 事务**内完成（见 24.4），不存在「先扣配额后扣款失败」或「先发货后配额超卖」的中间态。

---

## 24.4 结算与一致性

一次 `shop.buy` 在经济事务中写入三类事实：

1. **余额行**：扣减功德资产 `unitPrice × quantity`；同时支持绑定功德（`item.gongde-bound`）与流通功德（`item.gongde`），优先扣除绑定功德，不足部分扣除流通功德；`itemId` 增加 `quantity`。扣减与增发在 `economy.player_asset_balances` 内按固定行序 upsert，功德余额不足由既有守卫拒绝。
2. **流水行**：`economy.transactions.transaction_type = "shop.buy"`，分录包含上述两条资产变动，载荷记录 `offerId / itemId / unitPrice / quantity`，供审计与对账。
3. **限购认领行**：`economy.shop_daily_purchases(player_id, offer_id, day_index)` 累加 `quantity`；带 `WHERE quantity + Δ <= dailyLimit` 守卫的条件 upsert。守卫拒绝（返回零行）即判定超出限购，事务整体回滚，资产与流水一律不落库，命令返回 `SHOP_LIMIT_REACHED`。

**幂等**：命令请求 ID 作为幂等键（`shop.buy:{playerId}:{requestId}`），重放命中历史事务时直接返回原结果，不重复扣配额、不重复发物。限购认领参数纳入请求指纹，同一幂等键换商品或数量会被判定为幂等冲突。

## 24.5 协议

### 24.5.1 只读货架状态

`GET /api/v1/players/{playerId}/shop`（需会话 Cookie，且只能读本人）：

```json
{
  "dayIndex": 20455,
  "offers": [
    { "offerId": "shop.awakening-stone.daily", "itemId": "item.awakening-stone", "unitPrice": 100, "dailyLimit": 1, "purchasedToday": 1 },
    { "offerId": "shop.awakening-stone.open", "itemId": "item.awakening-stone", "unitPrice": 1000, "dailyLimit": null, "purchasedToday": 3 }
  ]
}
```

`purchasedToday` 为该玩家当日已占用配额；不限购商品按实际成交件数返回，仅作展示参考。

### 24.5.2 购买命令

WebSocket / HTTP 通用命令信封，`command = "shop.buy"`，`payload = { "offerId": "shop.awakening-stone.open", "quantity": 3 }`。

| 结果码 | 触发条件 | 用户提示 |
| --- | --- | --- |
| `INVALID_PAYLOAD` | 商品缺失、数量非正整数、超出单次上限（999） | 商品或数量无效。 |
| `SHOP_OFFER_NOT_FOUND` | `offerId` 不在配表中 | 商品不存在或已下架。 |
| `SHOP_LIMIT_REACHED` | 限购商品当日配额已用尽 / 限购商品一次买多件 | 该商品今日限购已达上限。 |
| `INSUFFICIENT_RESOURCE` | 灵石余额不足以支付总价 | 灵石不足。 |
| `SHOP_UNAVAILABLE` | 玩家运行时未装载商店目录 | 商店暂未开放。 |

成功回执：`Succeeded=true`、`Code="OK"`，气泡文案「购得 X 件…」；钱包增量随快照增量推送，前端无需手动刷新余额。

## 24.6 前端规范

1. **入口**：左侧主导航栏「商店」（标识 `shop`，图标为货担/钱袋），位于「坊市」之后；移动端底部页签同步提供入口。
2. **货架卡片**：每件商品一张卡，复用 `ItemTile` + `ItemTooltipTarget` 展示物品瓦片与悬浮详情；卡面只呈现「物名 + 单价 + 限购徽记 + 购买操作」，不重复堆砌配表长描述。
3. **限购徽记**：限购商品显示「每日限购 1 · 今日已购 1/1」，配额用尽时按钮置灰并保持可见（禁止隐藏，避免玩家误以为商品下架）；不限购商品显示「不限购」。
4. **数量选择**：不限购商品提供 `QuantitySelector`（上限 = 余额可买量，硬上限 999）；限购商品固定 1 件，不提供数量控件。
5. **余额反馈**：卡面展示当前灵石余额与本次应付总价；余额不足时按钮置灰并提示「灵石不足」。
6. **状态刷新**：进入页面拉取一次货架状态；购买成功后重新拉取（限购计数以服务端为准，禁止本地自增）。

## 24.7 持久化与迁移

- 新增表 `economy.shop_daily_purchases`：

```sql
CREATE TABLE economy.shop_daily_purchases (
    player_id uuid NOT NULL,
    offer_id varchar(64) NOT NULL,
    day_index bigint NOT NULL,
    quantity integer NOT NULL CHECK (quantity >= 0),
    updated_at timestamptz NOT NULL,
    PRIMARY KEY (player_id, offer_id, day_index)
);
```

- `PostgresSchema.Version` 推进至 **38**，对应迁移 `migrations/0038_v37_to_v38.sql`（纯表结构新增，玩家分段与存档标签不变，仍为 v36）。
- 本表只增不改：跨日旧行保留作对账底账，由既有保留策略窗口统一回收；不在读路径做删除。
