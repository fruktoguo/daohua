# 第十五篇 服务端领域数据架构与聚合运行时规约

## 15.1 四层数据架构体系
```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. 策划静态配置 (GameData 解析) │ 只读不可变、编译期内嵌启动加载、ReadOnlyDictionary │
├────────────────────────────────────────────────────────────────────────┤
│ 2. 运行时玩家聚合 (PlayerAggregate) │ PlayerSectionKind 八分段、ECS 分片单写者   │
├────────────────────────────────────────────────────────────────────────┤
│ 3. 纯业务逻辑系统 (SimulationEngine) │ 纯函数离散事件模拟推进、100% 确定性      │
├────────────────────────────────────────────────────────────────────────┤
│ 4. 持久化与快照 (Snapshots/DTO)   │ 异步落盘、冷计算传输、不可变流式投影     │
└────────────────────────────────────────────────────────────────────────┘
```

## 15.2 纯函数离散模拟引擎与单写者架构
- **单一真源推进**：所有挂机时间、产物结算与战斗模拟严格以 `SimulationEngine.AdvanceTo(state, now)` 为唯一真源，杜绝任何第二套执行器或过渡调度系统。
- **领域聚合零损耗**：玩家状态收敛为单体聚合 `PlayerAggregate`，按 `PlayerSectionKind` 划分为 8 大分段（`progression` / `world` / `combat` / `buffs` / `loadout` / `settings` / `action_queue` / `duel`），高频 Tick 直接访问聚合内存字段，零反射、零哈希查找。
- **ECS 分片单写者并发**：生产运行时为优化版 YuoCore ECS——`EcsGameRuntime` 按 `PlayerId` 哈希把玩家固定路由到 `EcsWorldShard`（`YuoWorld`+`YuoFiber`），同一玩家的命令与模拟推进在该分片 Fiber 内串行执行；适配层 `EcsPlayerRuntimeAdapter` 另持玩家级 `SemaphoreSlim` gate 作为跨边界串行保证。玩家聚合不再常驻：`MutatePlayer`/`RemoveAction` 等命令在锁内把实体组件状态还原为 `PlayerAggregate`、执行领域操作、整体回写组件并合并脏分段差集；跨边界访问仍不得直接持有聚合或 `YuoEntity` 引用。

## 15.3 实验性三版本运行时对比边界（TASK-20260924-09）

本节实验用于区分业务 ECS 迁移收益与 YuoCore 内核优化收益。**实验已收敛：优化版 ECS 现为生产权威运行时**——`src/Server`（生产入口）直接装配优化内核宿主（链接 `src/ServerEcs/Program.cs`+`EcsPlayerRuntimeAdapter`，`YUOCORE_OPTIMIZED`+`YuoCoreRoot=vendor/YuoCore-optimized`）；OOP `PlayerRuntime`/`PlayerActor` 已随迁移删除。ECS-current 基线腿保留在 `src/ServerEcs`（`ecs-current` 变体、`vendor/YuoCore`），仅作对照/差分基准：

| 版本 | 进程/入口 | 运行时内核 | 数据库 | 目的 |
| --- | --- | --- | --- | --- |
| A · OOP | 已退役 | — | — | 历史基准 |
| B · ECS-current | `src/ServerEcs`（基线变体） | 当前 `vendor/YuoCore` 的 `YuoWorld`/`YuoEntity`/`YuoSystem`/`YuoFiber` | `daohua_bench_ecs_current` | 内核差分与性能对照锚点 |
| C · ECS-optimized | `src/Server`（生产） | `vendor/YuoCore-optimized` 的同一组公开 ECS/Fiber API | `daohua_bench_ecs_optimized` | 生产运行时 |

三种服务必须分别构建、分别启动、分别采样，使用同一份游戏数据指纹、角色种子、行动开始时间、随机种子和协议入口。每个服务的工作目录、日志、GC/RSS 统计与数据库隔离；构建产物分别落在 `artifacts/runtime/oop`、`artifacts/runtime/ecs-current`、`artifacts/runtime/ecs-optimized`。由于两个 YuoCore 的程序集名称与命名空间相同，禁止在同一进程装载基线与优化版本。

ECS 游戏核心只实现一套，初始 B/C 对照仅替换 YuoCore 内核。玩家、怪物、遭遇和地图节点分别是长期可查询的实体；玩家采用粗粒度业务组件（身份、成长、世界、战斗、装配、Buff、行动队列、背包、经济），怪物和地图节点按同一套组件/系统边界组织。行动时钟、行动队列、采集、制造、战斗、奖励与快照系统必须保持离散事件边界、随机数顺序、`RemainingRepeats == -1` 无限循环语义和持久化快照语义与现行 OOP 逐位一致。

TASK-20260927-04 的 300 人离线上线性能收敛实验在 C 中增加宿主/游戏 ECS 优化编译路径：移除跨玩家全局加载门、缓存请求内组件引用，并合并单玩家无战斗计时行动的连续自然窗口。源码仍由 B/C 共用，领域原语与终态必须相同，但此后的 C/B 差值包含这些宿主与调度优化，**不能再全部归因于 YuoCore 内核**。报告应同时保存改造前的纯内核对照与改造后的端到端结果。该批量路径仍由当前玩家 Entity、业务组件与 ECS 行动工作区推进；每次请求末经 Fiber Tick 提交。战斗、旅行或队列切换到其它行动时回到完整 System 顺序，必须验证结果与持久化逐位一致。

对比报告必须同时输出墙钟、CPU、分配、GC、RSS、数据库与网络开销的总量及 p50/p95/p99/max，并记录每个版本相对 A/B 的实测倍率。用户不要求优化 ECS 必须胜过 OOP，因此 OOP 回归不设置“必须赢”的硬门槛；但用户给出的优化目标仍须原样展示并实测：优化 ECS 相对 ECS-current 的核心模拟 p95 目标至少降低 20%、每玩家分配目标至少降低 20%、GC 暂停不增加 10% 以上。未达目标必须如实报告，不得调低门槛或伪造达标；是否可替换仍由真实采集、制造、战斗和离线补算结果及“不比当前实现弱太多”的综合判断决定。任何只在极端 ECS 形状基准中变快、而真实玩法明显变慢或结果不一致的实现，不得进入正式服务。

当前状态说明：**优化版 ECS 已是生产核心架构**——`src/Server` 为生产宿主，全部业务命令经 `EcsPlayerRuntimeAdapter`+`EcsWorldShard.MutatePlayer` 通道落到 ECS 实体；`Domain` 保持纯领域（`SimulationEngine`/`PlayerAggregate` 文档往返不变）。命令迁移已完成：行动入队/取消/循环/排序、功法习得、装配替换、境界突破、世界移动、市场与物品操作、建筑贡献、改名、推进与在线状态等 OOP 全量命令面已逐条对齐；回执幂等、钱包事务、脏段差集、属性输入修订（`WireAttributesChanged`）、弃战路由语义保持一致。基线 `src/ServerEcs`（`ecs-current`）与双内核差分台（`tests/EcsDifferential`）保留用于回归对照。

### ECS World/Fiber 分片所有权边界（实验运行时）

实验 ECS 运行时允许按固定数量拆分独立的 `YuoWorld`/`YuoFiber` 分片。每个分片独占自己的 `EcsClockComponent`、玩家/遭遇/怪物实体集合、模拟结果缓冲和 owner gate；同一玩家在运行期间固定由稳定的 `PlayerId` 哈希路由到一个分片，不做在线迁移或动态扩缩容。服务端保留玩家级 gate，分片 gate 只负责保护该分片的 ECS 单写者，因此同一玩家的命令、推进、恢复和销毁仍按原顺序串行执行。

`shardCount` 默认值必须为 `1`，保证现有公开 `World`/`Fiber` 访问和单分片测试语义不变；基准实验可显式使用 `4`（后续再评估 `8`）。多分片只改变所有权和调度，不改变领域公式、自然边界、随机数顺序、快照、持久化、协议和数据库提交顺序。地图节点是各分片的只读长期投影，玩家、怪物和遭遇实体不得跨分片持有 `YuoEntity` 引用。

分片初始化必须顺序执行；只有默认分片可设置 `YuoWorld.Instance`，业务系统不得依赖静态 `YuoWorld.Main/Instance`。`YuoWorld.CloseSystemTry` 是进程级状态，运行时销毁不能在仍有其他分片或运行时存活时恢复该值。停止流程先拒绝新请求并等待分片 gate/mailbox 清空，再逐分片释放 Fiber/World。分片数量增加会重复程序集扫描、系统实例和基础实体，必须单独记录启动耗时、RSS、GC 和实体生命周期指标。

本阶段不实现跨玩家实时批量 Tick。跨玩家批量 Tick 仍需解决不同目标时间、`ActivePlayerId` 单值时钟、按玩家回滚和取消回执等语义问题；任何批量实现必须先证明与逐玩家回放逐位一致。TASK-20260927-04 只合并单玩家请求内部的无战斗自然窗口，不合并多个玩家的命令。

### 15.3.1 计时行动共享原语边界

采集与制造共用 `IPlayerActionContext` / `IPlayerActionState` 纯领域视图。视图直接引用状态所有者的粗粒度分段；队列操作、账本和脏标通过实际单写者回调完成，不创建第二份权威玩家。`TimedActionDuration`、`PrepareTimedAction`、`AdvanceTimedAction`、`CompleteTimedAction` 保留现行 OOP 的建筑倍率、整秒进位、收益、材料扣除、持续用品和无限循环结算顺序。ECS 时钟与队列负责边界选择和准入，采集/制造系统推进单轮，收益/完成系统提交本轮变化；资源自然窗口负责 Buff、回复、用品冷却、资产与版本提交。不得逐边界导出/重建整个 `PlayerAggregate`，不得把整段 `AdvanceWithResources` 改名包装为 ECS 阶段。早期 `ActionAdvanceSession` 已随原语接线删除，不保留兼容入口。

### 15.3.2 资源窗口、战斗实体与真实宿主验收（2026-09-25 04:05:43）

`EcsActionPipeline`只保存请求/资源边界、直接组件视图和窗口流水，不持有`PlayerAggregate`。Clock开启5秒回复/Buff到期/自动用品冷却自然窗口；Queue准备当前轮；采集/制造/移动系统分别推进自己的自然边界；`CombatEventAdvanceSystem`对实际Encounter与Combatant引用执行`AdvanceOneBoundary`；窗口末或终局由共享战斗原语结算技能、持续用品、死亡、掉落与远征轮转，再执行资源回复和Core版本，最后请求合并资产与版本。其它玩家的tick不能切碎当前玩家原本的浮点预算。零时间准备不得重复消耗物品、随机数、年龄或版本。

**亚 tick 残差不变量（2026-09-28 修复）**：`DateTimeOffset` 以 100ns tick 量化，double 精度的窗口剩余预算可能残留 <1 tick 的量；该残差经 `AddSeconds` 取整会让下一自然边界落回同一时刻，形成"边界==游标"的死循环不动点。规约：行动推进步长以 `min(remaining, needed)` 直接消费（`frameTarget >= NextBoundaryAt` 已蕴含可达性，不得再用量化差值二次限幅）；`CompleteClock` 在 `frameTarget >= windowEnd` 时对 ≤1μs 残差直接归零。

战斗`double`目标由窗口原始余量计算；UTC时钟仅决定系统调度先后，禁止将100ns量化后的差值反复回减成战斗预算。请求结束按现行OOP次序导出完整战斗快照，保留资源镜像和战斗单位内部值的原有区别。载入后恢复一次战斗单位，运行中原地续用；当前/optimized两版复用完全相同的ECS源文件。

宿主日志必须从已提交模拟事件经共享Mapper生成，写入每玩家有界日志buffer并驱动真实WS日志批次及快照增量；资产/状态事务失败时不得发送成功日志。基准持续模式以真实墙钟duration运行、常驻WS连接并发有界，报告实际连接/命令数、总耗时与人均耗时；离线`target-hours`只是模拟跨度，不能冒充在线15/60分钟负载。角色种子按三场景各1000生成，战斗保持持续重复。当前本机默认端口存在既有服务时，基准使用显式空闲端口覆盖，不停止用户既有进程。


### 15.3.3 基准控制面与观测口径（2026-09-25 14:03:00）

基准宿主仅允许 `Development`、API 角色、明确的 `DAOHUA_BENCH_MODE=replay|online` 与三种 variant，并核对本机 PostgreSQL 的三张实验库白名单。`replay` 必须提供固定业务时钟，禁用在线模拟、周期玩家刷盘和冷挂机派发；测量结束显式 flush。`online` 禁止固定时钟，保留在线模拟及持久化后台，按实际墙钟 duration、常驻真实 WebSocket 和显式 concurrency/interval 运行；冷挂机派发在两种基准模式均关闭，避免未加载种子被外部工作者抢先补算。租约和认证过期始终使用系统时钟。

本机 `POST /api/debug/bench/session` 仅为已种入实验库的玩家签发真实 PostgreSQL session 与正式 Cookie，用于绕开批量实验账号的登录准备开销；该端点不修改正式登录限流，不映射到生产环境，也不接受代理来源或浏览器 Origin。其余时钟、flush、metrics 控制面仍要求正式 session。端点映射由 OOP/ECS 共用同一实现，避免验证口径漂移。

观测使用纯 .NET Meter，领域不引用 Server。默认宿主不监听；基准在数据库 bootstrap 与运行时实例化之前监听，三版本必须使用相同 `DAOHUA_BENCH_OBSERVABILITY` 开关。`core.simulation` 样本是一名玩家一次真实推进，不含 Actor/Fiber 等锁等待与数据库；ECS 批量调用另标 `batch`，不得混进逐玩家 p95。共享行动、资源与战斗原语按真实调用阶段计时；ECS 系统 tick、实体创建/销毁及快照导出独立计时。阶段是嵌套观测，不能相加冒充总墙钟。

#### 逐阶段计时契约（2026-09-26）

本实验同时保留请求 RTT、进程窗口指标和服务端阶段直方图。阶段名必须是有限、稳定的代码常量，标签仅允许 `stage` 与 `scenario`（`gathering`、`crafting`、`combat`、`other`、`idle`、`all`）；不得加入玩家、实体、节点、配方或 System 实例 ID。`scenario` 取一次玩家推进开始时的队首行动，之后队列轮转不改写本次请求归属；无可确定的请求归属才用 `all`。在线和 replay 必须按相同埋点与窗口差分方法导出。

| 共享阶段名 | 唯一实测边界 | OOP 与 ECS 对比口径 |
| --- | --- | --- |
| `domain.resource.prepare` | `PrepareResourceBoundaryCore` | 每次自然资源窗口规划，包含 Buff 到期与即时用品检查 |
| `domain.resource.regen` | `CompleteResourceRegeneration` | 仅回复结算；OOP 与 ECS 外层资源收尾结构不同，不将整个 ECS `CompleteResourceBoundary` 假称同一阶段 |
| `domain.action.start` | `TryStartActionCore` | 行动地点、状态、材料等开轮准入 |
| `domain.action.prepare` | `PrepareTimedActionCore` | 持续用品与倍率准备，不与开轮准入混合 |
| `domain.action.advance` | `AdvanceTimedAction` | 计时片段进度与连续收益 |
| `domain.action.yield` | `CompleteRepeat` | 单轮到期的材料、产物、资产、统计与队列结算 |
| `domain.combat.prepare` | `AdvanceCombatPreparationCore` | 搜寻、复活与入场准备；仅在走到此边界时记录 |
| `domain.combat.event` | `DeterministicCombatEngine` 中 OOP `AdvanceTo` 与 ECS `AdvanceOneBoundary` 共用的私有单边界执行函数 | 同一战斗随机原子事件；仅包公开入口会漏掉另一实现 |
| `domain.combat.yield` | `CompleteCombatAdvanceCore` | 战斗片段收尾与终局结算 |
| `domain.combat.reward` | `ApplyCombatRewards` | 实际发生的怪物奖励与掉落；无击杀时可无样本 |

共享阶段必须埋在以上同一领域方法内部，不能在 OOP/ECS 外层各自复制一份名称相同但范围不同的计时。采集与制造沿用 `gathering`/`crafting` 场景标签，战斗用 `combat`；共享方法若在非目标玩法也执行，其样本仍按本次推进场景记录。对这些阶段的倍率，仅在三版相同初态、游戏数据指纹、目标时钟、成功命令和结果一致的 replay 窗口中计算。

OOP 实现专属阶段以 `oop.logic.*` 命名：`oop.logic.resource_window` 是 `AdvanceWithResources` 中一次自然窗口从准备到回复的完整控制段，`oop.logic.action_dispatch` 是其一次 `AdvanceToCore` 调用，`oop.logic.combat_dispatch` 是 `AdvanceCombatAction` 调用。它们显示 OOP 自身的循环与分派开销，内部会包含上述 `domain.*` 样本；不能与 ECS 同名 System 的总量直接相除称为算法倍率。`core.simulation` 仍是一名玩家的一次请求级模拟外层，作为两种实现共同的顶层样本。

ECS 对每个实际游戏 `YuoSystem.Run` 的**活动玩家/遭遇业务调用**记录 `ecs.system.run.<SystemClass>`。先通过 `ActivePlayerId`/准备态门控，再开始计时；非活动实体的空返回不逐次写 Meter，以免全实体遍历在千人负载下制造海量观测样本并扭曲性能。覆盖 `ActionClockSystem`、`ActionQueueSystem`、`GatheringActionSystem`、`CraftingActionSystem`、`ActionBoundarySystem`、`TravelActionSystem`、`TimedActionYieldSystem`、`CombatActionBoundarySystem`、`CombatActionYieldSystem`、`PlayerClockCommitSystem`、`CombatEventAdvanceSystem`、`CombatTargetSystem` 和 `CombatEventSystem`。按类名聚合活动调用，不记录实体 ID；即使活动实体在业务条件判断后不推进，也记录一次调度成本。`ecs.system_tick` 保留每次 Fiber/World Tick 的完整调度、查询、遍历和系统调用开销，包含非活动实体的门控成本。`ecs.system.run.*` 不包含 YuoCore 在调用 `Run` 前的查询/迭代及非活动实体的门控成本；不能把 `ecs.system_tick - Σ ecs.system.run.*` 直接归因于扫描，因为嵌套、非业务 System、异步调度与观测本身也在其中。

ECS 所有权另列 `queue.owner_wait`（进入分片 gate 前）、`ecs.owner_hold`（取得 gate 到释放，含备份、模拟、失败恢复）和 `ecs.mailbox.post`（每次宿主向 Fiber 提交消息并等待完成）。`ecs.system_tick` 已覆盖 `TickAsync`，不再为同一调用重复命名 `ecs.fiber.tick`。这几个阶段彼此嵌套或相邻，owner 等待的并发累计值不能并入请求墙钟。混合场景中，资源阶段与 System 阶段均归属正在推进的目标玩家请求；当一次 Tick 实际处理多个玩家时标为 `batch`，不把批次样本分摊到单人场景。若无法确定目标玩家，统一标 `all` 并在报告说明，禁止根据被遍历的非活动实体行动类型改写归属。

#### YuoCore 内核深度埋点（2026-09-27）

阶段长表另导出 `mean_ms=total_ms/count`。两套 ECS 具有相同真实调用边界且次数一致的 `ecs.core.*` 阶段可计算 C/B 倍率；OOP 列保持缺失。优化版专属的稀疏存储内部阶段只展示绝对值。

当前和优化两套 YuoCore 使用相同的 `YuoCoreTrace` 委托出口，由 ECS 宿主接入现有 Meter；只在 Meter 已启用时注册，故基准监听器必须先于 World 构造。每个存活 World 分片持有一份 hook 租约，最后一个分片释放时撤销。内核阶段统一以 `yuocore.*` 命名，报告归一化展示为 `ecs.core.*`。采样覆盖 Fiber 邮箱投递、排空和 Tick，World 更新、系统分派与生命周期，System 按类的 Run、实体扫描、条件检查与实体执行，以及 Entity 组件访问和增删。计数器单列 `*.count` 或命中、跳过等事件，不把事件次数误作计时样本数。优化版还记录稀疏组件存储、稠密实体集合和批处理独有的内部步骤；这些阶段没有当前版的同名方法时仅展示单版结果，不计算伪倍率。相同名字只有在真实调用边界相同且调用次数可比时才允许横向计算耗时倍率。

内核阶段与 `ecs.system_tick`、`ecs.system.run.*` 互相嵌套。前者测量 YuoCore 框架调度和组件热路径，后者测量游戏系统活动调用；总量不可相加，不能以两者的差值直接声称扫描或排队的独占耗时。所有阶段按测量窗口导出调用次数、累计毫秒、单次均值和 p50/p95/p99/max；另导出事件计数 CSV。`--target-hours 1` 是业务模拟跨度，真实墙钟耗时必须单独记录。深度观测对热路径有扰动，性能结论需同负载开关观测对照，并以业务终态一致性和三版服务的独立进程、数据库、构建产物为前提。

基准客户端先发送离线命令，关闭 WebSocket 并等待服务端会话和玩家卸载完成，再调用 `POST /api/debug/bench/flush`。该端点先请求仍已加载的玩家把脏 section 入 durable queue，再在同一请求内主动认领并应用队列，直到本轮没有可处理行后才返回；基准专用认领忽略 `next_attempt_at` 的模拟时间，但仍遵守已有租约。这样连接卸载追加的 Progression 写入也会落盘，`player_state_sections`、`player_state_heads`、动作队列和流水才可跨库比较；正常后台 `SectionFlushWorker` 仍按原定到期与退避规则刷盘。`flush` 的主动应用耗时单独计入基准的 `flush_wall_ms`，不能混入玩家模拟阶段。

回放测量窗口结束后，Bench 客户端先通过每条真实 WebSocket 发送同一确定性的 `player.presence=offline` 命令，关闭连接并等待服务端卸载，再调用同步 `flush`。该收尾命令不计入玩家推进 RTT，但纳入终态持久化窗口，保证 OOP 与两套 ECS 不因连接关闭时序不同而留下不同的在线状态。

共享领域方法不能从其调用时的当前队首反推场景，否则行动轮转会把同一请求拆到多个标签。基准启用时，OOP 在已确定的玩家推进外层建立请求场景作用域；ECS 在 Fiber 内执行活动 `Run` 前显式建立同一请求场景作用域，并在离开后还原。领域 `Measure` 从作用域读取标签；没有作用域时使用 `all`。`batch` 作用域只覆盖真正的多玩家 Tick。作用域仅传播观测标签，不改变领域输入、时钟、队列或随机序列；不要假定跨 Fiber 消息自动继承调用方的异步上下文。

每个 `variant × scenario × stage` 导出独立的 `count`、`total_ms`、`p50_ms`、`p95_ms`、`p99_ms`、`max_ms`，报告 JSON 保留 `server_measurements` 明细，并增附 `<report>.stages.csv` 长表（每行一个阶段，保留 `variant`、`scenario`、`stage`、`layer`、`count`、上述耗时字段、`status` 和 `percentile_method`）。三版汇总再输出同阶段横向比较：共享 `domain.*` 可计算 B/A、C/A、C/B 的 `total_ms` 与 p95 倍率；实现专属阶段并排展示但不伪称同名等价；每个缺失单元格保留空值及状态。现有总览 CSV 继续保留，但其 p50/p95/p99 明确是成功命令 RTT，不能替代阶段分位。分位只能由测量窗口的直方图桶差分求出；累计百分位和累计最大值均不能相减。窗口内最大值若不能精确恢复，`max_ms` 必须为 `null`；桶上界估计应在方法说明中注明误差。阶段未被调用显示 `not_observed` 且统计字段为 `null`，该版本不适用显示 `not_applicable`，指标窗口或监听缺失显示 `unavailable`；只有实际观测到样本才显示 `measured`。不得以 `0`、客户端 RTT、邻近阶段或另一版本数值补缺。

所有 `total_ms` 均为该阶段样本耗时累计，可能跨并发玩家重叠，不能直接与墙钟相加。父阶段包含子阶段，`domain.*`、`oop.logic.*`、`ecs.system.run.*`、`ecs.system_tick`、数据库时间和网络时间也不能彼此求和；报告并列展示原值、调用次数与分位，避免把重复包含的时间解释为独占耗时。共享领域阶段用于定位相同业务规则的成本，专属阶段用于解释各运行时的调度与扫描差异。

场景按测量开始的队首行动归入 gathering/crafting/combat/other/idle，不保留玩家标识或高基数标签。每个阶段/场景仅保存固定对数桶、样本数、总量与最大值，桶上界误差不超过 2%；窗口 p50/p95/p99 从前后桶差计算，禁止相减累计百分位。核心没有产生样本时显示不可用，不能拿请求 RTT 替代；不存在的 OOP ECS实体阶段也标不可用，不能填伪零。网络计数来自真实 WebSocket 发送完成与接收字节，接收等待含客户端闲置时间且单列。监听聚合自身时间记录为 `instrumentationListenerMs`，它仅是已观测开销下界；完整开销需相同负载开/关观测的独立重复测量。

在线不同调度产生不同结束时钟，其正确性以协议、命令、日志与错误检查为界，不宣称跨库逐字终态一致。固定初态、RNG 与 target 的 deterministic replay 继续承担跨三库严格 parity，离线 1/8/24/48 小时必须分别执行及比较。

#### 优化版活动实体查询边界（2026-09-27）

优化版 YuoCore 在保持公开 `YuoSystem` 完整实体集合语义的前提下，增加本次 Tick 的活动实体查询：`YuoWorld.SetActiveEntities` 为每个 System 按其稳定加入顺序建立稠密候选数组，`m_Run` 只遍历候选数组，`ClearActiveEntities` 后恢复完整集合遍历。输入实体自动去重，仍保留延迟增删、异常隔离和 System 执行顺序；未设置活动集合的批量 `World.Update` 不改变原语义。

DaoHua ECS 玩家级推进在优化版构建中，每次 Fiber Tick 前设置当前玩家实体及其 Encounter 实体，Tick 完成后在 `finally` 清除；采集/制造只命中玩家，战斗同时保留 Encounter 系统的活动实体。ECS-current 构建使用同一宿主适配层的空实现，继续作为全量扫描基线。活动查询只改变框架候选集合，不改变领域时钟、随机数顺序、战斗公式、快照或持久化语义；必须通过三版终态一致性和关闭观测的实测比较后才能评价收益。


固定回放的模拟资产事务统一使用共享封装，领域原始增量和行序、`simulation:{playerId}:{StateVersion}:{To}`幂等键、结果载荷与提交后余额版本保持现行语义。事务ID来源通过宿主可选依赖注入；生产与实时在线模式继续随机UUID，仅已通过开发环境、本机实验库校验的`replay`装配确定性ID，使跨库账本比较不受随机运维标识污染。该设置不改变事务结算规则、数据库幂等判断或历史数据格式。

300 人制造并发上线会使共享资产提交的 PostgreSQL Serializable 事务遭遇 `40001` 序列化冲突。资产仓储只在该事务整体回滚后的瞬态冲突上，以同一事务 ID、幂等键、业务时间和载荷，在新连接事务中有限次数重试；每次重试仍覆盖余额、流水、随附 section 与回执的完整原子提交。业务拒绝、幂等内容冲突、取消和非瞬态数据库错误直接上抛。重试耗时计入真实数据库和登录结算总耗时，不得从三版本性能报告中剔除。


下线刷盘必须沿用状态变更后的最新聚合版本：`SetPresence(Offline)`重置离线报告并标脏Duel/Settings后，宿主逻辑版本不得落后于聚合版本，随后Progression/Duel/Settings以同一新版本入durable队列并更新提交头。latest-only的严格递增写入约束保持不变，禁止用同版本覆盖放宽仓储不变量。非法presence值必须显式拒绝，不能默认为Offline改变玩家状态。
