# 第十五篇 服务端领域数据架构与聚合运行时规约

## 15.1 四层数据架构体系
```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. 策划静态配置 (GameData 解析) │ 只读不可变、编译期内嵌启动加载、ReadOnlyDictionary │
├────────────────────────────────────────────────────────────────────────┤
│ 2. 运行时玩家聚合 (PlayerAggregate) │ PlayerSectionKind 八分段、PlayerActor 单写者 │
├────────────────────────────────────────────────────────────────────────┤
│ 3. 纯业务逻辑系统 (SimulationEngine) │ 纯函数离散事件模拟推进、100% 确定性      │
├────────────────────────────────────────────────────────────────────────┤
│ 4. 持久化与快照 (Snapshots/DTO)   │ 异步落盘、冷计算传输、不可变流式投影     │
└────────────────────────────────────────────────────────────────────────┘
```

## 15.2 纯函数离散模拟引擎与单写者架构
- **单一真源推进**：所有挂机时间、产物结算与战斗模拟严格以 `SimulationEngine.AdvanceTo(state, now)` 为唯一真源，杜绝任何第二套执行器或过渡调度系统。
- **领域聚合零损耗**：玩家状态收敛为单体聚合 `PlayerAggregate`，按 `PlayerSectionKind` 划分为 8 大分段（`progression` / `world` / `combat` / `buffs` / `loadout` / `settings` / `action_queue` / `duel`），高频 Tick 直接访问聚合内存字段，零反射、零哈希查找。
- **Actor 单写者并发**：同一玩家的命令与模拟推进在其专属 `PlayerActor`（由 `PlayerRuntime` 持有）内串行执行，`SemaphoreSlim` 保证单写者语义；跨边界访问不得直接持有聚合引用，杜绝多重分布式大锁。`YuoCore`（Ecs/Persistence/Runtime）基座引用在项目文件中保留待用，当前不构成运行时对象模型；若未来启用 ECS/Fiber，所有权约束另行定义。

## 15.3 实验性三版本运行时对比边界（TASK-20260924-09）

本节定义一个**独立于现行生产服务**的长期实验，用来区分业务 ECS 迁移收益与 YuoCore 内核优化收益。它不改变现行 OOP 服务的权威地位，也不把 OOP `SimulationEngine` 包装成 ECS：

| 版本 | 进程/入口 | 运行时内核 | 数据库 | 目的 |
| --- | --- | --- | --- | --- |
| A · OOP | 独立服务、独立端口 | 当前 `PlayerRuntime` → `PlayerActor` → `PlayerAggregate` → `SimulationEngine` | `daohua_bench_oop` | 行为与性能基准 |
| B · ECS-current | 独立服务、独立端口 | 当前 `vendor/YuoCore` 的 `YuoWorld`/`YuoEntity`/`YuoSystem`/`YuoFiber` | `daohua_bench_ecs_current` | 测量只迁移游戏状态组织与调度后的变化 |
| C · ECS-optimized | 独立服务、独立端口 | `vendor/YuoCore-optimized` 的同一组公开 ECS/Fiber API | `daohua_bench_ecs_optimized` | 测量内核存储、查询、生命周期和邮箱优化的增量变化 |

三种服务必须分别构建、分别启动、分别采样，使用同一份游戏数据指纹、角色种子、行动开始时间、随机种子和协议入口。每个服务的工作目录、日志、GC/RSS 统计与数据库隔离；构建产物分别落在 `artifacts/runtime/oop`、`artifacts/runtime/ecs-current`、`artifacts/runtime/ecs-optimized`。由于两个 YuoCore 的程序集名称与命名空间相同，禁止在同一进程装载基线与优化版本。

ECS 游戏核心只实现一套，B/C 仅替换 YuoCore 内核。玩家、怪物、遭遇和地图节点分别是长期可查询的实体；玩家采用粗粒度业务组件（身份、成长、世界、战斗、装配、Buff、行动队列、背包、经济），怪物和地图节点按同一套组件/系统边界组织。行动时钟、行动队列、采集、制造、战斗、奖励与快照系统必须保持离散事件边界、随机数顺序、`RemainingRepeats == -1` 无限循环语义和持久化快照语义与现行 OOP 逐位一致。

对比报告必须同时输出墙钟、CPU、分配、GC、RSS、数据库与网络开销的总量及 p50/p95/p99/max，并记录每个版本相对 A/B 的实测倍率。用户不要求优化 ECS 必须胜过 OOP，因此 OOP 回归不设置“必须赢”的硬门槛；但用户给出的优化目标仍须原样展示并实测：优化 ECS 相对 ECS-current 的核心模拟 p95 目标至少降低 20%、每玩家分配目标至少降低 20%、GC 暂停不增加 10% 以上。未达目标必须如实报告，不得调低门槛或伪造达标；是否可替换仍由真实采集、制造、战斗和离线补算结果及“不比当前实现弱太多”的综合判断决定。任何只在极端 ECS 形状基准中变快、而真实玩法明显变慢或结果不一致的实现，不得进入正式服务。

当前状态说明：本仓库现行 `src/Server`/`src/Domain` 仍是 OOP 聚合运行时。实验ECS核心、独立宿主与基准源码已存在，严格单人/混合玩家/重载/长战斗单测已通过；真实 WebSocket/HTTP/PG 日志与持续负载门禁仍须逐项实测，不能把源码或单测通过等同于生产采用。

### ECS World/Fiber 分片所有权边界（实验运行时）

实验 ECS 运行时允许按固定数量拆分独立的 `YuoWorld`/`YuoFiber` 分片。每个分片独占自己的 `EcsClockComponent`、玩家/遭遇/怪物实体集合、模拟结果缓冲和 owner gate；同一玩家在运行期间固定由稳定的 `PlayerId` 哈希路由到一个分片，不做在线迁移或动态扩缩容。服务端保留玩家级 gate，分片 gate 只负责保护该分片的 ECS 单写者，因此同一玩家的命令、推进、恢复和销毁仍按原顺序串行执行。

`shardCount` 默认值必须为 `1`，保证现有公开 `World`/`Fiber` 访问和单分片测试语义不变；基准实验可显式使用 `4`（后续再评估 `8`）。多分片只改变所有权和调度，不改变领域公式、自然边界、随机数顺序、快照、持久化、协议和数据库提交顺序。地图节点是各分片的只读长期投影，玩家、怪物和遭遇实体不得跨分片持有 `YuoEntity` 引用。

分片初始化必须顺序执行；只有默认分片可设置 `YuoWorld.Instance`，业务系统不得依赖静态 `YuoWorld.Main/Instance`。`YuoWorld.CloseSystemTry` 是进程级状态，运行时销毁不能在仍有其他分片或运行时存活时恢复该值。停止流程先拒绝新请求并等待分片 gate/mailbox 清空，再逐分片释放 Fiber/World。分片数量增加会重复程序集扫描、系统实例和基础实体，必须单独记录启动耗时、RSS、GC 和实体生命周期指标。

本阶段只落地分片路由，不实现实时批量 Tick。批量 Tick 仍需解决不同目标时间、`ActivePlayerId` 单值时钟、按玩家回滚和取消回执等语义问题；任何批量实现必须先证明与逐玩家回放逐位一致。

### 15.3.1 计时行动共享原语边界

采集与制造共用 `IPlayerActionContext` / `IPlayerActionState` 纯领域视图。视图直接引用状态所有者的粗粒度分段；队列操作、账本和脏标通过实际单写者回调完成，不创建第二份权威玩家。`TimedActionDuration`、`PrepareTimedAction`、`AdvanceTimedAction`、`CompleteTimedAction` 保留现行 OOP 的建筑倍率、整秒进位、收益、材料扣除、持续用品和无限循环结算顺序。ECS 时钟与队列负责边界选择和准入，采集/制造系统推进单轮，收益/完成系统提交本轮变化；资源自然窗口负责 Buff、回复、用品冷却、资产与版本提交。不得逐边界导出/重建整个 `PlayerAggregate`，不得把整段 `AdvanceWithResources` 改名包装为 ECS 阶段。早期 `ActionAdvanceSession` 已随原语接线删除，不保留兼容入口。

### 15.3.2 资源窗口、战斗实体与真实宿主验收（2026-09-25 04:05:43）

`EcsActionPipeline`只保存请求/资源边界、直接组件视图和窗口流水，不持有`PlayerAggregate`。Clock开启5秒回复/Buff到期/自动用品冷却自然窗口；Queue准备当前轮；采集/制造/移动系统分别推进自己的自然边界；`CombatEventAdvanceSystem`对实际Encounter与Combatant引用执行`AdvanceOneBoundary`；窗口末或终局由共享战斗原语结算技能、持续用品、死亡、掉落与远征轮转，再执行资源回复和Core版本，最后请求合并资产与版本。其它玩家的tick不能切碎当前玩家原本的浮点预算。零时间准备不得重复消耗物品、随机数、年龄或版本。

战斗`double`目标由窗口原始余量计算；UTC时钟仅决定系统调度先后，禁止将100ns量化后的差值反复回减成战斗预算。请求结束按现行OOP次序导出完整战斗快照，保留资源镜像和战斗单位内部值的原有区别。载入后恢复一次战斗单位，运行中原地续用；当前/optimized两版复用完全相同的ECS源文件。

宿主日志必须从已提交模拟事件经共享Mapper生成，写入每玩家有界日志buffer并驱动真实WS日志批次及快照增量；资产/状态事务失败时不得发送成功日志。基准持续模式以真实墙钟duration运行、常驻WS连接并发有界，报告实际连接/命令数、总耗时与人均耗时；离线`target-hours`只是模拟跨度，不能冒充在线15/60分钟负载。角色种子按三场景各1000生成，战斗保持持续重复。当前本机默认端口存在既有服务时，基准使用显式空闲端口覆盖，不停止用户既有进程。


### 15.3.3 基准控制面与观测口径（2026-09-25 14:03:00）

基准宿主仅允许 `Development`、API 角色、明确的 `DAOHUA_BENCH_MODE=replay|online` 与三种 variant，并核对本机 PostgreSQL 的三张实验库白名单。`replay` 必须提供固定业务时钟，禁用在线模拟、周期玩家刷盘和冷挂机派发；测量结束显式 flush。`online` 禁止固定时钟，保留在线模拟及持久化后台，按实际墙钟 duration、常驻真实 WebSocket 和显式 concurrency/interval 运行；冷挂机派发在两种基准模式均关闭，避免未加载种子被外部工作者抢先补算。租约和认证过期始终使用系统时钟。

本机 `POST /api/debug/bench/session` 仅为已种入实验库的玩家签发真实 PostgreSQL session 与正式 Cookie，用于绕开批量实验账号的登录准备开销；该端点不修改正式登录限流，不映射到生产环境，也不接受代理来源或浏览器 Origin。其余时钟、flush、metrics 控制面仍要求正式 session。端点映射由 OOP/ECS 共用同一实现，避免验证口径漂移。

观测使用纯 .NET Meter，领域不引用 Server。默认宿主不监听；基准在数据库 bootstrap 与运行时实例化之前监听，三版本必须使用相同 `DAOHUA_BENCH_OBSERVABILITY` 开关。`core.simulation` 样本是一名玩家一次真实推进，不含 Actor/Fiber 等锁等待与数据库；ECS 批量调用另标 `batch`，不得混进逐玩家 p95。共享行动、资源与战斗原语按真实调用阶段计时；ECS 系统 tick、实体创建/销毁及快照导出独立计时。阶段是嵌套观测，不能相加冒充总墙钟。

场景按测量开始的队首行动归入 gathering/crafting/combat/other/idle，不保留玩家标识或高基数标签。每个阶段/场景仅保存固定对数桶、样本数、总量与最大值，桶上界误差不超过 2%；窗口 p50/p95/p99 从前后桶差计算，禁止相减累计百分位。核心没有产生样本时显示不可用，不能拿请求 RTT 替代；不存在的 OOP ECS实体阶段也标不可用，不能填伪零。网络计数来自真实 WebSocket 发送完成与接收字节，接收等待含客户端闲置时间且单列。监听聚合自身时间记录为 `instrumentationListenerMs`，它仅是已观测开销下界；完整开销需相同负载开/关观测的独立重复测量。

在线不同调度产生不同结束时钟，其正确性以协议、命令、日志与错误检查为界，不宣称跨库逐字终态一致。固定初态、RNG 与 target 的 deterministic replay 继续承担跨三库严格 parity，离线 1/8/24/48 小时必须分别执行及比较。


固定回放的模拟资产事务统一使用共享封装，领域原始增量和行序、`simulation:{playerId}:{StateVersion}:{To}`幂等键、结果载荷与提交后余额版本保持现行语义。事务ID来源通过宿主可选依赖注入；生产与实时在线模式继续随机UUID，仅已通过开发环境、本机实验库校验的`replay`装配确定性ID，使跨库账本比较不受随机运维标识污染。该设置不改变事务结算规则、数据库幂等判断或历史数据格式。


下线刷盘必须沿用状态变更后的最新聚合版本：`SetPresence(Offline)`重置离线报告并标脏Duel/Settings后，宿主逻辑版本不得落后于聚合版本，随后Progression/Duel/Settings以同一新版本入durable队列并更新提交头。latest-only的严格递增写入约束保持不变，禁止用同版本覆盖放宽仓储不变量。非法presence值必须显式拒绝，不能默认为Offline改变玩家状态。
