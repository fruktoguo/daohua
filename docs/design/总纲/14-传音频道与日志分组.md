# 第十四篇 传音频道与日志分组

> 本文是「游戏内日志分组 + 聊天（传音）系统」的设计真源。协议字段、频道语义、保留策略与前端展示口径以本文为准。

---

## 14.1 面板分组

日志面板共 8 个分组（Tab），顺序固定：

| 分组 | 键 | 数据来源 |
| --- | --- | --- |
| 综合 | `all` | 系统日志 + 好友私聊 + 队伍群聊（三源按时间合并，只读，不提供输入） |
| 世界 | `world` | 世界频道聊天（全服在线修士） |
| 附近 | `nearby` | 附近频道聊天（同一地图节点在线修士） |
| 系统 | `system` | 系统日志（消耗品使用、行动完成、抵达、离线补算、斗法撮合与结算、各类系统通知） |
| 战斗 | `combat` | 战斗过程日志（`combat.*`：搜寻/遭遇/施放/胜负/复活；普通攻击逐帧不落日志，同一次施放的多目标命中合并为一条施放行：模板内以 `\n` 分隔逐目标子句，前端拆行渲染并以隐藏前缀占位使续行「对/为」与首行对齐） |
| 好友 | `friend` | 好友私聊（1:1，需先建立双向好友关系） |
| 宗门 | `sect` | 宗门频道（**当前仅占位**，宗门系统未立项，输入与展示均提示未开放） |
| 队伍 | `party` | 队伍群聊（队伍成员） |

- 综合**不包含**世界、附近、战斗、宗门。
- 系统与战斗由服务端日志事件（`LogBatch`）按 `channel` 字段分流。
- 世界/附近/好友/队伍/宗门为聊天消息（`ChatMessage`）。

## 14.2 日志事件频道字段

`LogEventDto` 新增 `channel`（`"system"` | `"combat"`，缺省 `"system"`）。

分类规则（服务端 `SimulationLogMapper`）：

- 事件码前缀 `combat.` → `combat`；
- 消耗品自动使用与耗尽 `auto-use.*` → 高频自动化推演事件，**不输出至战报日志**（`LogChannels.FromEventCode` 返回 `null`，避免频繁刷屏污染系统日志）；
- 其余关键事件（`action.*`、`world.arrived`、`offline.capped`、`duel.*`、`enhance.*`、`tutorial.*`）→ `system`。

前端 `gameLogService` 按 `channel` 过滤，系统/战斗两个 Tab 各自独立渲染；综合不消费日志（只消费系统频道）。

服务端日志事件码一览（`SimulationEvent.Code` 实际产出全集，`channel` 列即 `LogChannels.FromEventCode` 分流结果）：

| 事件码 | 频道 | 语义 |
| --- | --- | --- |
| `combat.search.started` | `combat` | 讨伐搜寻读条开始（含参与会话跟随搜寻） |
| `combat.started` | `combat` | 遭遇妖兽：波次入场开战 |
| `combat.skill` | `combat` | 技能施放行：同一次施放的多目标命中合并为一条，逐目标子句 `\n` 分隔 |
| `combat.won` | `combat` | 讨伐成功：波次清空 |
| `combat.lost` | `combat` | 阵亡：仅真阵亡（实际击倒计败走与死亡；含队友阵亡通知） |
| `combat.downed` | `combat` | 波次开打时仍倒地/气血衰竭：单人无法迎战（行动阻塞），组队倒地随队迎战（不计阵亡） |
| `combat.respawned` | `combat` | 原地起身：气血回满（含队友起身通知） |
| `duel.charge` | `system` | 心血来潮：斗法遭遇感应 +1 |
| `duel.won` / `duel.lost` / `duel.draw` | `system` | 斗法推演胜/负/平结算 |
| `duel.staged.settled` | `system` | 斗法暂存物品入账 |
| `action.completed` | `system` | 行动完成/单轮结算（结构化模板带行动引用与物品明细） |
| `action.blocked` | `system` | 行动前置条件断绝转阻塞停泊 |
| `action.auto-travel` | `system` | 当前位置无法执行，自动插队前往可执行节点 |
| `action.invalid-dropped` | `system` | 时长配置无效的失效行动自动移出队列 |
| `action.participation.ended` | `system` | 行动参与会话已结束 |
| `auto-use.activated` | `无（不输出）` | 自动消耗品生效（高频推进事件，已由顶栏/侧栏Buff实时展示，不入系统日志防刷屏） |
| `auto-use.depleted` | `无（不输出）` | 持续用品持续时间耗尽（高频推进事件，不入系统日志防刷屏） |
| `auto-use.escrowed` | `无（不输出）` | 组队会话开打托管清单（属于会话内部托管状态，不入系统日志） |
| `enhance.succeeded` / `enhance.failed` | `system` | 强化成功提升 / 失败回落 |
| `world.arrived` | `system` | 抵达目的节点 |
| `offline.capped` | `system` | 离线补算达到 48 小时上限（仅跨越边界的请求发一次） |
| `tutorial.grant` / `tutorial.completed` | `system` | 新手引导赠送入账 / 引导完成终奖（结构化物品明细） |

注：斗法遭遇撮合通知、邀请里程碑入账、引导跳过补发三条为宿主直发 `LogEventDto`（`system`），不走 `SimulationEvent`。

## 14.3 聊天频道模型

聊天频道由「频道类型 + 作用域键」唯一确定：

| 频道 | `channel` | `scopeKey` | 可见范围 |
| --- | --- | --- | --- |
| 世界 | `world` | 空字符串 | 全部在线修士 |
| 附近 | `nearby` | 当前地图节点 ID | 同一节点的在线修士 |
| 好友 | `friend` | 两个玩家 ID 升序拼接 | 私聊双方 |
| 队伍 | `party` | 队伍 ID | 队伍全体成员 |
| 宗门 | `sect` | 宗门 ID | 未开放（占位） |

- 消息体长度上限 200 字符（去除首尾空白后非空）。
- 频道级发送节流：同一玩家同一频道 1 秒内最多 3 条，超出返回 `CHAT_RATE_LIMITED`。
- **不设计历史兼容**：聊天记录只保留最近 100 条/频道作用域，超出即删除。

---

## 14.4 保留策略（100 条/作用域）

聊天消息落 PostgreSQL `social.chat_messages`：

- 每条消息插入后，在同一事务内删除该 `(channel, scope_key)` 下超出最新 100 条之外的行；
- 历史回放：玩家握手成功、以及切入某频道时，服务端下发该作用域最近 100 条（`ChatHistory`）；
- 世界频道为单作用域（`scope_key = ''`），全局共享 100 条。

## 14.5 社交系统（好友 / 队伍）

### 14.5.1 好友

- 双向关系：申请（`friend.request`）→ 接受（`friend.accept`）/ 拒绝（`friend.reject`）→ 双向 `friendships` 落库；
- 解除（`friend.remove`）双向删除；
- 好友私聊：以双方 ID 升序拼接为 `scopeKey`，只有双方可收发。

### 14.5.2 队伍

- 邀请（`party.invite`）：邀请人未组队时**自建队伍并任队长**；被邀请人收到待处理邀请；
- 接受（`party.accept`）/ 拒绝（`party.decline`）：作用于自己待处理的邀请；
- 队伍上限 5 人（含队长）；只有队长可以邀请；
- 成员离开（`party.leave`）：队长离开时队长位移交剩余成员中最早加入者；成员全部离开后队伍解散；
- 队伍群聊作用域为 `party_id`，成员变更即时生效。
- 完整组队系统（队伍档案/招募匹配/组队大厅/聊天队伍链接/身家口径）以 [第二十一篇](./21-同道与组队系统.md) 为准；本篇仅保留队伍频道与邀请通道的基础语义。

### 14.5.3 持久化表（schema v4 新增 `social` schema；队伍档案/散人池/聊天链接字段见第二十一篇 §21.9）

- `social.friend_requests`：好友申请（`pending`/`accepted`/`rejected`/`cancelled`），`(requester_id, target_id)` 的 pending 部分唯一索引防重复申请；
- `social.friendships`：双向好友关系（两行）；
- `social.parties` / `social.party_members`：队伍与成员（`player_id` 作主键，一名玩家最多一队）；schema v7 起 parties 追加 `name`/`activity_kind`/`map_id`/`min_valuation`/`is_public`/`updated_at` 档案列；
- `social.party_invitations`：待处理队伍邀请（`invitee_id` 作主键，每人最多一条）；
- `social.party_seekers`（schema v7）：「匹配中」散人登记（`player_id` 作主键）；
- `social.chat_messages`：聊天消息（含保留清理索引；schema v7 增 `party_ref` 队伍链接外键）。

## 14.6 协议契约

新增 `WireMessageType`：

| 值 | 名称 | 方向 | 载荷 |
| --- | --- | --- | --- |
| 18 | `ChatSend` | C→S | `ChatSendDto` |
| 19 | `ChatMessage` | S→C | `ChatMessageDto` |
| 20 | `ChatHistory` | S→C | `ChatHistoryDto` |
| 21 | `SocialAction` | C→S | `SocialActionDto` |
| 22 | `SocialState` | S→C | `SocialStateDto` |
| 23 | `ChatHistoryRequest` | C→S | `ChatHistoryRequestDto` |
| 24 | `UnitInspect` | C→S | `UnitInspectDto`（火忘帧，无回执） |
| 25 | `PartyLobbyRequest` | C→S | `PartyLobbyRequestDto`（见第二十一篇 §21.6） |
| 26 | `PartyLobby` | S→C | `PartyLobbyDto` |

- `ChatSendDto { requestId, channel, body, targetPlayerId? }`：`targetPlayerId` 仅好友频道使用；正文去首尾空白后 1~200 字符。
- `ChatMessageDto { messageId, channel, scopeKey, senderId, senderName, body, sentAtUnixMilliseconds, partyLink? }`：`partyLink` 为队伍卡片快照（见第二十一篇 §21.8），队伍解散后缺席。
- `ChatHistoryDto { channel, scopeKey, targetPlayerId?, messages[] }`：`targetPlayerId` 仅好友频道回填，供客户端把会话映射到具体好友。
- `ChatHistoryRequestDto { channel, targetPlayerId? }`。
- `SocialActionDto { requestId, action, targetPlayerId?, targetName?, partyId?, channel?, party? }`，`action` ∈ `friend.request|friend.accept|friend.reject|friend.remove|party.invite|party.accept|party.decline|party.leave|party.create|party.update|party.disband|party.kick|party.join|party.match.set|party.match.clear|party.share`（后 8 个动作的字段语义见第二十一篇 §21.7/§21.9）：
  - `friend.request` 可用 `targetPlayerId` 或 `targetName`（道号检索）指定目标；
  - `friend.accept` / `friend.reject` 用 `targetPlayerId` 指向申请人；
  - `party.accept` / `party.decline` 作用于自己待处理的邀请，忽略 `targetPlayerId`；
  - `party.invite` 在自己未组队时**自建队伍并任队长**（邀请是组队的唯一入口）。
- `SocialStateDto { requestId?, friends[], incomingRequests[], outgoingRequests[], party?, partyInvitation?, nearbyPlayers[], seeking? }`：
  - `friends[]`：`FriendDto { playerId, displayName, online }`；
  - `incomingRequests[]` / `outgoingRequests[]`：`FriendRequestDto { requestId, playerId, displayName, createdAtUnixMilliseconds }`；
  - `party?`：`PartyDto { partyId, leaderId, name, activityKind, mapId, minValuation, isPublic, members[] }`，`PartyMemberDto { playerId, displayName, online, valuation }`，队伍上限 5 人；
  - `partyInvitation?`：`PartyInvitationDto { partyId, inviterId, inviterName, partyName }`；
  - `nearbyPlayers[]`：`NearbyPlayerDto { playerId, displayName }`（同节点在线修士，含自己）；
  - `seeking?`：`PartySeekerDto { activityKind, mapId, minValuation, createdAtUnixMilliseconds }`（本人匹配中登记，未登记为 null）。

`requestId` 回传用于指令配对；为 null 表示服务端主动推送（好友上线、队伍变更、附近修士变化）。

## 14.7 服务端组件

- `ChatRuntime`（单例）：频道作用域解析、消息落库与广播、历史回放；
- `SocialRuntime`（单例）：好友与队伍的持久化读写、在线状态、附近修士快照；
- `OnlinePresenceRegistry`：在线会话 → 玩家 ID / 道号 / 当前节点，供世界、附近广播与在线状态判定；
- `WebSocketRuntime`：入站 `ChatSend` / `SocialAction` 分发，出站 `ChatMessage` / `ChatHistory` / `SocialState` 推送；
- 玩家节点变化（`world.travel` 抵达、握手加载快照）触发 `OnlinePresenceRegistry.UpdateNode`，并重算附近修士快照。

聊天与社交**不经过玩家级单写者门禁**：它们不属于玩家聚合状态，由独立单例服务串行化处理，避免跨玩家互相阻塞。
