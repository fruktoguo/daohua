# 性能与分布式改造 · 变更说明

> 这是 TASK-20260924-08 的账本。每一批改动**为什么要改、改了什么、怎么验证的**都写在下面，供你逐条审查。
> 底线只有一条：**游戏内容完全不变**——战斗输赢、掉落多少、市场谁成交、挂机收益，改之前什么样改之后还是什么样。

## 背景

- 主服务器：YuoHira（有公网 IP）。计算节点：odin（没有公网 IP 的设备，以后大部分节点都这样）——所以节点只能**主动连主服**，主服不能反过来找它。
- 当前结构：主服负责玩家连接和存档，计算节点（odin 等）帮忙算"离线挂机补算"这类重活。

## 先说两个重要发现

### 1. 计算节点一直在"假装干活"（严重，已建议止损）

现状的 odin 计算链路其实**没有在算**：主服把玩家存档发给节点，节点只是往存档里盖了个"已结算"的章就发回来，实际的修为/掉落结算根本没跑。后果：**玩家被节点"补算"过的时间段，离线收益被悄悄吞掉了**，而且生产上默认开着。

- 建议：真实补算落地前，在 YuoHira 上把 `COMPUTE_NODE_ENABLED=false` 先关掉止血（任务会排队等着，不会丢）。
- 根治方案已在开发中（见 W3）：让节点真正跑游戏模拟逻辑，并且用"同一输入两端跑、逐字节比对"的测试保证主服和节点算得一模一样。

### 2. 客户端可以"快进时间"刷收益（已修复）

`simulation.advance` 这个指令接受客户端自己填的目标时间，没设上限——理论上可以一次请求秒结最多 48 小时挂机收益。已在 W1-B 修掉：服务端把时间钳到"当前时间"，客户端填未来时间不再生效。

## 改动记录（按时间倒序，最新在前）

### `f0d1ecf` · 经济提交省往返 + 失败回滚只备份脏了的分段（W3-C）

- **问题**：每笔经济事务提交都要多跑一圈数据库——每个资产行先 `SELECT ... FOR UPDATE` 再 `INSERT/UPDATE`（2 趟/行），流水逐行插入（N 趟），提交后还要整包重读钱包余额（1 趟）；同时运行时每个受保护写操作（模拟推进、功法学习等）都把整个玩家聚合完整克隆一份做失败回滚备份，即使这次操作只动了一个分段。
- **改法**：余额变更改为单语句 `INSERT ... SELECT ... ON CONFLICT DO UPDATE ... WHERE 结果域守卫 RETURNING`（1 趟/行，顺带带回提交后余额与版本）；流水行用 `unnest ... WITH ORDINALITY` 一次写入（1 趟）；提交回执携带余额行，`PlayerRuntime` 直接并入内存钱包（`AssetWallet.SyncCommitted`），消掉提交后整包重读。合并后 K 个资产行、N 行流水的提交从 2K+N+2 趟降到 K+2 趟；负余额/非有限结果被 WHERE 守卫拦截后按需 SELECT 取证，照抛 `EconomyInsufficientBalanceException`。Serializable 隔离、幂等键、请求哈希冲突、行锁顺序全部不变；`PostgresMarketRepository` 同款优化一并落地。
- **回滚**：Domain 侧新增 internal 分段/头标量检查点（`Capture/RestoreSectionCheckpoint`、`Capture/RestoreHeadCheckpoint`、`RestoreDirtyTracking`），`PlayerRuntime` 在每个受保护写操作起点按脏流水戳差集只重捕被标脏的分段（推进热段按节拍号强制重捕，头标量每次刷新）；失败时全分段就地写回 + 精确复原脏集合/流水号/脏龄/逻辑版本/钱包，与旧整份克隆回滚逐位等价。`ExportState`/`RestoreFrom` 公共语义不变。
- **验证**：Release 全解 0 警告 0 错误；Domain.Tests 181/181；Server.Tests 151/151（经济集成、回滚逐位一致、checkpoint、compute golden 全绿）。市场租约两个用例在本机开发服进程持有分片租约时无法竞争租约（环境性阻塞，非回归；该进程未运行时通过）。

### `f0d1ecf` · 计算节点真补算落地（compute.v2 + compute-link.v1.2）（W3-A）

- **问题**：计算节点一直在"假装干活"——收到存档不跑模拟，只盖个"已结算"的章就还回来，玩家离线收益被悄悄吞掉（见上文"重要发现 1"）。
- **改法**：节点改为真正跑游戏模拟。存档编码/解码逻辑从服务端搬到领域层（`Domain.Persistence.SectionCodec`，两端共用同一份代码）；任务载荷升级为 compute.v2，把玩家身份、完整存档分段、资产余额、存档指纹一起带过去，节点不需要碰数据库就能原样还原玩家；节点跑完把"变了的分段 + 资产增减"发回，主服在同一个数据库事务里落库（分段写回 + 资产入账 + 任务完结，要么全成要么全不成）；握手协议升到 v1.2，节点会自报运行时指纹，方便排查 arm64/x64 差异。顺手修了一个真 bug：超过 48 小时的空闲补算会给"空技能状态"误标脏，导致每次都多写一段相同内容。
- **一致性保证**：新增 golden vector 测试——同一份存档输入，主服在线路径和节点线协议路径各跑一遍，要求分段原始字节、校验和、提交头校验和、资产增量**逐字节一致**；批量派发与逐任务派发结果一致；空闲/封顶/指纹换绑等边界形态全覆盖。
- **验证**：服务端测试 152/152（含 8 个 golden vector 用例），领域测试 181/181，Release 构建零警告，前端契约检查通过。

### `f0d1ecf` · 战斗中不再每 5 秒拆装一次战场（W3-B）

- **问题**：打怪中的玩家每推进一小步（≤5 秒），都要把整场战斗从存档里拆开（还原每个敌人、Buff、技能冷却）→ 走一步 → 再整个装回去。挂机 48 小时就是几万次重复拆装。
- **改法**：同一场没打完的战斗在相邻两步之间直接复用内存态，只把血条、出手时刻这类会变动的数字写回存档镜像；战斗结束或状态被外部改动时才完整回写。装备/Buff 中途变化时会刷新面板，不会出现"换装备了但战斗里还是旧属性"。
- **验证**：领域测试 180/180；新增 5 个用例专门盯"一口气补算 vs 一秒一秒分段补算结果逐字节一致"（含战斗结束、倒地复活、Buff 到期等边界）。
- **附带**：`StuckCombatReproTests` 的夹具怪物血量从 362 调到 150——因为你手工下调了小怪血量权重（tier1_minions.json），旧夹具血量超过了新上限；只改了测试夹具，没碰配表。

### `561ce55` · 推送瘦身：只发"变了的部分"+ 修复慢客户端漂移（W2-B）

- **问题**：每次给玩家推数据，都把全部 8 个数据段重新打包+加密校验+编码一遍，再用"找不同"决定发哪些——相当于每次都把 8 个箱子全封一遍再拆开看哪个要寄。500 个玩家在线时这是最烧 CPU 的地方。
- **另外修了个隐患**：玩家网慢、推送队列塞不下时，服务端会丢包，但"已发到哪"的账本已经往前记了——客户端会永远缺一段数据直到重连。
- **改法**：记录"本次操作碰了哪几段"，只打包这几段；丢包时账本不往前记，下拍自动补发；一直塞不下的客户端强制断线重连拿全量。顺带把地图信息做成了只算一次的缓存、世界频道广播一条消息只打包一次、登录握手时几件事并行做。
- **验证**：后端测试 136/136，领域测试 172/172，前端构建通过。

### `0ab4777` · 属性计算缓存：不再每 5 秒重算一遍（W2-D）

- **问题**：角色属性面板（攻击/防御/血量上限等）原来每 5 秒就从零重算一遍，哪怕装备、Buff、境界全都没变。挂机 48 小时就是每人算 3 万多次白工。
- **改法**：给每个会影响属性的东西（装备、Buff、境界、建筑加成）记一个"版本号"，东西没变就直接用上次的计算结果；存档导出同理，没变就直接复用上次的文档。**缓存结果和重算结果逐字节一致**是硬性要求，专门加了 11 个测试盯着这条。
- **验证**：领域测试 170/170 全绿。

### `a802096` · 市场不再一次抖动就永久罢工 + 撮合提速（W2-C）

- **问题一**：市场只要撞一次数据库抖动就永久停摆，必须重启进程才恢复。
- **问题二**：每一笔挂单/撤单都会全量扫一遍所有订单找"到期的"，还把整个订单簿复制两遍。
- **改法**：市场加了"自动复职"机制——抖一下没关系，自动重新拿到写权、重建盘口、继续干活（实测约 2 秒自愈）；订单簿加了按价格和到期时间排好序的索引，找候选单/到期单直接取队头不再全扫；每笔操作不再需要整簿复制。用 400 步随机操作做了"新写法 vs 老写法逐笔对照"测试，成交结果完全一致。
- **验证**：服务端测试 125/125，领域测试 170/170。

### `312d11d` · 计算任务派发并行化 + 按大小装箱（compute-link.v1.1）（W2-A）

- **问题一**：派发器是单线程流水线——发一批、等结果、存库、才发下一批。整个节点组同一时刻只有 1 批在跑，节点说自己能同时跑 8 批也没用。
- **问题二**：装批只看任务个数不看大小，超大批次发过去会被节点整批判死，之后又被反复重新派发、再判死，形成死循环。
- **改法**：按每个节点声明的并发能力同时派多批；装批时按实际字节数装箱（默认 8MB 一批），装不下的回队列下轮再派；握手时节点上报"我一批最多接多少任务/多少字节"，主服按此装箱；修掉了节点侧一个把上限算错成四分之一大小的 bug；同时修好了"后台进程空跑派发链+重复扫任务"的角色配置错误。
- **验证**：服务端测试 124/124，含新增 7 个用例。

### `a884b15` · 社交/聊天提速 + 会话认证缓存（W2-E）

- **问题**：一个玩家换地图节点或上下线，相关好友/附近玩家每人都串行跑 6 次数据库查询；聊天每发一条都顺手做一次"只留 100 条"的清理；每个请求都查一次三表联查验证登录。
- **改法**：社交状态 7 条 SQL 合并成一次往返；"谁在哪个节点"建倒排索引（原来每次把全服在线列表扫一遍）；聊天清理改成每写 16 条才清一次；登录验证加 3 秒缓存，登出/改名主动清缓存（踢人立即生效不受影响）。
- **验证**：服务端测试 117/117。

### `bf4e7b4` · 存档写库批量化 + 冷扫描不再白搬数据（W1-C）

- **问题**：计算结果写库时，64 个任务 × 每个约 8 段 = 500 多次一条条发的 SQL；冷挂机扫描先把玩家整个存档读出来、发现不该算再扔掉；任务表里多余存了一份完整结果（数据库里存两遍一样的东西）。
- **改法**：写库改"一批一条 SQL"（数组批量写入）；扫描时先在 SQL 里按时间窗过滤，不再白读全量存档；多余的结果副本只留摘要。
- **验证**：服务端测试 116/116（含新增 4 个用例）。

### `a7b211f` · 服务器主循环减负 + 堵快进漏洞（W1-B）

- **问题**：每个玩家每次推进都往数据库写一次"我还是房主"的续约（500 人≈每秒 500 次无意义写入）；玩家日志缓冲区越堆越多不清；上面说的快进漏洞；每个玩家每拍都要过一把全局锁查节点建筑。
- **改法**：续约改成 15 秒内只写一次；玩家下线即清日志缓冲；快进钳制；节点建筑改成"拍快照"式读取——读不抢锁，只有有人建造/完工才更新快照。
- **验证**：服务端测试 116/116。

### `17f62f4` · 节点链路韧性：迟到结果不再"炸线"（W1-A）

- **问题**：odin 网慢时批次超时，任务退回重发；但节点还在算，算完结果晚到——主服居然把这当"违规"直接断链，把节点其他在算的批次全害死，还触发重连，恶性循环。另外节点断线后还在空算、重连等待时间有 bug 永不重置。
- **改法**：迟到的结果记日志丢弃，不再断链；双方都设了心跳超时（60 秒没回音认定断线）；断线立刻停掉在算的活；重连等待时间修正；握手令牌改成防时序攻击的比较方式；节点调试端口默认只绑本机（odin 已显式配过不受影响）；odin 守护脚本的进程探测修正。
- **验证**：服务端测试 105/105（新增 4 个端到端用例）。

### `6616a3c` · 前端解码与本地存储减负（W1-E）

- **问题**：前端每收到一个数据段就新建解码器+逐字节手动解码；战斗中每次击杀都往浏览器 localStorage 全量重写一遍战报历史（主线程卡顿源）。
- **改法**：解码器共享+走原生 API；战报历史改成内存里先合并、内容没变就跳过、5 秒攒一次写盘、切后台立即写盘。
- **验证**：前端构建通过，契约检查通过。

### `8629e2d` · 挂机模拟省内存 + 每步固定开销削减（W1-D）

- **问题**：48 小时离线补算能产生十几万条日志事件堆在内存里，但下游只看最后 200 条；模拟每走一小步都固定做一堆扫描（Buff 到期、冷却、暂存物……），不管有没有活要干；大量 LINQ 写法产生无谓内存分配。
- **改法**：事件只保留末尾一段（保底 256 条），更早的折叠成"丢弃计数"；每步先问"有没有 Buff/冷却/暂存物"没有就整段跳过；手写循环替代 LINQ——**所有随机数调用顺序、数值累加顺序逐位不动**（确定性是命根子）。
- **验证**：领域测试 156/156，含"整段跑 vs 分段跑结果逐位一致"的确定性门禁。
