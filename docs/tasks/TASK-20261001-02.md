## 一、结论与统计口径

当前已经统一了 **ECS 状态驻留与运行时所有权**，但业务执行仍混合 **Update 调度 System、tag 相位包装器、聚合命令方法与过程式静态引擎**。目录迁入 `src/Ecs`、挂上 Component、经过 `RunSystem`，都不能单独证明规则已经组件化。

用户所说的「组件决定参与能力、tag 像回调一样在事件点触发 System」已实现，但当前覆盖面小；默认配表下，那 3 个最典型的反应组件尚未启用。最有效的下一步是统一已有业务变更与副反应的入口，消除平行状态和重复规则，而非增加更多转调包装器。

### 静态统计（不代表耗时或运行频率）

范围：当前工作区 `src/Ecs/**/*.cs` 的 `YuoSystem<...>` 实现，排除 `obj`/`bin`，并全 `src` 核对没有遗漏其他游戏 System。比例分母为 22 个 System 类型。

| 类别 | 数量 | 类型占比 | 实际含义 |
| --- | ---: | ---: | --- |
| `IUpdate` System | 13 | 59.1% | 10 个行动阶段 + 3 个遭遇阶段 |
| 自定义战斗相位 tag System | 6 | 27.3% | 6 个不同 tag，每个目前只有一个 System，全部转调同名引擎方法 |
| 命中能力组件 + tag System | 3 | 13.6% | 气血汲取、灵力汲取、反伤；同一个 `IOnHitTrigger` 配合不同能力标记 |
| 自定义 tag System 合计 | 9 | 40.9% | 6 个相位 + 3 个命中反应，不能称为 40.9% 的业务已反应式 ECS 化 |
| 以主要阶段规则转调为主的 System | 17 | 77.3% | 10 个行动 + 1 个战斗推进 + 6 个相位；不把门控/埋点/局部簿记算成规则下沉 |

其余 5 个 System 为 2 个直接维护目标索引/日志的系统和 3 个能力匹配系统；后者仍调用会修改命中上下文的 `CombatTriggerMath`，所以也不能据此宣称规则全写在 Run 体内。

本次没有现场采样进程或玩家数据，因此不提供 CPU、调用频率或线上负载百分比。真正的动态占比需区分 tag 派发次数、组件匹配后 Run 次数、规则执行耗时，以及普通推进/批量推进；不能仅统计 `RunSystem` 调用次数。

## 二、YuoCore 的真实理念与机制

设计依据：

- `vendor/YuoCore/docs/yuocore-et-essence-final-design.md:8`：ECS 负责数据和逻辑，Fiber 负责所有权与执行上下文。
- 同文 `:41`：并行粒度是 Fiber；同一 World 内 System 串行。
- 同文 `:74-99`：消息入口与 ECS 逻辑入口分离，System 不负责网络、RpcId、超时与回包。
- `docs/design/总纲/18-服务端ECS化执行架构与触发器规约.md:18-33`：道化目标是 System 持有规则本体、Component 持有状态本体。

这里有两个独立维度：

| 维度 | 作用 | 当前例子 |
| --- | --- | --- |
| `ISystemTag` 接口 | System 订阅的派发时机 | `IOnHitTrigger`、`ICombatPlayerActPhase` |
| 实体上的组件组合 | 哪个实体具备响应能力与数据 | `CombatantComponent + ThornsComponent` |

`YuoWorld.RunSystem<IOnHitTrigger>(unitEntity)` 是调用处立即同步执行的条件派发；tag 是 System 上的接口，不是挂在实体上的对象。多组件 System 需要实体同时具有所有泛型组件。负载经 `CombatTriggerInboxComponent` 等组件传递，RunSystem 自身没有请求/返回值协议。

机制证据：`YuoWorld/Function.cs:217`（接口订阅注册）、`YuoSystemContent.cs:56`（组件交集）、`YuoWorld/RunSystem.cs:15,57`（实体同步派发）、`SystemBase.cs:646`（匹配资格）。

推荐使用实体入口，让它选择实体所属 World；`RunSystemForAll<T>()` 使用默认 World，不宜作为多分片业务事件入口。不同 tag 的先后由调度器的调用顺序决定，`SystemOrder` 只排序订阅者，不能自动排列不同相位。当前同组的汲取/反伤明确为 100→110→200；通用内核还存在 SystemGroup 拓扑，不应跨组仅比较数字。

内核默认捕获 System 异常；本项目 `EcsWorldShard.cs:36-43` 已把 `CloseSystemTry=true`，让错误向上传递并触发宿主失败处理。不是当前业务在静默吞异常。

## 三、真实生产调用链与覆盖缺口

### 1. 运行时与状态所有权已经落地

`src/Server/Program.cs:110-120` 注册 `EcsGameRuntime` 和 `EcsPlayerRuntimeAdapter`；ComputeNode 在 `DeterministicBatchEngine.cs:102-107` 也通过同一运行时创建玩家、重绑定指纹并推进。

`EcsWorldShard.MutatePlayer`（`:372`）已经通过 `WrapViewAggregate`（`:398`）直接引用组件中的 POCO 状态。`PlayerAggregate.Wrap`（`:580`）是请求内命令视图，已不存在旧的完整导出→Restore→回灌。仍待统一的是聚合方法中的规则入口，而不是再做一次「去快照往返」。

### 2. 行动 System 主要是调度入口

`ActionSystems.cs:29-170` 仍主要调用 `EcsActionSession.PrepareClock/PrepareQueue/AdvancePreparedAction/CompleteYield/...`。

接着 `EcsActionPipeline.cs:245,280,348,356,367,419,463` 再进入 `SimulationEngine`。准入、轮结算、物品/材料、回复、旅行等状态变更规则仍主要由静态方法实现。它们已在 ECS 程序集，不等于已经由组件组合选择执行。

采集、制造、空闲的单玩家批量推进另有真实快速路径：`EcsWorldShard.cs:497-503` 调用 `AdvanceBulkTimedUntilUnsupported`；后者在 `EcsActionPipeline.cs:180-195` 直接按阶段顺序调用静态方法，绕过 `YuoSystem.Run`。批量路径与普通路径共用同一规则，但新增 tag 反应若只挂在 Update 包装层，会被批量路径漏掉。

### 3. 战斗相位已 tag 化，单位规则尚未本体化

生产遭遇推进在 `EcsActionPipeline.cs:401-402` 显式传入 ECS 相位派发器。`DeterministicCombatEngine.cs:139-167` 逐相位派发 tag，`CombatPhaseSystems.cs:28-67` 全部将上下文再交给引擎相位方法。

目前 6 个 tag 均在**遭遇实体**上派发，不是按玩家/怪物单位能力组件选择；玩家/敌方出手仍分别由 `ApplyPlayerActPhase/ApplyEnemyActPhase` 过程式组织。施法、普攻、冷却、Buff 处理本体见 `DeterministicCombatEngine.cs:403-538`。

### 4. 3 个反应式组件目前未被默认配表启用

`OnHitTriggerSystems.cs:9,22,34` 是真正的能力组件交集：缺少对应 marker 即不参与。挂摘由 `CombatTriggerSurface.Sync`（`CombatTriggerDispatch.cs:100-104`）按 Effects 点数是否大于 0 决定。

对 `config/game-data` 全部 **27 个 JSON** 递归解析：`hpDrainPoints`、`mpDrainPoints`、`damageReflectPoints` 三个键的出现次数均为 **0**。玩家参数只由装备 specialMechanics 汇入（`PlayerAttributeResolver.cs:175,191-193`），怪物缺省读取也为 0（`GameDataCatalog.cs:885-888`）。因此按当前仓库配表初始化的正常战斗单位不会挂这 3 类 marker；命中点仍派发 tag，但不会执行这 3 个匹配 System。测试注入或自定义配表可以激活，不能据此推断所有现存部署状态。

目前 `CombatTriggerKind`（`CombatHooks.cs:87-90`）只定义了 OnHit；总纲里的 OnKill/OnCast/OnExpire/OnDeath 属于扩展设计，不是现有完成清单。

### 5. 部分组件仍是平行数据壳

`PlayerComponents.cs:169-192` 定义 `CombatantComponent.Stats/State`、`SkillStateComponent.Skills/CooldownUntil` 和 `BuffComponent.Active`。

实际战斗读取的是 `CombatantState.Skills/SkillCooldownUntil/Buffs`（`DeterministicCombatEngine.cs:433,453-477,518-534`）。`SkillStateComponent` 和战内 `BuffComponent` 目前只在创建/挂接处出现（`EcsWorldShard.cs:719-720,780,860-861`），没有消费冷却/Active 的 System。新增技能或 Buff System 前必须将这些组件变成同一权威状态的视图，或一次性转移字段与所有读写；不能对空壳新增读者，再做双写同步。

## 四、适合统一的业务与建议顺序

以下为建议设计，尚未实现；tag 命名仅说明职责，不要求每个函数、buffId 或技能 ID 都新增类型。

| 优先顺序 | 现行规则入口 | 建议组件/tag 组织 | 真实收益与约束 |
| --- | --- | --- | --- |
| 1 | 行动取消、插队、轮转、轮完成 | 队列/请求组件 + 队列变更与轮结算 tag；归档、后继激活、遭遇清理由固定同步阶段承担 | `PlayerAggregate.cs:724,782,892` 与 `EcsPlayerActionContext.cs:97,117,135` 已有对应规则；统一命令与模拟入口，保住 -1 无限循环与版本提交时机 |
| 2 | 行动/战斗/成长后的统计回调 | 明确的统计增量负载 + 同步记账 tag，仍共用三账本更新规则 | `ActionReportBook.cs:12` 当前是真正的 `Action<PlayerBattleReport>` 回调；覆盖行动、离线、每日账本。只消费实际入账量，不重新算奖励；保留 UTC+8 日期切换与现行更新顺序 |
| 3 | 资源边界、自动用品、Buff 到期 | 资源/用品/被动 Buff 数据组件 + 资源窗口准备/收尾 tag，拆独立反应订阅 | `SimulationEngine.ResourceBoundaries.cs:32-128` 与 `SimulationEngine.cs:557-630,1622-1819` 跨业务串联；在同一自然窗口执行，普通/批量路径都进入同一规则 |
| 4 | 六战斗相位及施法/普攻/Buff/死亡 | 先收敛战斗权威状态，再把相位规则放入 System；单位出手按共享单位组件及行为能力选择 | 当前相位 tag 都是转调壳。批量 AdvanceTo 继续充当调度骨架；每个自然边界内同步派发，保持同刻玩家/敌序、RNG、命中后立即反应与反应后死亡裁决 |
| 5 | 装配、习得、参悟、突破 | 命令业务变更由相应组件 System 承载；属性实际重算后派发面板/能力表面同步 | 活跃命令在 adapter `:326,331,386`，本体在聚合/Loadout 方法；保留 InputRevision 惰性解析，不能每获得一点经验就立即重算，宿主仍控制钱包/存档/回执事务 |
| 6 | 节点驻留、建筑效果投影 | 节点变更 tag 维护人口；提交后的建筑投影 tag 更新受影响玩家效果 | `SyncNodeMembership`（shard `:687`）已共用但需多个入口显式调用；节点 tag 能统一副反应。建筑组件明确是 Registry 的镜像，DB 行锁、跨实例采纳、扣料事务仍在宿主 |

其中第 1/2 项最直接解决已经存在的重复规则与回调组织；第 3/4 项收敛当前最大的过程式调度块。装配/突破可以改成命令 System，但不要求每条命令都强行建立一层空包装。

一个适合现有机制的执行形态：

```text
宿主：输入解析、鉴权、幂等、事务控制
  → 玩家/分片所有权内的规则执行
  → 组件工作上下文 + 同步 tag System
  → 明确的已结算增量 + 统计/属性/节点等同步副反应
  → 数据快照与资产增量返回宿主
  → 宿主持久化并回包
```

组件组合划分原则：需要独立响应的能力才独立组件；普通数值 buff、用户定义技能条件、同族技能条目继续放内聚数据集合。tag 表达稳定的业务时机，数据表达配表差异。`SkillTriggerEvaluator.MatchesAll` 是条件求值，不是「OnHit 事件回调」，适合保留为 System 调用的纯函数。

## 五、不宜为了统一而搬入 System 的边界

- WebSocket 信封、鉴权、限流、回包、网络超时、会话生命周期仍由宿主适配层处理。
- PostgreSQL 仓储、durable outbox、快照编解码、DTO 映射保留现有边界。
- 市场 `MarketRuntime` 的 fence、Serializable 事务、幂等、journal/Undo 不能由同步 tag 派发替代；`OrderBook` 等纯撮合算法可继续是规则函数。
- 属性解析、经验曲线、伤害乘区、条件求值、建筑效果聚合等纯算法可由 System 调用，无需各自建 System。
- 建筑 Registry 的数据库写入与缓存采纳保持宿主权威，优先统一提交成功后的 ECS 投影反应。
- 斗法 `TryReserveDuel/AttachDuel/BuildDuelMirror` 等在 `src` 内没有实际调用者，`DuelScriptEngine.Resolve` 同样只有测试调用；不算进当前生产业务占比。活跃的弃战入口与既有回放推进可以分别归入取消事件及行动规则统一。
