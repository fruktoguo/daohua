## 1. 需求分析

用户要求把“完全清零历史包袱”的商业级持久化最终方案写入正式文档，并明确讨论为什么当前不使用 Redis。文档必须同时满足：

1. 不把现有 `player_snapshots`、旧 outbox、旧市场账本、旧协议或旧部署方式当作设计约束；
2. 玩家状态、资产、市场、离线补算和外部副作用具备清晰的权威边界；
3. 支持目标 `2c4g/40g`、5000+ 注册账号、100+ 持续连接、500+ 峰值网络收发和 2000+ 冷挂机补算；
4. 避免高频日志、消息和逐 Tick 记录造成硬盘/WAL 膨胀；
5. 对 Redis 做职责级决策：明确不用它承载什么、为什么不用、什么客观条件满足后才允许引入。

- [x] 模拟状态按 section 合并写回，默认不超过 15 秒一次；行动边界、登出、停机触发强制保存。
- [x] 资产、订单、冻结、成交和账务流水在 PostgreSQL 同一事务内完成；幂等键和唯一约束为硬门禁。
- [x] Durable outbox 只记录必须跨进程/跨系统投递的副作用，不记录每帧消息、日志、心跳和战斗 Tick。
- [x] 当前部署不引入 Redis；不将 Redis 当作权威存储、市场锁、玩家状态库或 outbox。
- [x] 未来只有在跨实例共享临时状态、连接广播或限流等明确需求出现，且可接受 Redis HA/持久化/监控/备份成本时，才单独评审引入。
