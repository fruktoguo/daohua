## 需求复述与理解

用户痛点：当前 Buff 实现复用性低——每种效果维度（如 `hpRegenPerSecond` 每秒回血）都要单开一个平铺字段横跨约 24 类位置散弹修改（4 份 record 副本 + 6 处授予读键 + 6 处互转复制 + 3 组结算接线 + 3 个协议 DTO + 前端两套解码）。目标：

1. **高扩展性**：新增效果通道 = 枚举值 + 注册表一行的成本；
2. **高性能**：命中结算热路径消除重复 O(Buffs) 遍历；
3. **可读性与架构优美**：数值效果通道、生命周期元数据、结算时机三类关注点分离。

用户裁定：**全量统一四处副本 + 聚合缓存与折叠面板缓存**。

## 核心设计

- `BuffEffectChannel` 枚举（14 存量通道）+ `BuffEffectRegistry` 单点注册表（ConfigKey/StackMode/GrowsWithLevel/OutOfCombatPanelKind）+ `BuffEffectParser` 统一配表解析。
- 四副本（`CombatBuffState`/`CombatBuffCarry`/`ActionSustainedBuff`/`ActiveBuff`）统一为 `(元数据, Effects 通道载荷, StatRatios)` 形态；互转退化为载荷直传。
- `CombatantState` 单位级聚合缓存（`_buffTotals` 数组 + 5s/1s 网格存在性标记）与 `EffectiveStats` 脏标记缓存；失效点封闭于既有函数（授予/到期剔除/层数重算/跨波注入/快照恢复/开战授予/战外注入/换面板）。
- 协议统一为 `effects: [{channel, value}]` 数组 + `statRatios`；前端单一通道注册表吞并 `STAT_RATIO_LABEL_KEYS`。
- 硬性不变量：战斗结算数值逐位一致（聚合累加保持列表序）、配表 JSON 零改动（ConfigKey 与现有键同名）、战内本期不消费 StatRatios、触发器管线不动。
