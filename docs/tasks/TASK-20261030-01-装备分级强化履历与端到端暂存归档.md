# TASK-20261030-01: 装备分级强化履历与端到端暂存归档

## 1. 任务背景与核心目标

当前装备强化系统在服务端每轮推进时仅有即时日志事件（`enhance.succeeded` / `enhance.failed`）与战报消耗记录，缺乏针对「具体装备」在「各个强化等级（+1 ~ +20）」的尝试次数、成功次数与实际成功率的统计沉淀。
为了支持玩家清晰了解自身装备的强化历史胜率，且不增加服务端数据库的长期冷数据膨胀，构建一套**「服务端高可靠轻量暂存 + 客户端长期累加归档 + 双向确认清理」**的完整闭环。

## 2. 核心架构设计

### 2.1 统计维度与数据模型
* **装备标识**：`ItemId`（如 `equipment.qingyun-sword`）。
* **等级分段**：目标等级 $1 \sim 20$。
* **分级指标**：
  * `attempts`：该等级累计尝试次数。
  * `successes`：该等级累计成功次数。
  * 成功率动态计算：$\text{rate} = \frac{\text{successes}}{\text{attempts}} \times 100\%$。

### 2.2 服务端暂存生命周期（Staging Buffer）
* **存储挂载**：挂载在玩家聚合的 `PlayerProgression` 或 `PlayerActionQueue` 分段中，随玩家快照持久化，挂机补算或重启不丢失。
* **行动状态分类**：
  * **进行中（Active）**：行动仍在队列中，强化数据持续累加更新，状态为 `Active`。
  * **已完成（Finished）**：强化行动出队（达到目标等级或玩家手动取消或材料不足提前完成），状态标记为 `Finished`。
* **数据推送与确认机制（Ack/Handshake）**：
  * 玩家建立 WebSocket 连接（上线/重连）时，服务端在玩家快照或增量通知中下发暂存记录。
  * 客户端收到后，安全合并并写入浏览器本地存储（LocalStorage / IndexedDB）。
  * 客户端向服务端发送确认回执 `enhancement.ack_records`（携带已落盘的记录批次 ID）。
  * 服务端收到确认后：
    * **彻底清理所有标记为 Finished（已完成）的暂存记录**；
    * **保留 Active（进行中）的记录**，直到该行动彻底完成并在下次被确认接收后才移除。

### 2.3 客户端存储与 UI 呈现
* **本地长期存储**：`daohua.enhancementRecords.${playerId}`，客户端按物品、等级永久累加合并。
* **UI 交互**：在强化页面（`EnhancementPage.tsx`）中增加「强化履历与胜率统计」面板，展示当前选定装备在各个等级的强化战绩：`+1: 70次/100次 (70.0%)`。
