## 共享 API 与协作契约

- B/C 的游戏代码必须使用同一套源文件和同一命名空间；只能通过项目引用/构建配置选择 baseline 或 optimized YuoCore。
- ECS 核心允许使用粗粒度业务组件：玩家身份、成长、世界、战斗、装配、Buff、行动队列、背包、经济；怪物共用 `Combatant`/技能/Buff 组件，地图节点为长期实体。装备、技能、Buff 和物品默认是组件数据，不为每个条目无条件创建 Entity。
- System 顺序固定为离散事件推进：行动/战斗时钟 → 队列/目标 → Buff/冷却 → 技能/普攻 → 伤害/死亡/奖励 → 快照/落盘；不得改成固定 Tick 语义或复制另一套战斗公式。
- Fiber 只承载所属 World 的串行所有权；数据库、WebSocket 和 HTTP 通过宿主适配边界进入命令，不允许外部线程直接持有或修改 ECS 聚合/组件。
- 任何协议字段、快照结构和数据库写入语义变化必须同步所有三套服务、前端和测试；本地内测可一次性破坏历史兼容，但禁止新增 legacy fallback、双写或迁移运行时。

每个 `variant × scenario` 输出 JSON 和 CSV，至少包括 `variant`、`scenario`、`players`、`duration`、`total_wall_ms`、`cpu_ms`、`simulation_ms`、`entity_create_ms`、`system_tick_ms`、`snapshot_ms`、`database_ms`、`network_ms`、`allocated_bytes`、`gc0`/`gc1`/`gc2`、`rss_mb`、`p50_ms`/`p95_ms`/`p99_ms`/`max_ms`。同时记录进程启动、World 初始化、程序集扫描、System 注册、Entity 创建、角色加载、命令排队、Actor/Fiber 调度、快照映射、JSON 编码、PG/连接池等待和 WebSocket 发送队列。

报告只陈述实际运行结果：给出 OOP、ECS-current、ECS-optimized 的绝对值和相对倍率，注明 workload、硬件、GC 模式、数据库状态、运行时长和未覆盖风险；同时单独标示上述三项优化目标是否达到。优化 ECS 的采用建议必须基于真实玩法中的结果一致性与综合代价，不能用极端 100 组件/100 系统 benchmark 替代采集、制造、战斗或离线补算证据。

进程采样的追加与报告快照使用同一同步边界，保留采样顺序和原始字段。`measurement_status` 独立于成功 WS 命令数：缺失前后宿主指标窗口，或服务端阶段/事件、进程差分与数据库差分全部不可用时，报告为 `partial`；执行错误仍为 `failed`，不可用字段保持 `null`，不能因命令成功而标为完整实测。
