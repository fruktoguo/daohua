# TASK-20260917-01 · 斗法（PVP）与战斗收益战报

## 任务信息

- 提出时间：2026-09-17 04:20
- 状态：🚀 进行中（设计定稿，开始实施）
- 分类：全栈新功能（领域模型 / 匹配运行时 / 协议对齐 / 前端面板 / 配表数值）

## 需求口径（用户原话整理 + 已确认裁定）

1. 历练（战斗行动）的确认开始面板增加「斗法」勾选，勾上表示玩家同意 PVP。
2. 当前战斗没有统计本次战斗内的全部收益，需要增加：修为、底蕴（经验）、物品、六维经验；每次开启新的行动后重置；服务端最多保存 10 次记录；前端每次获取记录都写入浏览器本地存储，且必须去重。
3. 开启斗法后出现「暂存区」：20 分钟内通过战斗获得的所有物品进入暂存区；PVP 被击败后暂存区内所有物品归胜方。
4. 每个队伍（单人/多人均算一个队伍）每次行动有一定概率增加一次「斗法遭遇计数」；计数 > 0 时下次进入战斗随机匹配实力相近、同样有计数的队伍；实力暂按六维总和，匹配范围上下浮动 30%，不匹配过强或过弱。
5. 是否进入 PVP 由斗法遭遇计数控制；后续可能加「斗法遭遇不再下降」类道具，设计保留扩展点。
6. PVP 失败后，队伍一小时内不会再进入 PVP。
7. 开启斗法后战斗所有物品爆率总增 20%。
8. 每次进入战斗有概率增加斗法计数，目标均值约每 2 小时一次，允许随机波动。

### 用户补充裁定（2026-09-17）

- **击杀收益**：战斗击杀按配表产出修为、底蕴与六维经验，数值全部来自配置文件（怪物配置新增奖励字段，先统一填 10，禁止写死）；六维经验「按照功法给」——按已装配功法槽位的 `rootAttribute` 均分，无功法时六维平均分配；修为与底蕴分别记录。
- **匹配池**：玩家分在线 / 离线挂机 / 彻底离线三态；在线与离线挂机本质无区别（actor 已加载即参与），只有彻底离线（actor 未加载）不参与任何行动与匹配。
- **实时性**：斗法双方是实时同一场战斗，无挑战/被挑战之分；战斗中修改任何战斗相关配置均不生效，重新进入战斗行动才生效。
- **中途结束行动 = 直接判负**（含显式移除、旅行插队、被移出队首、actor 卸载即离线）。

## 关键设计定案

### 定案 A：实力与匹配

- 队伍 = 玩家聚合（当前单玩家即单队伍，`TeamId = PlayerId`；多人队伍未来在 `PlayerDuelState` 之上加队伍层，本版预留字段语义）。
- 实力值 `Power` = 六维等级总和（`PlayerCoreAttributes` 六维派生等级之和）。
- 候选条件（双方同时满足）：actor 已加载（在线或挂机）、`EncounterCharges > 0`、未处于冷却（`CooldownUntil <= now`）、无进行中斗法（`ActiveDuelId == null`）、队首行动为勾选斗法的战斗行动（`Intent.PvpEnabled && ExecutionKind == CombatEncounter`）。
- 匹配区间：`[0.7 × self.Power, 1.3 × self.Power]`（double 比较，含端点）。
- 候选为空 → 不消耗计数，本次正常进入怪物波次战斗；计数保留到下次触发。
- 匹配随机源：服务端 `Random.Shared`（匹配路径不属于确定性模拟，匹配结果落地为持久化斗法脚本后回放是确定性的）。

### 定案 B：遭遇计数与概率

- 斗法勾选行动的远征在每次「搜寻完成、即将生成波次」的战斗入口判定：
  1. 若冷却中 → 直接走普通怪物波次。
  2. 若 `EncounterCharges > 0` 且当前推进启用了匹配（在线 actor 路径）→ 进入 `DuelPending` 等待相位，由运行时异步撮合；撮合成功才扣双方各 1 次计数。
  3. 否则按概率 roll 增加计数：`roll = NextSeed(seed) % 1_000_000 / 1e6 < DuelEncounterChancePerBattle` 时 `charges += 1`（本次战斗仍是怪物波次，计数留给「下次」）。
- 概率常量 `DuelEncounterChancePerBattle = 0.005`（每场战斗 0.5%）。估算依据：搜寻 5s + 单场战斗约 15~60s + 重生 5s，每小时约 60~140 场，期望约 2.9~1.4 小时一次，符合「约每 2 小时一次，允许波动」。
- roll 由远征种子派生，离线补算与在线推进的计数增减序列位级一致（确定性）。匹配决策本身是运行时行为，不计入确定性回放：离线补算路径（ComputeNode / 不带匹配开关的 AdvanceTo）在 `charges > 0` 时不进入 `DuelPending`，保留计数直接打怪物波次。

### 定案 C：斗法战斗形态（权威脚本回放）

为保证双方结果一致与确定性重放，斗法采用「一次权威解算 + 双方脚本回放」：

1. 撮合成功后由 `DuelRuntime` 收集双方**冻结镜像**（`CombatantStats` + 功法槽映射的 `MonsterSkillSlot[]` + 显示名 + 暂存区快照），调用领域纯函数 `DuelScriptEngine.Resolve(initiator, defender, seed)`：
   - 发起方为 `player`，应战方镜像为 `enemy:0`；
   - 双方功法槽统一映射为一次性技能（`TriggerHpRatio = 1`，开场即触发一次；后续版本可升级为完整触发语义）；
   - 用 `CombatEncounterState + DeterministicCombatEngine` 一次性推进到 `MaxDuelSeconds = 180` 秒或分出胜负；超时判 `Draw`；
   - 产出 `DuelScript { durationSeconds, outcome, events[] }`，事件为 `(at, attackerIsInitiator, targetHitpointsAfter, damage, hit, critical, abilityId?, healing)` 紧凑序列。
2. 双方远征进入 `Phase = Duel` 回放相位，各按自身视角回放同一脚本（应战方视角交换 player/enemy 角色），血量按事件时间轴推进；`Outcome` 直接取脚本权威值。
3. 回放推进完全由已持久化的脚本驱动，离线补算可原样重放（确定性）；`彻底离线`（actor 卸载）按判负处理，回放持久化载荷中已写入判负标记，重连后落到败方结算。
4. 战斗期间任何装配/功法/消耗品变化均不影响该场斗法（快照冻结），与「重新进入战斗行动才生效」一致。

### 定案 D：结算规则

- 回放结束（或判负）时**各自在自身 actor 内本地结算**，跨玩家一致由同一 `DuelScript` 保证：
  - 胜方：钱包 += 败方暂存区快照（撮合时刻冻结，随脚本下发）→ 走 `AssetDelta` → economy 事务入账；`CurrentReport.DuelWins += 1`；战报物品计入。
  - 败方：清除暂存区快照对应条目（斗法期间暂存结算冻结，快照与现存条目逐条精确匹配）；`CooldownUntil = now + 3600`；`CurrentReport.DuelLosses += 1`。
  - 平局：双方无暂存转移、无冷却，事件 `duel.draw`。
  - 双方 `EncounterCharges` 已在撮合 attach 时各扣 1。
- 判负（中途结束行动 / actor 卸载 / 斗法行动被移出队首）：立即按败方结算自身（清暂存、冷却、计负），`DuelRuntime` 通知对方 actor 执行 `duel.peer-forfeited` → 对方立即按胜方结算并结束回放。`DuelRuntime` 内存表 `duelId → {initiator, defender, resolvedOutcome}` 防重复结算；重启后失效的斗法以双方持久化脚本为准，各自完成回放结算。
- 暂存区规则：
  - 勾选斗法的战斗行动期间，战斗掉落与斗法战利品**进入暂存区而不直接入钱包**；斗法胜利所得战利品直接入钱包（不再进暂存，避免链式风险）。
  - 条目 `acquiredAt + 1200s <= now` 时结算入钱包（`duel.staged.settled` 事件）。
  - 斗法进行中（`ActiveDuelId != null`）冻结到期结算。
  - 未勾选斗法的行动收益、非战斗物品产出不受影响，直接入钱包。

### 定案 E：战斗收益战报

- `PlayerBattleReport`：`{ reportId(=行动实例ID), actionId, actionName, startedAt, endedAt, qi, experience, rootExp{stamina,intelligence,attack,defense,swordsmanship,talisman}, items[{itemId,quantity}], duelWins, duelLosses }`。
- 生命周期：`CurrentReport` 绑定队首战斗行动实例 ID；新战斗行动会话开始（远征创建且实例 ID 不同）或该行动被移除/离开队首时归档；全部计数为零的空报告不归档；`Reports` 只保留最新 10 条。
- 记录口径：修为（`Qi` 入账量）、底蕴（`Experience` 入账量）、六维经验（各维入账量）、物品（掉落与战利品入账量，按 itemId 聚合）。
- 前端：收到 `duel` 分段后将 `reports` 与 `currentReport` 合并写入 `localStorage["daohua.battleReports.<playerId>"]`，按 `reportId` 去重、按开始时间倒序截断 50 条；服务端权威仍是最近 10 条。

### 定案 F：六维经验落地

- `PlayerCoreAttributes` 由六维「等级」改为六维「经验」字段（`StaminaExp` 等，内测可破坏存档结构）；等级派生：`Level = floor(cbrt(exp / 100)) + 1`，与前端 `getCumulativeExpForLevel = 100×(l-1)³` 曲线一致，域内新增 `RootAttributeCurve.Level(exp)`。
- `PlayerAttributeResolver`、协议映射、前端 `loadout` 全部改用派生等级；`coreAttributes` 载荷同时下发 `*Exp`（前端可展示真实进度，顺带修复洞察页硬编码 0% 的问题）。
- 功法配表新增可选 `rootAttribute`（`stamina|intelligence|attack|defense|swordsmanship|talisman`），全部现有功法按流派补齐配置；击杀时 `rootExpReward` 均分到已装配功法槽声明的维度集合，无槽位功法时六维均分。

## 一致性 / 不变量

- `RemainingRepeats == -1` 语义不变；斗法不改动行动出队规则。
- 离线补算位级一致：计数 roll 由种子派生；斗法脚本持久化后回放确定；`DuelPending` 在无匹配能力路径下回退普通波次（不回放 pending）。
- 每个玩家状态只经自身 actor 单写者修改；跨玩家只传不可变镜像与脚本。
- 战利品转移单边一次结算：胜方入账由自身 sim 产生 `AssetDelta` 走 economy 事务；败方清暂存只改自身分段；双方一致由共享 `DuelScript` 权威保证。
- 协议信封无新消息类型：斗法状态全部走既有 section 快照/增量 + 日志模板，无需新增 `WireMessageType`；`action.enqueue` 载荷新增可选字段向后兼容（schema v3 直接切换，内测清零）。
- Schema：`PlayerStateHead/PlayerSectionSnapshot/SectionCodec` schema v2→v3；`PostgresSchema.Version` 不变（sections 表按 kind 通用）；前端 `decodeSections` schemaVersion 检查同步改 3。
