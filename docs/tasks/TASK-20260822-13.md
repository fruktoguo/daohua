## 2. 需求背景与核心痛点

当前代码库处于开发早期，不存在历史数据兼容负担。但现有 `src/Domain/Models` 及宿主事务逻辑存在多项技术债务：
1. **伪 ECS 退化**：虽然引入了 `YuoCore.Ecs`，但只创建了单个 `PlayerComponent`，把 600 行的庞大单体 `PlayerState` 包装在内，未发挥 YuoCore 细粒度组件与 `YuoSystem<T1..Tn>` 调度的威力。
2. **手写深拷贝地狱**：由于采用可变贫血类，状态隔离依赖上百行手写的 `Clone()`，新增字段极易漏拷引发状态穿透 Bug。
3. **上帝文件堆砌**：`Models.cs`、`CombatModels.cs`、`Enums.cs` 单文件包含十余种异构类型。
4. **事务与锁机制违背 YuoCore 思想**：
   - 外部控制器通过多重分布式大锁同时锁 Market 与 PlayerFiber；
   - 跨分片/跨 Fiber 未走 Actor 消息事务（Saga 补偿机制）。

---

## 3. 技术重构方案总览

基于 YuoCore 架构哲学（Fiber 独占单线程 World、多泛型 System、Actor 跨边界、StateSync 差量同步与异步 Persistence），重构为**四层数据体系与 Actor 消息事务**：

1. **Definitions 只读配置层**：`sealed record` + `FrozenDictionary`，启动加载后只读不可变。
2. **Components 细粒度领域组件层**：拆分 `InventoryComponent`、`ActionQueueComponent`、`CultivationComponent` 等。
3. **Systems 纯业务逻辑层**：`YuoSystem<T1, T2...>` 驱动无锁单线程 Tick。
4. **Snapshots 零拷贝持久化层**：流式投影快照丢入 `YuoCore.Persistence` 异步落盘队列。
5. **Actor 消息事务与 Saga 补偿**：挂单/撤单等跨边界事务由外部分布式大锁改造为 Actor 消息请求-应答与补偿机制。
