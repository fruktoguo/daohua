### 3.2 `platform.section_flush_queue` 是 WAL 主要产源

`pg_stat_user_tables` 实测：

```
n_tup_upd = 82193    n_tup_hot_upd = 0    n_tup_newpage_upd = 44387
n_tup_ins = 82102    n_tup_del  = 82193
```

**`n_tup_hot_upd = 0`** —— 全部更新均为非 HOT 更新，每次更新重写全部索引项。

根因链条：

1. `ix_section_flush_ready ON (next_attempt_at, lease_until)`（`PostgresSchema.cs:416`）
2. worker 认领租约的语句 `SET lease_until = $3, lease_token = $4`（`PostgresSectionRepository.cs:574`）**更新了索引列 `lease_until`**
3. 索引列被修改 → HOT 更新条件不满足 → 每次租约操作重写索引项
4. `full_page_writes = on` 且 `checkpoint_timeout = 900` / `max_wal_size = 1GB` → checkpoint 后首次改页写**整页 8KB FPI**

**重要更正**：v27 已将该表刻意设计为「追加式收件箱」（纯 INSERT，见 `PostgresSchema.cs:35` 与 `PostgresSectionRepository.cs:445-450` 注释），目的是从根上消除与 Serializable 资产事务的 40001/40P01 冲突。**不得**改为 `UPDATE` 覆写——那会重新引入并发冲突。

### 3.6 留存治理的真相（2026-10-22 19:0x 补充取证，推翻初判）

**初判更正**：本任务初稿称「`economy.transactions` 无清理机制」——**错误**。`PostgresRetentionWorker` 早已实现该清理，且在线运行中。

`PostgresRetentionWorker.cs:85-95` 的删除条件：

```sql
WHERE t.created_at < now() - interval '1 hour'
  AND t.transaction_type IN ('simulation.reward', 'participation.settlement')
  AND NOT EXISTS (SELECT 1 FROM economy.transaction_lines   l WHERE l.transaction_id = t.transaction_id)
  AND NOT EXISTS (SELECT 1 FROM social.party_session_inbox  i WHERE i.consumed_transaction_id = t.transaction_id)
LIMIT $2   -- batchSize: Math.Min(10_000, RetentionBatchSize * 16)
```

实测运行日志（19 次）每轮均为 `emptyTransactions=4096`，即恰好被 `256 * 16` 的批上限卡死。

**积压归因**（清理条件本身有效，是吞吐不足）：

| 项 | 值 |
| :--- | :--- |
| 无明细行总量 | 408869（**全部为 `participation.settlement`**） |
| 满足时间条件（>1h） | 376135 |
| 被 inbox 引用阻塞 | 仅 4 |
| `simulation.reward` 积压 | **0**（已清空） |

结论：清理逻辑正确且生效，`simulation.reward` 因量小而清空；`participation.settlement` 因**生成速率 > 清理吞吐**持续积压，并被 2026-10-19 单日 330750 行的异常进一步打穿。

清理吞吐对比：

```
改造前：4096 条/轮 × 24 轮/天 =  98184 条/天
硬上限：10000 条/轮 × 24 轮/天 = 240000 条/天   ← Math.Min(10_000, ...) 天花板
```

### 3.7 流水保留必要性判定（用户判断的验证结论）

`economy.transactions` 的**唯一运行时读取路径**是幂等重放（`WHERE idempotency_key = $1`，`PostgresEconomyRepository.cs:130/214`），不存在任何业务统计或对账读取方。

| 类型 | 明细行 | 幂等是否依赖流水行 | 判定 |
| :--- | :--- | :--- | :--- |
| `simulation.reward` | 无（payload 仅 `{stateVersion,to}`） | **否**，TransactionId 由 `simulation:{playerId}:{version}:{toMs}` 哈希派生 | 纯审计，可删 |
| `participation.settlement` | 无 | **否**，`market.settlement_claims` + `party_session_inbox` 双重承担 | 纯审计，可删 |
| `market`/`item.sell`/`shop.buy`/`item.use` 等 | 有 `transaction_lines` | 是 | **必须保留** |

真实玩家操作仅占 0.3%（1779 行）且均带明细行。**用户「战斗掉落/消耗/制造无需记录、市场交易需记录」的判断成立。**

## 5. 改造清单

### 5.1 A 项：留存清理吞吐扩容（已完成，线上已验证）

**背景**：清理逻辑本身正确，是吞吐不足。批上限被 `Math.Min(10_000, RetentionBatchSize * 16)` 卡死。

**已执行**（2026-10-22 18:34~18:41，生产）：

| 步骤 | 操作 | 证据 |
| :--- | :--- | :--- |
| 1 | 备份 `/opt/daohua/compose.prod.yaml` | `compose.prod.yaml.bak-retention-20261022-183426` |
| 2 | `Storage__RetentionBatchSize: "256"` → `"2048"` | 行 98 已生效 |
| 3 | `docker compose up -d app` 重建 | `daohua-app Up (healthy)` |

`2048 * 16 = 32768`，经 `Math.Min(10_000, ...)` 封顶后为 **10000 条/轮**（原 4096），吞吐 2.44×。

**实测结论（2026-10-22 19:20 验证）：A 项单独无效。** 首轮确实删到 `emptyTransactions=10000`（证明配置生效），但积压从 410890 反增至 412010。根因是生成速率远超清理吞吐：

| 指标 | 实测 |
| :--- | :--- |
| `participation.settlement` 新增速率 | **38135 条 / 30 分钟 ≈ 1271 条/分钟 ≈ 7.6 万条/小时** |
| A 项清理吞吐（1 小时 1 轮 × 10000） | **1 万条/小时** |
| 吞吐缺口 | **7.6 倍** |

因此仅调批大小无法逆转积压，必须同时缩短清理周期。已补充实施 B 项第 1 条（周期配置化）。

### 5.2 结算流水治理（P0，第 1 项已实施代码待部署）

1. **清理周期可配置化（已实施代码，待部署）**：新增 `Storage:RetentionIntervalSeconds`（校验区间 60..86400，默认 3600 保持既有行为）。`PostgresRetentionWorker` 改注入 `ServerOptions` 并 `PeriodicTimer(options.RetentionInterval)`。生产 compose 已设 `600`，单日清理能力从 24 万提升至 **144 万条**，可覆盖 7.6 万条/小时的生成速率并逐步消化积压。
2. **停止写无意义流水（根治）**：`simulation.reward` 与 `participation.settlement` 直接不写入 `economy.transactions`。二者的幂等已由两条独立机制承担——前者是 `simulation:{playerId}:{version}:{toMs}` 哈希派生 TransactionId，后者是 `market.settlement_claims` + `party_session_inbox` 双重确认——**删除流水行不影响正确性**。市场、买卖、商店、技能学习等带 `transaction_lines` 的真实交易继续完整记录。
3. **归因 2026-10-19 单日 330750 行异常**：需查清是何种循环放大（该日无对应玩家规模增长），否则仍会周期性打穿。

### 5.3 WAL 放大治理（P0，待实施）

4. **拆分 `ix_section_flush_ready` 的索引列**：`lease_until` 被 worker 认领语句 `SET lease_until, lease_token` 更新，导致 `n_tup_hot_upd=0`。改为不由索引覆盖 `lease_until`（如部分索引 `WHERE lease_until IS NULL` 或独立表），恢复 HOT。
5. **验证 HOT 命中率**：改造后 `n_tup_hot_upd / n_tup_upd` 必须 >50%，否则改造无效。
6. **可选：`checkpoint_timeout` / `max_wal_size` 调优**，降低 FPI 频次（权衡崩溃恢复时间）。

### 5.4 磁盘水位护栏（P1，待实施）

7. **`wal-archive.sh prune` 增加磁盘水位判定**：低于阈值强制激进清理并告警，避免再次撞 ENOSPC 进 PG 重启循环。
8. **`daohua.env` 显式声明 `WAL_RETENTION_DAYS`**：当前**未定义**，脚本取默认 8 天，属配置缺口。建议改 3 天。
