## 二、需求与裁定

用户原始需求：给当前组队增加复活选项，在组队信息里做成可调整项，分别为：
1. 直接复活；
2. 当所有队友「可复活/存活」时复活；
3. 当指定队友存活时复活。

**关键裁定（用户确认）**：
- **归属层**：每名成员**自己设置自己的**复活策略（不是队长统一设定全队）。
- **兜底**：复活读条当前 180 秒，等待硬上限取 **360 秒**（2 × 读条），到点强制起身——「这个时长再怎么肯定都活了，不活就是炸了」。

## 三、设计要点

### 3.1 策略语义

| 策略 | 标识 | 起身条件 |
| :--- | :--- | :--- |
| 直接复活 | `immediate` | 读条走完立即起身（缺省，与既有行为逐位一致） |
| 全员就绪 | `all-allies-ready` | 全部队友均存活或仍在复活读条中（可复活）时起身 |
| 指定队友存活 | `target-ally-alive` | 仅当指定队友处于存活状态时起身 |

- **判定时机**：门禁在**本人读条走完之后**才判定。倒地瞬间仍正常进入读条，读条期间行为与直接复活一致。
- **退化口径**：`target-ally-alive` 目标未指定 / 不在本场名册 / 指向本人 → 退化为直接复活，不静默阻塞。
- **单人战斗**：恒按直接复活处理，个人策略只在参与会话内生效。

### 3.2 推进不变量（本任务最高风险点）

侦察确认：若门禁不通过时只在复活派发处 `continue`（不推迟 `RespawnAtSeconds`），则
`NaturalNextAttackOrRespawn` 恒返回该过期时刻 → `AdvanceTo` 单帧空转到 `MaxEventsPerAdvance`（10 万次）后抛
`战斗推进超过最大事件数`；`SimulationSchedule` 亦会 `Consider(0)` 零延迟空转。

**根治**：门禁拒绝时必须把复活截止点**推进到未来的下一次判定时刻**：
- 取「最近的其他队友复活点」与「等待硬上限」的较小值；
- 该值若不晚于当前时钟，叠加 `RespawnRetryStepSeconds = 1` 秒最小步长；
- 由此保证自然边界严格递增，战斗时钟必然推进。

### 3.3 持久化与恢复

- 策略与观察目标随玩家 `settings` 分段持久化（`respawnPolicy` / `respawnTargetPlayerId`）。
- 开打时随 `ActionParticipantSnapshot` 冻结进会话规格，由会话在成员下标域解析为 `RespawnTargetIndex`。
- 战斗单位快照新增 `respawnPolicy` / `respawnTargetIndex` / `respawnDeadlineSeconds` / `respawnWaitingUntilSeconds`，崩溃恢复后等待条件输入完整保留。
- 跨波携带：新波入场按新战斗时钟重设复活截止点与硬上限，不沿用旧绝对时刻。
- 版本：`SectionCodec.CurrentSchemaVersion` 38 → 39；`PostgresSchema.Version` 43 → 44；新增 `migrations/0044_v43_to_v44.sql`（仅推进标签，表结构未变）。

### 5.5 新增测试覆盖的独立故障面

1. 缺省策略到点立即起身（回归既有行为）；
2. 全员就绪在队友存活时通过；
3. 全员就绪在队友彻底出局时等待，**且战斗时钟仍推进**（防空转回归）；
4. 硬上限到点强制起身（防互等僵局）；
5. 指定队友存活：目标倒地未起时等待，目标起身后立即起身；
6. 指定队友存活：目标已存活时到点立即起身；
7. 目标下标失效时退化为直接复活；
8. 策略字段随快照往返不漂移。

## 六、任务中发现并修复的周边缺陷

**全新库无法启动**：`PostgresSchema.Sql` 的 `platform.schema_version` 种子只写到 `(38, now())`，而 `PostgresSchema.Version` 已推进至 44。空库执行建表 DDL 后立即进入版本校验，最新版本仍为 38 ≠ 44，启动直接抛
「PostgreSQL schema 版本不匹配，要求 v44」并退出——任何全新环境（新库、新部署）都无法启动。

该缺陷由本次起服务做烟测时实际撞出，非本任务引入，但不修则功能无法上线，故一并修复：种子补齐 `39~44`，并以 `TEMPLATE template0` 建空库实测启动成功，日志 `PostgreSQL schema v44 已就绪`、`/readyz` 返回 `{"postgres":"healthy","market":"healthy"}`。

**观察对象离队未回收**：初版只在战斗侧按会话名册解析观察目标、失效时退化为直接复活（`ResolveRespawnTargetIndex` 返回 -1），但 `ClearRespawnTargetIf` 从未被调用——设置里残留指向已离队玩家的悬空引用，本人界面会停在「指定队友存活」与一个不存在的目标上，与真实起身行为分叉。已补 `SocialRuntime.ClearDepartedRespawnTargetsAsync`，经既有 `ApplySessionMutationAsync` 单写者通道接入 `party.kick`、`party.leave`、48h 离线逐出三条移除路径，并补两条聚合级回归（命中收敛、未命中不误伤）。
