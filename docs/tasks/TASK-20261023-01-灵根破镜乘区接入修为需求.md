# TASK-20261023-01 灵根破镜乘区全面接入修为需求

- **提出时间**：2026-10-23 02:19:30

- **分类**：数值系统 / 灵根玩法 / 境界系统 / 全栈

## 1. 需求来源

用户在开天门面板拖拽灵根时发现「后续破镜难度」永远显示 ×1.0 且拖拽中数值不变，质询「后续破镜难度怎么没有变化」。

## 2. 根因取证

设计真源 `docs/design/总纲/07-战斗数值与内视规约.md` §7.7.5.1 规定：入天门后每多一条有效灵根，升级需求乘区 +50%（五系封顶 3.0 倍），未入天门不放大。

实现偏差：
- `HeavenGateRules.ResolveCultivationMultiplier`（`src/Domain/Player/HeavenGateRules.cs:184`）与前端 `linggenCultivationMultiplier`（`frontend/src/game/linggenCalculations.ts:61`）**仅有定义与测试，无任何生产调用方**；
- 服务端修为瓶颈直接取配表原始值：`ActionExecutionRules.Timed.cs` 三处 `RealmProgression.ExpCapFor(...)`（:272 持续收益封顶、:411 轮次收益封顶、:686 底蕴成本基数）均未乘灵根乘区；
- `PlayerAggregate.Breakthrough`（`src/Domain/Player/PlayerAggregate.cs:1023`）校验 `Experience < realm.ExpCapFor(...)` 同样未乘乘区；
- 协议层 `expToNext` 透传配表原始值，前端 `calculateRealmProgress` 用本地静态曲线，灵根乘区在整条修为链路上**不存在**；
- 前端弹窗乘区显示仅是本地函数计算的可视化，与真实修为需求无关（纸上规则）。

## 3. 设计确认（已与用户对齐）

用户裁定：**全面接入**——乘区真实生效于修为需求全链路，非仅 UI 预览。

口径（沿用 §7.7.5.1，不改动数值规则）：
- `multiplier = 1 + 0.5 × (有效灵根条数 − 1)`，条数 = 入天门后 ConfirmedValues 中点数 > 0 的轴数，封顶 3.0；
- 未入天门恒 1.0（含叩天门 18 级本身：开天门前瓶颈不放大，开天门后下一层才放大）；
- 放大对象：**本层修为瓶颈（expToNext/ExpCapFor 的有效值）**，即「升到下一层所需修为」；行动获取速率不放大（否则乘区无意义——收入与需求同比放大等于没放）；
- 乘区生效范围：突破校验、持续/轮次收益封顶、底蕴成本折算基数（逆天改命/逆命丹/行动底蕴成本均按「已含乘区的 expToNext」折算，与其注释语义一致）。

## 4. 实施步骤

1. **领域层**：`PlayerAggregate.Breakthrough` 瓶颈乘以 `HeavenGateRules.ResolveCultivationMultiplier(Progression.HeavenGate.EffectiveValues, Entered)`；
2. **ECS 层**：`ActionExecutionRules.Timed.cs` 三处 `ExpCapFor` 统一乘同一乘区（新增私有 helper 避免重复）；
3. **协议层**：`ProtocolSnapshotMapper` 快照/增量透传权威 `expToNext`（乘区后）与 `linggenMultiplier` 字段，前端信封枚举对齐（协议信封强对齐门禁）；
4. **前端**：`calculateRealmProgress` 接受服务端权威 expToNext（存在则用之，缺省回退本地曲线）；开天门弹窗「后续破镜难度」显示**入天门后将生效的预览倍率**（随拖拽整轴归零/复活而变），入天门后显示当前权威倍率；
5. **测试**：领域确定性测试（不同条数 × 突破瓶颈）、ECS 结算测试（封顶与底蕴成本）、协议往返测试、前端单测。
