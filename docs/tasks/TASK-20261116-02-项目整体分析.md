## 一、总体判断

《道化太初》是服务端权威、行动队列驱动、长线挂机放置的修仙 RPG。核心技术目标是在线推进、离线补算和重连恢复使用一致的确定性规则，而不是让前端自己结算收益。

从当前代码组织看，项目已超出玩法原型阶段：成长、战斗、生活制造、装备、地图、公共建筑、坊市、社交组队、宗门、图鉴、排行榜、邮件和新手教程都有相应模块与入口；同时具备持久化、部署、备份和回归门禁设施。这是对实现范围的判断，不代表本轮逐项试玩或生产验收。

当前最值得优先投入的方向是：文档与真实实现同步、双端规则一致性、核心边界的持续回归、真实容量证据。没有证据支持先做一次大规模重写或盲目拆分微服务。

## 二、实际架构与职责

```text
React 19 / TypeScript 5.9 / Zustand 5 / Vite 7
  ├─ 同源 HTTP API（账号、目录、市场等）
  └─ 同源 WebSocket（DHW1 二进制信封 + JSON 载荷）
       ↓
ASP.NET Core 10 / src/Server
  ├─ Server.Clean：认证、仓储、协议映射、市场及后台任务
  ├─ EcsPlayerRuntimeAdapter：玩家级串行、命令、提交与恢复边界
  └─ src/Ecs：World/Fiber 分片、组件、行动管线与战斗规则
       ├─ src/Domain：POCO、配表、公式、聚合门面、编解码
       └─ vendor/YuoCore：固定版本 ECS/Fiber 内核
       ↓
PostgreSQL 18：身份、资产、市场、玩家分段、任务、回执及 outbox
       ↑
可选 ComputeNode：主动拨入主服，使用相同 ECS 规则做冷补算
```

- `.csproj` 引用方向与主要分层约束相符：Domain 不反向引用宿主或 Protocol；Ecs 不依赖数据库；ComputeNode 引用 Domain/Ecs，不直接引用 Server 或 Npgsql。
- `src/Server/Clean/**` 实际由 `src/Server.Clean/Server.Clean.csproj` 链接编译，`src/Server` 显式排除该目录。阅读源码时不能把目录名直接等同于程序集边界。
- 运行态权威在 ECS 组件。`EcsWorldShard.MutatePlayer` 使用 `PlayerAggregate.Wrap` 包装组件持有的同一份分段与队列，形成短命命令视图；当前不是每个命令先全量序列化再重建聚合。
- 生产宿主确实装配 `EcsGameRuntime` 与 `EcsPlayerRuntimeAdapter`，不是仅保留 ECS 实验目录。
- `Game.slnx` 包含 9 个主仓功能/工具项目、3 个测试项目以及 3 个 YuoCore 项目。
- 当前代码常量：数据库 schema `56`、玩家分段载荷 `43`、客户端最低可读载荷地板 `41`。这不是对远端数据库版本的核验。

## 三、核心链路与一致性设计

### 1. 玩家命令

HTTP/WS 鉴权 → 命令入口 → 玩家级 `SemaphoreSlim` → ECS 分片所有权/Fiber → 领域校验及规则变更 → 按脏分段和资产副作用提交 → 回执、快照/增量及日志推送。

关键证据：

- 玩家级 gate 与分片 owner gate 分别处理跨边界和 ECS 内部单写者约束；玩家运行时另有数据库所有权租约保护。
- `CommitPlayerAssetsAsync` 将资产变更、关联 section 与命令回执绑定为同一经济事务请求。
- 提交结局未知时使用原事务身份重放核实；仍未知时保留 fenced 状态和错误证据，拒绝继续写入，而非盲目回滚后继续结算。
- `CommitSimulationAsync` 在提交成功之后才生成并发布对应成功日志。
- section 队列实际采用追加式 INSERT，后台按租约认领，旧版本由版本守卫收敛为最新持久化状态；不能将其描述为“队列中同一玩家/分段永远只有一行”。

### 2. 在线、离线与补算

产品采用在线、离线挂机、彻底离线三态。当前默认断线宽限 5 分钟、离线收益上限 48 小时；离线批次目标受收益截止点约束，上线时由主服补齐尚未结算的时间。

计算节点只有候选结果权：冻结源状态与钱包 → 节点使用共享 ECS 规则推进 → 主服独立 ECS 重演 → 比较版本、时钟、section 字节和资产增量 → 事务内复核租约、源基线、钱包版本与 CAS → 原子提交结果及任务完成。

可信验证是明确优势，但节点侧模拟之后，主服仍完整重演。节点数量增加不等于主服计算成本同比下降；净收益必须结合真实业务、网络和主服重演成本测量。

### 3. 前端状态同步

- `gameClient.ts` 管理同源连接、心跳、请求超时、会话世代、有限次数指数退避重连与入站串行解码。
- Zustand 分离游戏、UI、市场、社交、邮件、宗门等状态；服务端快照/增量是游戏状态来源。
- 共享 `ItemTile`、`ItemIcon`、`FloatingPopover`、`Modal` 等组件形成统一展示体系。
- 非首屏页面已有 lazy 拆包，模拟器通过 Worker 执行，避免将沙盒计算直接塞入主界面线程。
- WS 服务端已有有界下行队列、推送基线保护与慢消费者关闭语义。

## 四、已具备的工程基础

1. **持久化一致性意识较强**：资产与普通状态区分，市场使用租约/fence，幂等回执、提交未知隔离和冷补算 CAS 均有明确实现入口。
2. **在线与冷补算共享 ECS 实现**：ComputeNode 和主服重演复用 `DeterministicCatchUpEngine`/`EcsWorldShard`，不各自维护一套冷挂机算法。
3. **测试故障面分层**：Domain/Ecs/Server 三套 xUnit，真实 PostgreSQL 集成测试，前端 `node:test`、协议契约与模拟器黄金样例，以及独立容量和烟测入口。确认的是这些设施存在，本轮未执行测试。
4. **门禁防止假绿**：`verify.sh` 对 xUnit TRX 的实际执行数设下限，避免零匹配被当作成功；快速口径与全量口径有区分。
5. **生产隔离已有基础**：多阶段镜像、非 root、Compose 只读根文件系统、回环端口、不可变镜像与备份/烟测脚本都已提供；本轮未验证容器或线上运行效果。
