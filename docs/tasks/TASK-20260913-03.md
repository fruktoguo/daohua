### 二、图标注册表扩展（`frontend/src/game/itemIcons.ts`）

原实现只 glob `../assets/items/*.png`，且用 `slice(0, -'.png'.length)` 硬切后缀。改为：

- 分别 glob `*.png` 与 `*.webp`，抽出 `registerIconModules()` 统一按 `replace(/\.(png|webp)$/i, '')` 去后缀登记；
- 先后登记，**同名时 `.webp` 优先**（运行时资源覆盖历史图片）；
- 注释同步说明该注册表现在覆盖「物品/材料、装备、功法战技」三类资源 ID。

物品与装备的 ID 本来就作为 `itemId` 流经既有展示位（背包、市场、装备面板、日志引用、气泡标题），
扩展后**自动生效**，无需逐个改组件。

### 三、战技图标显式接线（战技是唯一例外）

战技面板走的是 `ability.name` 而非 `itemId`，不接线的话这 10 张 WebP 就是死文件。接入 4 处：

| 位置 | 处理 |

| `AbilitiesPanel.tsx` 装配槽瓦片 | `resolveItemIconUrl(ability.abilityId)` 命中时渲染 `.item-tile-icon` 整块替换文本，未命中保持 `<strong class="item-tile-name">` |

| `AbilityGridPicker.tsx` 网格瓦片 | 同装配槽写法 |
| `App.tsx` 战斗面板战技槽位 | 同装配槽写法（与 AbilitiesPanel 平行的另一套渲染路径） |

全部沿用既有 `.item-tile-icon` / `ItemIcon` 模板，未新增任何样式类。

### 四、构建配置修正（`frontend/vite.config.ts`）

**这是本次唯一一处非预期的必要改动。** 首次构建后发现：`dist/assets/*.webp` 只有 6 个文件，
但注册表里有 64 个 `.webp` 键 —— 说明 **58 张因小于 Vite 默认的 4KB 内联阈值被压成 base64 塞进入口 JS**。

影响可量化：入口 `index.js` 572.21 kB（gzip 260.81 kB），其中约 240KB 是这 64 张图标的 base64。
而注册表是 **eager 全量引用**，这意味着**入口体积会随图标数量线性膨胀**（本项目图标最终会有数百张），
且这些字节无法被浏览器单独缓存。

修正：给 `build.assetsInlineLimit` 传入函数，`assets/items/` 下的资源返回 `false`（禁止内联），
其余资源保持 Vite 默认行为。

## 五、切图规格与 ID 映射固化（`art/sheets.json` / `art/icon_ids.json`）

### 为什么要固化

原切图规格（各图集的行列数、取图数量、名称顺序）当时是临时文件，已随 `/tmp` 清理。
不固化的后果是**无法换尺寸、无法复现**——只能永远沿用当时那批产物。

现固化两份文件到 `art/`（与母版同处，随 Git 走）：

| 文件 | 内容 |
| --- | --- |
| `art/sheets.json` | 三张图集的 `src` / `cols` / `rows` / `limit` / `names`（共 64 个名称，按左上→右下顺序） |
| `art/icon_ids.json` | 中文名 → 资源 ID 映射（64 条，按图集分组），由配表 `name` 字段匹配得出 |

**可复现性已实测**：用 `art/sheets.json` 重跑切图脚本（`--pad 8 --master-size 256`），
产出的 64 张母版与现有 `art/master_256/**` **逐字节一致**（`cmp` 64 相同 / 0 不一致 / 0 缺失）。
因此母版与网页版都可由该规格完全重建；中间产物目录 `art/_build/` 已加入 `.gitignore`。

### 一个真实的映射歧义（已判定）

按全量配表（18 个 json）匹配中文名时出现 **34 处歧义**：

```text
百炼铁 → craft.refine-iron（配方） | item.refined-iron（物品）
青锋剑 → forge.qingfeng-sword（配方） | equipment.qingfeng-sword（装备）
```

来源是 `config/game-data/actions/{crafting,forging}.json`——那里的 `id` 是**配方（动作）**，
其 `outputs` 指向真正的实体，而**配方名与产物名相同**，于是中文名撞车。

**判定：图标只归属实体（`item.*` / `equipment.*` / `ability.*` / `currency.*`），不归属配方。**
依据是配方面板的取 ID 方式：

- `frontend/src/App.tsx:1096` `primaryOutputId = Object.keys(action.outputs)[0]`，
  再以实体 ID 传入 `<ItemTooltipTarget itemId={primaryOutputId}>`（`:1117`）；
- `ActionDetailItem`（`:1135`）与 `CombatArena.tsx:789` 同样以 `outputs` 的实体 ID 渲染。

即配方卡片本身显示文本名，产物图标由 `outputs` 桥接到实体 ID 取得 —— **接入无遗漏**。
排除 `actions/` 后：**64/64 唯一命中、0 未命中、0 歧义、资源 ID 全部唯一**：

| 前缀 | 数量 |
| --- | ---: |
| `equipment.` | 28 |
| `item.` | 25 |
| `ability.` | 10 |
| `currency.` | 1 |

（第一节的「64/64 唯一命中」是在 5 张实体配表内匹配的结果，结论不变；此处补齐了全量扫描下的歧义判定依据。）

### 起因

### 实际绘制尺寸（真实浏览器实测，非推算）

在 DPR2 下用本机 Edge 读取计算样式，链路上限依次收窄：

| 环节 | 数值 | 来源 |
| --- | --- | --- |
| 瓦片 `.item-tile` | 64×64 | `--item-tile-size: 64px`（`selection-grid.css:3`） |
| 图标包含块 | 62×62 | `.item-tile-icon` 绝对定位，`width/height:100%` 解析的是**定位祖先的 padding box**（64 − 2×1px 边框） |
| **图标内容盒（真正绘制区）** | **52×52** | 再减 `.item-tile-icon` 自身 `padding: 5px` ×2（`selection-grid.css:316`） |

浏览器实测：`img` 的 `getBoundingClientRect()` = 62×62，`computedStyle.width` = 62px，内容盒 52×52。
因此在 52 CSS px 的绘制区上：32px 源被放大 **1.625×**（DPR2 需要 104 物理像素 → 放大 **3.25×**）。

### 导出路线的取舍（实测）

换尺寸有两条路线，都从 `art/` 出发：

| 路线 | 源 | 说明 |
| --- | --- | --- |
| **A（采用）** | 原图集全分辨率方格（~380–396px）→ 直接降采样 | 切片脚本 `--web-size` 的默认路径，只经过一次重采样 |
| B（弃用） | 256 母版 → 降采样 | 母版 256 本身由 ~380px 上采样而来，等于 380→256→N 往返，多一道重采样 |

同一目标尺寸下 64 张逐张对比：**可见像素 RGB 中位 38.36 dB、最小 35.13 dB；整图中位 33.20 dB**；
体积 76.2 KB vs 76.1 KB。视觉差异难以察觉，但 A 的采样链路更短，故**运行时资源统一改由 A 产出**。

### 一并统一：26 张 128px 遗留图标

目录里另有一批 TASK-20260911-02 产出的图标（丹药 / 秘籍 / 战技残页，`item.*` 前缀），
尺寸为长边 128px 的非正方形（宽 100–128），合计 167.2 KB。定稿 32 后它们与新一批会明显不一致
（背包里同屏：新图标糊、旧图标清），故一并统一。

- **这 26 张的原图已不在本机，它们就是唯一存留的高分辨率副本**，因此先归档再转换：
  `art/legacy_128/<资源ID>.png`（26 张，与源文件 `cmp` 逐字节校验一致）。
- 转换方式：先按**长边**补成正方形（内容居中），再 LANCZOS 缩到 32×32 ——
  这与原先 CSS `object-fit: contain` 的渲染等价（内容占满长边，透明部分不参与视觉）。
  源图内容本身贴边（贴边距离 0px），补正方形不会裁到内容（已断言内容包围盒未超界）。
