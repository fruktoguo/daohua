# TASK-20260920-03 · 日志分组重构与聊天（传音）系统全量落地

- 提出时间：2026-09-20 00:14:34
- 状态：🚀 进行中
- 设计真源：[docs/design/传音频道与日志分组.md](../design/总纲/14-传音频道与日志分组.md)

## 需求

用户要求把游戏内日志拆分为 8 个分组：综合、世界、附近、系统、战斗、好友、宗门、队伍。

- **综合**：显示 系统、好友、队伍 三个分组；
- **系统**：消耗品使用、任务/行动相关日志、各类系统通知；
- 确认口径：
  - 聊天系统全量落地（世界、附近、好友、队伍真实可用），**宗门仅保留占位符**；
  - 聊天记录**落 PostgreSQL**，每频道作用域保留最近 **100 条**；
  - 现有系统日志中 `action.completed`、`world.arrived`、`offline.capped`、`duel.*` 全部归入**系统**分组，战斗分组只放 `combat.*` 战斗过程。

## 设计取舍

- 聊天与社交不进入玩家聚合，由独立单例运行时处理，避免跨玩家写者锁互相阻塞。
- 宗门频道只保留 Tab 与占位提示，不建表、不建协议分支。
- 不设计任何历史兼容：旧快照/旧 schema/旧协议字段直接废弃。

## 追加：schema v4 落地与本地迁移入口（2026-09-20）

用户反馈「数据库怎么没有自动迁移」——这是**刻意设计**而非缺陷：`PostgresSchemaBootstrap.EnsureAsync` 的顺序是先校验 `platform.schema_version`、再跑 `IF NOT EXISTS` DDL（注释原文「已有库必须先通过版本门禁，避免 IF NOT EXISTS 把旧表误标为当前结构」），`Storage:EnableSchemaBootstrap=true` 的语义只是「空库直建 + 版本校验」，不是 migration runner；`AGENTS.md` §3 亦明确禁止代码内 migration runner 与对 `migrations/` 的运行时依赖。

处理：

1. **本地 `daohua` 库就地升级到 v4**：执行 `migrations/0003_v3_to_v4.sql`（纯加性 DDL），`platform.schema_version` 由 {2,3} 变为 {2,3,4}，新增 `social` schema 六张表；既有 41 个账号与 41 个玩家存档完好保留。启动复验：日志输出 `PostgreSQL schema v4 已就绪。`，`/healthz` 与 `/readyz` 均 200，`/api/v1/meta` 返回 `schemaVersion: 4`。
2. **新增 `scripts/migrate-local-db.sh`**（人工显式调用的本地库迁移入口）：
   - 读取 `platform.schema_version`，按 `NNNN_vX_to_vY.sql` 序号**链式**执行落后的迁移脚本（v2 库会自动连做 0002 → 0003）；
   - `--dry-run` 空跑；空库（无 `platform.schema_version`）直接提示走启动直建；版本表为空时报明确错误；
   - 结束时与 `PostgresSchema.Version` 对账，落后且无脚本可用时以非零退出码告警；
   - 仅由人工调用：`verify.sh`、服务端启动门禁与任何运行时装配都不引用它，符合「`migrations/` 可整体删除」约束。
3. **文档登记**：`AGENTS.md` §5 脚本清单新增该脚本；`migrations/README.md` 新增「本地库升级入口」；`docs/ops/deployment.md` 本地升级段落改指向该脚本。

验证：`bash -n` 语法通过；`--help` / 未知参数 / `--dry-run` 行为正确；在临时库上分别模拟 **v4（无需迁移）**、**v3（应用 0003）**、**v2（链式 0002→0003）** 三种起始状态，均正确收敛到 v4 并通过版本对账。
