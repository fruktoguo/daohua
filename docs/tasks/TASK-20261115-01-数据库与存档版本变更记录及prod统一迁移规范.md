## 1. 需求背景与核心边界

此前开发规范要求每次数据库或存档改动都在 `migrations/NNNN_vX_to_vY.sql` 手写过渡脚本，导致日常开发负担重、碎片脚本多，且一旦遗漏脚本或涉及跨多版本合并与配表删项，正式服发布时仍需对照 `git diff` 临时反推。

经与用户对齐，确立以下三项核心规则改造：

1. **取消日常强制手写迁移 SQL**：日常开发涉及数据库、存档或破档配表改动时，不再要求手写单次 `migrations/*.sql`（SQL 留待正式发布时按版本区间统一合并编写或手动执行）；本地开发遇库版本/存档标签漂移仍按兼容清零原则，优先执行已有链式脚本、缺失时由 `scripts/reset-outdated-players.sh` 交互确认 `RESET` 重置玩家域数据。
2. **单一滚动版本变更总台账**：新增 [`docs/backend/db-version-changes.md`](../backend/db-version-changes.md)，按 `## vX -> vY` 顺序滚动追加每一次变更记录；每条强制包含：**① 变了什么**、**② 是否需要处理存量数据**、**③ 如果需要怎么处理**。文档以当前线上 `v0.3.6`（`yuohira` 数据库 `v54` / 存档 `v43`）与代码 `v55`（`TASK-20261114-24` `is_bot` 标记）为起始锚点初始化。
3. **强制纳入全部破档变更范围**：凡涉及以下任一改动，均必须推进 `PostgresSchema.Version`（存档载荷变化同步推进 `SectionCodec.CurrentSchemaVersion`，仅破坏性变更才抬高 `MinReadableSchemaVersion`）并强制登记至上述总台账：
   - PostgreSQL DDL、索引、约束与角色权限（`PostgresSchema.Sql` / `postgres-local-roles.sql`）；
   - 玩家八分段及持久化 JSON/检查点结构与语义（`SectionCodec` / 队列 / 会话检查点）；
   - `config/game-data/**` 中删除或重命名 ID、修改持久化字段单位等会导致存量存档加载抛 `DomainException` 或错解的配表变更。
4. **`prod-release` 按变更账统一迁移或人工迁移**：更新 [`.agents/skills/prod-release/SKILL.md`](../../.agents/skills/prod-release/SKILL.md)，阶段 0 查明线上运行版本 `v_prod` 与代码目标 `v_target` 后，必须通读 `db-version-changes.md` 的 `[v_prod -> ... -> v_target]` 全部条目并交叉对账 `git diff`，在镜像构建前确定走**路线 A（统一编写 `[covered_ver -> target_ver]` 合并 SQL 并提交后再发布）**或**路线 B（分步构建备份并在阶段 2.5 停写窗口手工执行 SQL / `.mjs` 脚本后走 `deploy-prod.sh`）**。
