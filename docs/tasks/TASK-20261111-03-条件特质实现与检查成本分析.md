## 实现链路与确定结论

1. `PlayerProgression.UnlockedTraits` 是解锁及等级记录，`TraitIds` 是 `SetTraits` 设置的激活集合；部分旧注释将后者写为「已解锁」，应以实际装配行为区分。
2. `PlayerAttributeResolver.Resolve` 只将激活 ID 复制到 `CombatantStats.Traits`，等级记录独立传入 `TraitLevels`。仅解锁或仅持有等级不代表效果激活。
3. 特质定义及机制映射集中硬编码在 `src/Domain/Combat/CombatTraitRules.cs`，当前不是 JSON 条件表达式求值器，也不是每个特质一套 ECS System。
4. `RefreshConditionalBuffs` 先统计双方存活人数，再遍历双方全体单位，每个单位固定调用「我要打十个」「单挑王」两项更新。统计含存活召唤物，没有排除 `IsSummon`；倒地待复活者不计存活。
5. 「我要打十个」层数为 `max(0, 对方存活数 - 1)`；「单挑王」要求己方和对方各存活 1 人，且持有者自身存活、已激活该特质。1 级四通道各 +20 点，正向数值乘 `1 + 0.05 × (等级 - 1)`。
6. 条件成立时写入战内 Buff，免伤、总增伤、暴击伤害、行动速度复用既有数值通道。条件失效移除对应 Buff；存量层数及点数相同则不重写，避免不必要的聚合缓存失效。已起手动作不重排。

### 未装备者实际成本

- 仍会计算人数条件并进入两项 Update；对存活单位用 `ContainsTrait` 线性查激活 ID。
- 即使没有特质或资格检查失败，仍分别执行两个 `Buffs.FirstOrDefault`，检查是否有旧条件 Buff 需要清除。
- 普通未装备者不会创建 Buff、计算等级数值、写入新效果或因为这两项检查失效属性缓存；如果确有旧条件 Buff，则会在刷新时移除。
- 每次全场刷新成本可表为 `O(N × (T + B))`（N 为参战单位数，T/B 为平均激活特质与 Buff 数）；是源码复杂度估算，未测量 CPU、分配量或容量影响。
- 不是扫描全服全部注册账号，也不是循环全特质注册表；范围是正在刷新的一场遭遇。

### 条件刷新时机

| 入口 | 位置与行为 |
| --- | --- |
| 开战创建 | `CombatModels.cs` 的 `CreateAllied` 在开战特质授予后刷新 |
| 首次动作决策 | `CombatActSystem.DecideInitialActions` 再次刷新；常见 Start 路径会执行两次全场刷新 |
| 恢复 | `RestoreAllied` 先经 `CreateAllied`，应用真实快照后再刷新 |
| 伤害致死 | `CombatDamageSettlement.Apply` 在实际扣血导致阵亡后立即刷新；普通未致死伤害不触发此刷新 |
| 周期回复改变存活 | `CombatBuffTickSystem.Apply` 在 Tick 前后存活状态改变时刷新 |
| 复活 | `CombatAllyRespawnSystem.Apply` 显式刷新，随后 `DecideInitialActions` 再刷新 |

因此人数条件不是逐帧、每包、每次普通攻击或每个周期 tick 无条件重查；连续刷新是已有入口重复，不能直接推断为已测得的性能瓶颈。

### 其他机制特质的差异

| 类型 | 实际入口及未激活者行为 |
| --- | --- |
| 纯属性特质 | 属性解析只遍历激活集合，随输入修订缓存，不在每次命中枚举全部特质 |
| 初见、看不到我、欲速则不达的开战 Buff | 开战时每单位做固定 ID 检查，仅激活者授予 Buff |
| 力微饭否 | 属性解析折为 `CombatEffectProfile.ThreatOnTakenPoints`；实体派发由能力标记筛选 |
| 蓄意、燃魂的命中反应 | 实体路径仅给持有任一特质的单位挂 `TraitReactionComponent`，共享处理器内部再分辨具体特质；内联路径遍历全局强类型处理器数组，各处理器内部退出 |
| 欲速留一、蓄意受伤积累 | 共享最终扣血入口仍有条件短路后的 ID 判断，不完全受命中能力标记保护 |
| 燃魂持续伤害 | 周期结算遍历目标 Buff；目标无需自己装备燃魂，因为它是受伤状态 |
