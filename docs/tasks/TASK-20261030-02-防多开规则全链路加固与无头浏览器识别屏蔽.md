# TASK-20261030-02 防多开规则全链路加固与无头浏览器识别屏蔽

## 1. 任务背景与核心目标

在 2026-10-30 生产环境「神」倒金洗钱事件排查中，确认了小号绕过防多开与注册风控的三大根因：
1. **空 Cookie 自动派发全新 UUID 漏洞**：无痕模式或清理 Cookie 下，服务端因缺少 `daohua.device` Cookie 而无脑调用 `Guid.NewGuid()` 分配新设备标识，导致 `MaxAccountsPerDevice = 1` 与 `MaxAccountsPerPerson = 2` 的硬限制彻底失效；
2. **软风险评分与速度限制阈值偏宽**：同 IP（20分）+ 同网段（15分）仅 35 分，远低于默认 80 分拒绝门槛；频次限制（1小时10次）易被卡点规避；
3. **缺乏对自动化环境与无头浏览器（Headless Browser）的主动识别与阻断**：脚本可无成本调用 Puppeteer / Playwright 驱动无头 Chrome 进行批量操作。

**核心目标**：
1. 彻底实现对无头浏览器与自动化脚本环境的主动识别与强力屏蔽；
2. 修复空 Cookie 设备标识派发漏洞，将稳定硬件/浏览器指纹与主体硬限制强绑定；
3. 收紧风控评分权重与频次门槛，杜绝卡点绕过；
4. 保证正常物理设备/真人玩家体验不受误伤。

## 2. 详细技术方案设计

### 2.1 无头浏览器识别与屏蔽维度（前端探针 + 服务端校验）

```
                  ┌────────────────────────────────────────┐
                  │          无头浏览器多维识别矩阵          │
                  └────────────────────────────────────────┘
                                      │
         ┌────────────────────────────┴────────────────────────────┐
         ▼                                                         ▼
   【前端特征探针】                                          【服务端协议校验】
   1. navigator.webdriver === true                           1. UA / Sec-CH-UA 含 HeadlessChrome
   2. 软件光栅化渲染器: SwiftShader / llvmpipe / Mesa       2. 缺少必要标准请求头 (Sec-Fetch-*)
   3. 插件列表: navigator.plugins.length === 0               3. 客户端自报自动化特征被拦截
   4. 语言特征: navigator.languages 为空或异常
   5. 注入变量: window.__nightmare / __webdriver 等
```

1. **前端识别维度**：
   - `navigator.webdriver === true`：直接标识被自动化工具控制；
   - **WebGL 软件光栅化识别**：无物理 GPU 的无头环境通常使用 `Google SwiftShader`、`llvmpipe`、`Mesa OffScreen`、`VirtualBox` 等虚拟/软件渲染器，真实玩家设备均为硬件 GPU（NVIDIA / AMD / Intel / Apple / Adreno / Mali）；
   - **插件列表与特性**：正常 Chrome/Edge/Firefox 的 `navigator.plugins.length > 0`（含内置 PDF 插件等），无头浏览器此数组通常为空；
   - **已知自动化变量扫描**：探测 `window.__nightmare`、`window._phantom`、`window.callPhantom`、`window.__selenium_unwrapped` 等注入对象；
   - 处置方式：前端在采集信号时标记 `isAutomated: true`，并在注册/登录请求中携带。一旦判定为自动化环境，服务端直接拒绝（返回 `HEADLESS_BROWSER_BLOCKED`），或前端直接阻断。

2. **服务端兜底拦截**：
   - 检查 `User-Agent` 与客户端 Hints（`Sec-CH-UA`）：若包含 `HeadlessChrome` 或无头标识，直接拒绝；
   - 校验必须携带的客户端特征摘要：对于纯 curl/脚本伪造请求，缺少有效浏览器特征直接拦截。

### 2.2 设备锚点与主体硬限制加固（修复无痕窗口绕过漏洞）

1. **消除无脑生成全新 UUID 逻辑**：
   - 当前逻辑：`if (!deviceId.HasValue && client?.DeviceId is not null) deviceId = Guid.NewGuid();`
   - 加固逻辑：
     - 若未携带签名 Cookie，**禁止凭空生成全新未关联的设备 ID**；
     - 必须以客户端提交的稳定物理指纹（`DeviceConfigHash` 与私有 `BrowserFingerprint`）计算设备确定性键：`fingerprint:{BrowserFingerprint ?? DeviceConfigHash}`；
     - 服务端主体键 `PersonKey` 改为优先基于稳定设备指纹，即使开无痕窗口，同一设备的指纹相同，推导出的 `PersonKey` 必然相同；
     - 当同一个物理指纹注册账号达到 `MaxAccountsPerPerson = 2` 时，直接触发硬限制拒绝（`PERSON_ACCOUNT_LIMIT`）。

### 2.3 软风险评分与频次策略优化

1. **同 IP 关联账号权重**：由 20 分提升至 40 分；
2. **同设备配置/指纹关联权重**：由 10~45 分提升至 40~50 分；
3. **同 IP + 同指纹组合封杀**：40 + 40 = 80 分，刚好触发 80 分拒绝线（`deny`），单 IP 换号直接拦截；
4. **注册频次限制（registrationVelocity）**：
   - 触发阈值从「同 IP 1 小时内 10 次」下调至「同 IP 1 小时内 3 次」；
   - 权重保持 80 分，同 IP 批量注册第 4 个号起直接 80 分秒拒。
