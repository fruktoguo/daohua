# TASK-20261022-01 坊市同一标的单笔挂单约束

## 1. 任务背景与核心诉求

用户提出坊市规则优化：**同一个物品，只能出售或者求购，不能又买又卖，也不能挂多个同一个物品的单子。**

拆解为两条硬约束（同一交易标的维度 = `itemId` + 强化变体，如 `equipment.qingfeng-sword:+3`）：

1. **方向互斥**：同一玩家在同一标的上不得同时存在卖单与买单。
2. **单笔唯一**：同一玩家在同一标的上不得存在两笔及以上活动挂单（含同向多单）。

现状（改造前）：领域 `OrderBook.Place` 只做参数校验与自成交防护，同一属主可在同一标的上无限叠加买卖单；运维系统货架与压测脚本也依赖这一宽松语义。本次将规则落到服务端权威层，客户端仅做前置提示，避免玩家提交后才被拒。

### 1.1 口径边界（明确不做）

- **不做跨变体约束**：+0 与 +3 是两本独立订单簿、钱包按变体行冻结互不挤占（`docs/backend/domain-data-architecture.md` §5.2），因此允许同一玩家基础件与强化件各挂一笔。
- **不做跨标的约束**：不同 `itemId` 之间无任何限制。
- **不做历史数据迁移**：当前为本地开发阶段（AGENTS.md §3 兼容清零）。存量库里若已有「同玩家同标的多笔活动单」，规则在下次挂单时生效（拒绝新增），既有单照常撮合/撤单/到期，不需清库或翻库。本地实测当前库无此形态（`GROUP BY owner,asset,variant HAVING count(*) > 1` 为空）。
- **运维系统身份（系统坊市）也在规则内**：系统货架每标的本就只有一笔卖单；运维面板重复下单时，服务端先撤销该系统身份在该标的的既有活动单再挂新单，保持「面板点一次 = 货架一个价位」的可预期语义。

## 2. 技术设计方案

### 2.1 领域层（`src/Domain/Market/OrderBook.cs`）

- 新增属主索引 `Dictionary<PlayerId, HashSet<OrderId>> _ownerIndex`，只在 `AddIndexes`/`RemoveIndexes`/`RebuildIndexes` 三处维护，与既有卖档/买档/到期索引同构（活动单才登记，终态自动摘除）。
- `Place(request, journal)` 在任何写入前校验：若属主在该簿已有活动单 → 抛 `DomainException(DomainErrorCode.OwnerOrderExists, …)`（新增错误码，追加在枚举末尾不改既有取值）。方向互斥由「每标的最多一笔」自然覆盖（一笔不可能同时是买和卖）。
- 幂等前置返回（`MarketRuntime` 查 `book.TryGet(orderId)` 命中）发生在 `Place` 之前，重放既有 `OrderId` 不会误触新校验。

### 2.2 运行时层（`src/Server/Clean/MarketRuntime.cs`）

- `PlaceCoreAsync` 在既有 `DomainException` 通道上透出新错误码；不新增降级分支（属业务拒绝，走 `IsExpectedRequestFailure` 的 `MarketException` 路径）。
- 新增 `GetActiveOrder(PlayerId ownerId, MarketInstrument instrument)`：返回该玩家在该标的的活动单（无则 null），供运维下单与前端接口复用。

### 2.3 运维（`src/Server/Clean/Ops/OpsMarketActions.cs`）

- `PlaceSystemOrderAsync` 在注入资金与 `PlaceAsync` 之前，先取系统身份在该标的的活动单并 `CancelAsync` 撤掉，保证批量挂售/收购重复执行时只替换不叠加。

### 2.4 协议与前端

- 不新增协议字段：拒绝原因复用既有 `CommandResult` 失败码 + 中文提示文案。
- `MarketPage` 从既有「我的订单」轮询结果派生「当前标的 + 当前强化等级是否已有活动单」，透传到 `MarketOrderModal`：
  - 已有活动单 → 提交按钮禁用，摘要区显式提示「该标的已有活动单（出售/求购 X 份），请先到「我的订单」撤销后再挂单」。
  - 入口级提示：盘口详情/强化等级行的买卖按钮仍可打开弹窗（便于看清盘口），只拦截提交，避免玩家在不知道原因的情况下按钮失效。
- i18n 词条新增并同步 `frontend/public/locales/template.csv`。

## 6. 验证要点

1. 玩家 A 在 `item.x` 有卖单时再挂买单 → 拒绝，提示「该标的已有活动单」；再挂卖单亦拒绝。
2. 玩家 A 撤销该卖单后再挂买单 → 放行。
3. 玩家 A 在 `item.x` 有卖单时，去挂 `item.y` 或 `item.x:+3` → 放行（跨标的/跨变体不受限）。
4. 玩家 B 在 `item.x` 挂单 → 不影响玩家 A 的既有单，且与 A 正常撮合。
5. 服务重启（`RestoreBooks`）后，属主索引按活动单重建，同标的新增单依旧被拒。
6. 运维面板连续两次「系统挂售」同品种 → 货架只剩一笔（旧单被撤、新单价位生效）。
