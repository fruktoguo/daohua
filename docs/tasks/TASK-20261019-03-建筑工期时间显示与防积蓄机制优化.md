## 1. 核心需求与背景分析

用户反馈当前节点公共建筑（建造与升级）存在两项明显的体验与逻辑缺陷：
1. **工期缺少真实时间展示**：
   - 当前在地图附近面板的建筑小卡片上仅显示 `材料 X% · 工期 Y%`，在建筑详情弹窗的升级/建造面板中也仅显示 `工期 {percent}%` 和进度条，未显示工程实际需要多少总时间、已流逝多少有效工时、或还需多长时间。
   - 需求：在工期百分比后补充直观的真实时间（如 `已耗时 / 总时长`，例如 `5分0秒 / 10分0秒`）。
2. **工期停滞防积蓄机制（防止补料瞬间完工）**：
   - 原始规则设定：工期进度不能超过当前材料的百分比（如材料只交了 50%，工期最多推进到 50%）。
   - 现存 Bug：当工期受限于材料卡在 50% 之后，如果等待了很长时间（超过了剩余 50% 的工期时间），由于之前单纯使用 `StartedAtUnixSeconds` 记录最初开工时刻，墙钟流逝时间在后台持续“积蓄”；当玩家再次提交材料放开上限时，积蓄的时间一次性释放，导致建筑瞬间完工，而没有继续匀速赶工期。
   - 需求：工期**不能积蓄**。当工期达到材料上限时停工；提交新材料放宽上限后，工期应从当前停滞进度点重新起步持续增长，而不是把停工期间流逝的等待时间补算出来瞬间补全。

## 2. 技术设计方案

### 2.1 领域规则与防积蓄模型（Domain / Server）
- **有效已耗工时公式**：
  设工程目标等级为 $L_{\text{target}}$，总需工时为 $T_{\text{req}} = \text{RequiredBuildSeconds}(L_{\text{target}})$。
  当前材料比例为 $M = \text{MaterialFraction}(\text{state}, \text{definition})$。
  在材料上限约束下，工期允许推进的最大有效工时为 $M \times T_{\text{req}}$。
  实际从基准起始时刻流逝的时间为 $T_{\text{raw}} = \max(0, \text{now} - \text{state.StartedAtUnixSeconds})$。
  则当前时刻该工程的有效已耗工时为：
  $$T_{\text{effective}} = \min(T_{\text{raw}},\; M \times T_{\text{req}})$$
- **提交新材料时的基准起始时刻重锚定**：
  在玩家提交材料时（`NodeBuildingRegistry.ContributeCoreAsync` 行锁事务内）：
  1. 计算在提交时刻 $t_{\text{now}}$，按旧材料比例结算的有效已耗工时 $T_{\text{effective\_old}}$。
  2. 合并新提交的材料得到新的材料比例 $M_{\text{new}}$。
  3. 将建筑状态的基准起始时刻重置为：
     $$\text{StartedAtUnixSeconds}_{\text{new}} = t_{\text{now}} - T_{\text{effective\_old}}$$
  4. 效果：彻底裁减掉由于缺少材料而停工等待的无效墙钟时间；提交新材料后，工程从原停顿工时 $T_{\text{effective\_old}}$ 起步，以正常速率 $1\text{s}/\text{s}$ 向新材料上限 $M_{\text{new}} \times T_{\text{req}}$ 推进，彻底杜绝瞬间补全。
- **协议快照映射**：
  - `ProtocolSnapshotMapper` 中的 `elapsedSeconds` 统一取 `EffectiveElapsedSeconds`，保证卡住期间下发的已耗秒数封顶于材料秒数，绝不超出总工期。

### 2.2 前端工期时间展示与布局优化（Frontend）
- **详情弹窗（`NearbyPanel.tsx`）**：
  - 重构 `.building-progress-row`，改为上下结构或头部信息两端对齐：
    - 左侧展示 `工期 {percent}%`
    - 右侧展示具体时间（`<span className="underlined-value">{elapsed} / {total}</span>`，例如 `5分0秒 / 10分0秒`）
    - 下方承接满宽的进度条 `ProgressBar`
- **卡片缩略信息**：
  - 卡片进度信息在工期百分比后展示时间（如 `材料 50% · 工期 50% (5分0秒/10分0秒)`）。
- **国际化词条对齐**：
