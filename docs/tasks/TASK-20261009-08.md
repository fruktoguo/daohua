## 复评修复（2026-10-10 08:45 起，已随 fleet 进程重启生效）

长跑 8h+ 复核日志定位并修复四处 FleetScenario 缺陷：

1. **监控协程静默死亡**：`MonitorLoopAsync` 按 `is not OperationCanceledException` 过滤异常，但 HttpClient 10s 超时抛 `TaskCanceledException`（OCE 子类）——00:24 启动风暴期一次采样超时即杀掉监控循环（此后内部监控归零，靠外部 fleet-watch.sh 兜底）。改为仅 `cancellationToken.IsCancellationRequested` 时退出，其余异常照常落 anomaly。
2. **同类过滤缺陷扩散**：`RegisterAndConnectAsync`/`ReconnectAsync` 同样写法——单个注册或 WS 连接内部超时抛 OCE 会穿透 `Task.WhenAll` 掀翻整场仿真 / 永久杀死角色协程（与 373/500 在线缺口吻合）。统一改为「真取消才上抛，超时按失败记账退避重试」，并把 `RunForeverAsync` 整轮体包进 per-iteration try。
3. **`_partyMemberIds` HashSet 跨线程写坏**（05:53、07:51 日志实锤 `concurrent collections corrupted`）：接收线程 Clear/Add 与 tick 线程 Contains 竞争。改 `ConcurrentDictionary`；`_partySessionActive`/`_ws`/`_inExpectedParty` 补 volatile，会话计时改 `Interlocked` 读写的 unix-ms 长整型。
4. **`SOCIAL_TARGET_IN_PARTY` 语义修反**：原修复把目标直接补进本队名册——但服务端该错误表示「在**其他**队伍」，误标导致卡别队的成员永远等不到补邀请、本队凑不满 5 槽永不开战。改为只记 60s 节流；成员侧新增自愈——推送 party 的 `leaderId` 与编制队长不符时主动 `party.leave`（无确认才离队，防推送畸形误退本队），离队后下轮邀请自然落地。ready 门槛同步收紧为 `_inExpectedParty && 名册含自己`。

## 服务端快照增量丢帧永久漂移修复（2026-10-10 09:42 起生效）

**现象**：新一轮长跑约 55 个角色持续 `world.travel` 超时/落地超时，循环止步 445/500；但 DB 显示这些角色早已落在目标节点（world 段 22 分钟未变、action_queue 为空）——服务端状态正常，**客户端分段视图永久失同步**。

**根因**（`WebSocketRuntime.cs`）：SnapshotDelta 走 `TrySendDroppable` 可丢弃通道；出站队列拥塞丢帧时推送基线不前移，设计意图是「下一拍推送重投」。但静止态角色（落地后不再动）不会再产生 `SnapshotUpdated` 事件——**没有下一拍**，丢帧永不重投；慢消费者踢线阈值（32 连丢/15s 饱和）对单帧掉落不触发；后续命令回执的窄化 delta 只含触及段，world 段照抄陈旧基线校验和，同样救不回来。真实玩家弱网丢帧也会表现「角色永远在路上/属性不刷新直到重登」。

**修复**：会话新增 `DeltaResyncPending` 重投标记——增量入队失败置位；`SendLoopAsync` 每次发完检测通道排空（`Count==0`）即回调按 `_loaded` 当前快照**全段重编码 delta**（touched=null，校验和裁决全部漂移分段）补投，成功才解标记。窄化增量/回执提交基线不清标记（不覆盖被丢分段）；不能存旧帧重放——序号在建帧时分配，重放会因乱序被客户端丢弃。重连路径本就拉全量快照，不受影响。

**验证**：服务端 dev-hot 热重启（09:42）→ 500 客户端 ~25s 全部重连 → 重连快照使 55 个卡死角色视图恢复落地 → 3 分钟内全部完成 bootstrap，09:46 `loop=500 equipped=500` 满编；重连风暴后零新增异常，`errFrames` 稳定。补投机制已在生产服务端常驻，后续拥塞丢帧自动补投。

## section_flush_queue 并发改造 + 资产提交串行化（2026-10-10 16:10 生效，schema v27）

长跑稳定期持续 `40001` 告警（~25/min，堆栈落 `EnqueueInTransactionAsync`）+ 偶发 `40P01` 死锁 + `MarketRuntime` 领取告警（~66/30min）。排查后按冲突面拆三类根因分别修复：

1. **同玩家并发资产提交互撞**（`ExecCheckTupleVisible` 主力）：`PostgresEconomyRepository.CommitAsync` 增按玩家分桶的 128 条带锁——收集事务触及的全部玩家（Actor/Deltas/Sections/Receipts/ParticipationReceipt）映射条带、升序加锁覆盖整个重试循环。同玩家提交由「SSI 回退+重放」变为「进程内排队」，开销低一个量级；多玩家事务排序加锁无环。
2. **flush_queue upsert 共享行被写方/清理方争夺**（死锁+冲突的根源结构）：队列由 `(player_id, section_kind)` upsert 共享行改为**追加式收件箱**（`queue_id` 自增主键，v27 迁移）。入队纯 INSERT 不触碰既有行；worker 认领/删除按 queue_id 主键；同 (player,kind) 多行认领后仅最高版本应用、落选行并入胜者组同事务删除/归还；`player_state_sections` 应用侧 version 守卫兜底收敛。写入方与清理方从此不共享元组——SSI 无冲突可裁。
3. **市场结算领取谓词读撞成交插入**：`market.trades` 增 `(buyer_id, traded_at)`/`(seller_id, traded_at)` 复合索引（v26），claim 的 `(buyer OR seller)` 计数走 BitmapOr 双索引，SIREAD 范围从「成交表时间尾部」收窄到「本人成交页」，冲突概率降 ~500 倍；领取查询顺带加速。

配套：`SectionFlushBatchSize` 256→8192（追加式入队速率 ~21K/min 远超旧 upsert 合并形态，原批大小排空不动）；`FlushQueueItem` 增 `QueueId`；`ReleaseClaimsAsync`/认领 CTE/删除全部改按 `queue_id`。

**验证**：实例 #46 运行 7min+ 统计——`40001=0`、`40P01=0`、重试耗尽=0、连接池耗尽=0（对照：上一实例同窗口 ~170 条）；重连后 flushQ 10.8 万积压 ~5min 排空回 ~2.8K 稳态水位；`online=500 loop=500 equipped=500`；交易 ~135 笔/分钟；`errFrames` 全程冻结。剩余告警面只剩个位数/分钟的分区撮合固有 SSI 瞬态重试（attempt=1/3 内消化，正确语义）。

## 市场结算游标 + 分区单写者串行化（2026-10-10 16:37 生效，schema v28）

残余 `市场分片瞬态数据库错误`（~2-3/min）：领取按 trades 时间窗谓词计数，与同玩家并发成交插入的 SSI 谓词冲突——索引收窄后只剩同玩家维度，结构上消不掉。另随带发现并修复 dev-hot 监督进程自杀缺陷。

1. **结算领取改游标锁（v28）**：新增 `market.settlement_cursors`（每玩家一行 pending_count/settled_count）；`ApplyFillAsync` 成交落库成功即对买卖双方游标 upsert +1；`ClaimSettlementAsync` 先确保游标行存在再 `FOR UPDATE` 读 pending→清零累加 settled→插 claims 审计行。游标行锁与同玩家成交物理互斥，领取降级 ReadCommitted、SSI 表面归零；计数由「时间窗谓词推导」变「提交序游标累加」，晚提交的成交按提交顺序入账，语义更正确。迁移含回填（最近领取点之后的成交腿数）。
2. **市场分区写事务进程内串行**：分区本就是单写者语义（lease fence 保证单实例持有），但异步并发事务仍在分区内互撞订单行/SIREAD 订单簿。新增 `PartitionGates`（按 partitionId 的信号量字典），`CommitPlacementAsync`/`CloseOrderAsync`/`ExpireBatchAsync`/`AcquireLeaseAsync` 全部分区写路径先取分区闸再进事务——分区内部 SSI 竞争归零，吞吐仍 ≫200 单/秒·分区。
3. **玩家条带闸提取共享**：`CommitAsync` 的 128 条带玩家锁提为 `PlayerCommitGates`（经济仓储文件内 internal static），市场写路径按「分区闸→玩家条带→DB 锁」全局一致顺序复用——市场事务与经济事务在同玩家维度排队而非互撞（市场事务同样更新余额行）。
4. **dev-hot 崩溃拉起失效修复**（运维缺陷，实证）：`startServer` 的拉起 `setTimeout` 被 `.unref()`——服务子进程意外退出瞬间事件循环只剩 unref 句柄，监督进程静默退出，服务再未被拉起。去掉该 unref（文件内注释说明原因）。此前 46 次重启均为预期退出未触发；本次版本门禁 crash 第一次暴露。

**验证**：实例 #47（v28）运行 5min+——`40001=0`、`40P01=0`、市场瞬态错误=0、重试耗尽=0、池耗尽=0；claimed 1443 持续增长；`online=500 loop=500 equipped=500`、flushQ ~2K 稳态、trades ~150/min。剩余告警仅剩 `member-unready` 组队散场领域事件（业务语义日志，非故障）。
