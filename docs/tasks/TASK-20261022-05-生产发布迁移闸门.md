## 事故背景（2026-10-22）

线上并发两起独立故障，第二起源自发布流程缺口。

### 第一起：结局未知栅栏永久封锁（已由 `fc806910` 修复）

10:16:43 生产 PostgreSQL 崩溃重启（59 秒恢复）。玩家「东」当时有一笔资产事务正在 COMMIT，连接被切断后抛 `EconomyCommitOutcomeUnknownException`；精确重放核实也因数据库仍在恢复而失败，适配器把 `_fencedCommits[东]` 永久置位。该事务在 `economy.transactions` 中实际并不存在（已回滚），但栅栏只能靠进程重启内存清零解除——每次握手都抛异常、以 1011 关闭、前端指数退避重连，形成死循环。

修复：栅栏记录可精确重放的核实入口，装载/刷盘/卸载/批量推进前先做幂等核实；确认已提交则解除栅栏并丢弃陈旧内存状态从 durable 事实重建，仍不可达则继续 fail-closed。

### 第二起：迁移后旧容器写回旧存档标签（本任务）

| 时间 (UTC) | 事件 |

`SectionCodec.Decode` 对 `SchemaVersion` 做**严格相等**校验，v37 载荷一律被拒绝；`PostgresSchema.VerifyAsync` 只校验 `platform.schema_version`，**不校验分段标签**，所以启动门禁放行了不一致的数据。

## 根因

发布流程存在结构性缺口，而非某次操作失误：

1. `scripts/deploy-prod.sh` 与 `scripts/release-prod.sh` **完全没有迁移步骤**；迁移靠人工 `psql -f` 执行。
2. 人工迁移与容器替换之间没有停写约束：旧进程在迁移窗口内继续按旧标签写入。
3. 启动门禁只校验库版本，不校验存档标签，无法在启动时拦住这类不一致。
4. 库版本与存档标签版本是两个独立数字（v41 ↔ v38），此前文档与脚本都没有把这个区分写清。

## 方案

### 新增 `deploy/migrate-prod-db.sh`

强制顺序：**停写 → 备份 → 链式迁移 → 校验**。

| 步骤 | 行为 | 失败处理 |
| :--- | :--- | :--- |
| 写者校验 | 检查 `daohua-app` / `daohua-compute` 是否运行；运行时默认拒绝迁移 | 非零退出，不动库 |
| 全库备份 | `pg_dump -Fc` → `/opt/daohua/backups/pre-migration/`，写入 `latest` 指针 | 非零退出，不动库 |
| 链式迁移 | 按 `platform.schema_version` 依次应用 `migrations/` 落后脚本；涉资产退款的脚本拒绝自动执行 | 非零退出，脚本自带事务边界 |
| 版本对账 | `platform.schema_version` 必须等于 `EXPECTED_SCHEMA_VERSION` | 非零退出 |
| 标签校验 | `player_state_heads` / `player_state_sections` / `section_flush_queue` 的 `schema_version` **不得有任何一行**偏离 `EXPECTED_SECTION_VERSION` | 非零退出并打印修复 SQL |

`--dry-run` 仍执行只读校验，避免把「存在陈旧标签」误报为可部署。`--allow-running` 仅供排障。

### `scripts/deploy-prod.sh` 接入

- 从源码派生两个独立目标：
  - `EXPECTED_SCHEMA_VERSION` ← `PostgresSchema.Version`（当前 41）
  - `EXPECTED_SECTION_VERSION` ← `SectionCodec.CurrentSchemaVersion`（当前 38）
  任一无法派生即拒绝部署。
- 上传 `migrate-prod-db.sh` 并同步 `migrations/*.sql` 到 `/opt/daohua/migrations/`（该目录不进镜像）。
- 在 `ccr-auto-update.sh` 之前插入：停用自动更新 timer → 执行迁移闸门 → 再替换镜像。
