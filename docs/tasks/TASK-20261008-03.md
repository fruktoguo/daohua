## 实施结果

已完成的核心迁移：

- 组队不再制造 `party.expedition` 伪行动；社交层选择配表中的真实战斗行动并写入 `ActionParticipationSpec.ActionId`。
- 队列、聚合、ECS、讨伐执行、协议与前端战斗表现改用 `participation`；原行动实例保留在队列中，散场后按实例恢复。
- 到期参与会话在暂停判断前清理；装载补算前先按社交会话行收尾或补发，周期看门狗也扫描“活跃会话但缺绑定”的在线玩家。
- schema v21、迁移脚本、前端快照契约与单人/多人回归测试同步。

仍明确保留的当前讨伐策略：共享冻结剧本、成员独立推演、经验/掉落按既有规则分配。未来 Team/Guild 只需提供相同参与规格与组织裁决，不应进入讨伐执行器或 `CombatArena` 分支。

### 3. 建议的职责边界

```text
Party / Team / Guild
  └─ 组织成员、准入、准备、权限、人数和开战请求
       ↓ 创建一次参与会话
ActionParticipationSession
  └─ sessionId、实际 ActionId、参与者快照、参与序、开始/结束时刻、场景输入引用
       ↓ 提供通用 ActionParticipationContext
既有行动执行器
  └─ 讨伐只接收行动定义 + 参与者集合/观察者索引 + 冻结场景输入
       ↓
既有 CombatEncounterState / DeterministicCombatEngine / allies 投影
       ↓
独立 RewardAllocationPolicy
  └─ 当前先实现讨伐平分/掉落归属；未来按团队或宗门策略替换
```

建议的最小模型不是 `PartyExpeditionSpec` 泛化，而是拆成三块：

1. **通用参与会话**：只描述谁以什么顺序参与哪个实际行动、会话何时开始/结束，以及离线恢复所需的不可变输入引用。
2. **讨伐场景输入**：遭遇、种子、冻结战斗面板、盟友镜像和寻敌速度等只属于 Combat/Expedition 执行上下文；它不出现 Party、Team 或 Guild 类型。
3. **结算策略**：经验分配、掉落判定/归属、消耗品费用等作为会话策略或讨伐结算上下文，不放回组织记录。

行动队列仍可保持现有抢占、挂起、散场恢复和无限重复语义；改动点是把当前专用 `PartySession` 绑定替换为通用参与绑定，并让队列在暂停判断之前处理已到期的会话收尾。这样用户看到的行动卡、战斗阶段、盟友阵列和动画可以保持原样，来源从 Party 专用绑定改成通用参与上下文。

### 4. 团队/宗门的扩展判断

- **团队/宗门共同参加同一场讨伐**：应复用同一个 `ActionParticipationSession`；新增的只有组织准入、容量、准备和结算策略，讨伐执行器与 `CombatArena` 不应新增组织分支。
- **宗门累计任务**：不应伪装成一次多人同场行动。它通常汇总多个成员各自执行的行动结果，应该另建任务目标/贡献聚合，订阅行动结果；否则会把“共享战场”和“跨成员累计进度”混成一个状态模型。
