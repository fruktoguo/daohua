## 2. 缺陷清单（取证结论）

### 2.1 P0-1 `equal` 可编辑器选中但快照解码缺白名单（自锁断连循环）

- 服务端 `SkillTriggerEvaluator.ValidateTrigger` 接受 `"equal"`；前端 `CombatTriggerEditor` 数值与 Buff 两个分支的比较方式下拉都列出 `equal`。
- `frontend/src/network/snapshot.ts:942` 的 `enumValue` 白名单**漏了 `'equal'`**，`frontend/src/game/types.ts` 的 `CombatTriggerComparator` 联合类型同样缺失。
- `enumValue` 直接 `throw`（`snapshot.ts:893`） → `decodePlayerSnapshotDto` 抛 → `handleParseFailure` 逐级升级为 notice/resync/断开重连 → 重连后再收同快照 → 再抛。**无限自锁**。
- 违反 `AGENTS.md` §7「协议信封强对齐与往返门禁」。

### 2.2 P0-2 消耗品触发条件保存必然失败

- `frontend/src/App.tsx:1340` 的 `saveItemTriggers` 把消耗品条件写进 `abilityTriggers[itemId]`，经 `loadout.replace` 上送。
- 服务端 `src/Server/Clean/LoadoutCommand.cs:104` 校验键必须是**已习得功法**：
  `if (!player.Loadout.LearnedAbilities.Contains(new AbilityId(entry.Name))) throw …「功法未习得，无法配置触发条件。」`
- 四条消耗品求值路径（`ActionParticipationSessionEngine.cs:575/612`、`ActionExecutionRules.Resources.cs:351`、`CombatActionRules.cs:1458`）读的都是 `ConsumableDefinition.Triggers`（**配表**），无玩家侧覆盖通道。
- 结论：战斗栏条件 UI 当前为纯装饰，且点击保存会返回命令错误。

### 2.3 P1-1 Buff 选择器硬编码且 4/6 为幻影

`frontend/src/components/CombatTriggerEditor.tsx:320-327` 硬编码 6 项：

| 编辑器列出 | 配表实存 |
|---|---|
| `buff.zhixue` / `buff.shunqi` | ✅ `items/pills.json` |
| `buff.yinshen` | ⚠️ 仅由 `CombatTraitRules.UnseenBuffId` 常量注入 |
| `buff.qi-gathering` / `buff.spirit-tea` / `buff.fire-talisman` | ❌ 全仓无定义 |

配表实存但编辑器遗漏：`buff.ganlu`（`spell_abilities.json:148`）、`buff.sui-gang`（`physical_abilities.json:152`）。
新建 Buff 条件默认值恰为 `buff.qi-gathering`（`CombatTriggerEditor.tsx:219`）——**一加就是恒 0 层的死条件**。

### 2.4 P1-2 清空条件回退配表默认，无法表达「恒可用」

`LoadoutCommand.cs:106` 仅当 `triggers.Length > 0` 才写入 map；`CombatSkillState.cs:47` 仅当 `custom.Length > 0` 才覆盖。空数组被折叠为键缺失，`FromAbilitySlots` 回退 `defaultTriggers`。玩家**无法表达无条件恒施放**，与 `common-components.md` §22 与前端注释的「空表 = 恒可用」口径矛盾。

### 2.5 P2-1 集合条件（ally/enemy）服务端有、前端全无

服务端支持 `ally`/`enemy` + `alive-count`/`dead-count`（`SkillTriggerEvaluatorTests.cs:113` 覆盖）。前端三处白名单均缺：`types.ts` 的 `CombatTriggerDependency`、`snapshot.ts:940` dependency 解码、`snapshot.ts:941` condition 解码。配表一旦启用即整帧崩。

### 2.6 P2-2 `equal` 与浮点百分比互斥

服务端 `"equal" => value == threshold` 精确比较，百分比为 `hp/max*100` 浮点除；模拟器 `skillTriggerEvaluator.ts:84` 用 `1e-9` 容差——两边语义已漂移。

### 2.7 P2-3 `MAX_TRIGGERS=4` 三处不联动

`CombatTriggerEditor.tsx:9`、`LoadoutCommand.cs:115` 各写 4；`ValidateTrigger` 与配表 `defaultTriggers` 无上限。

### 2.8 P2-4 控制状态为死词表

`stun-status`/`blind-status`/`silence-status` 在 `ReadCondition` 恒返 0（`SkillTriggerEvaluator.cs:279` 自认预留），但校验器接受、类型存在、i18n 有文案。配 `is-active` 恒假。

## 3. 实现方案

### 3.1 领域层（`src/Domain`）

1. `SkillTriggerEvaluator` 新增 `MaxTriggersPerList = 4` 与 `EqualTolerance = 1e-6` 公开常量；`equal` 改为容差比较。
2. `ValidateTrigger` 增加条数上限校验；`buff-stacks` 的 `buffId` 校验改为**可选词表**参数（装载期传配表派生集合，命令期传当前配表集合）。
3. `PlayerLoadoutState` 新增 `ConsumableTriggers`（`VersionedDictionary<string, JsonElement[]>`，键为物品 ID），与 `AbilityTriggers` 同构；`PlayerLoadoutDocument` 增对应可缺省字段。
4. `FromAbilitySlots` 改为「键存在即覆盖」：键在 map 中（含空数组）一律覆盖，仅键缺失才回退 `defaultTriggers`。
5. 消耗品条件解析：`ConsumableDefinition.Triggers` 保持配表默认；玩家覆盖在四条消费路径上生效。

### 3.2 宿主与协议（`src/Server`、`src/Protocol`）

1. `LoadoutCommand` 接收 `consumableTriggers` map：键必须是配表中存在的消耗品（`catalog.Items` 存在且 `Category == consumable`），值走 `ReadTriggers` 同口径校验。
2. 消耗品条件随 `loadout` 分段下发（`ProtocolSnapshotMapper` 增 `consumableTriggers` 字段）。
3. 新增 `GET /api/v1/catalog/buffs`：从配表派生 Buff 词表（消耗品 `consumable.buffs[]`、功法 `buff.buffId` 或合成 `ability-buff:<id>`、行动产出 Buff、特质注入 Buff），下发 `{ buffId, name }` 列表。
4. `GET /api/v1/catalog/triggers` 返回 `{ maxTriggersPerList }` 常量，供前端契约门禁断言。

### 3.3 前端（`frontend/src`）

1. `types.ts`：`CombatTriggerComparator` 补 `'equal'`；`CombatTriggerDependency` 补 `'ally'`/`'enemy'`；`CombatTriggerCondition` 补 `'alive-count'`/`'dead-count'`。
2. `snapshot.ts`：`mapTriggers` 三处白名单同步补齐。
3. `CombatTriggerEditor`：
   - Buff 选项改为从 `catalog/buffs` 派生，默认值取词表首项；
   - 依赖下拉补「友方全体」「敌方全体」，选中集合对象时条件下拉切换为群体聚合词表、比较方式切换为数值比较；
   - 上限读 `catalog/triggers.maxTriggersPerList`。
4. `App.tsx`：消耗品条件读写从 `abilityTriggers[itemId]` 迁至 `consumableTriggers[itemId]` 独立通道；「清空全部」写入空数组而非删除键。
5. 模拟器 `skillTriggerEvaluator.ts`：`equal` 容差对齐服务端常量。

### 3.4 持久化

- `SectionCodec.CurrentSchemaVersion` 36 → 37，`PostgresSchema.Version` 39 → 40。
- 新增 `migrations/0040_v39_to_v40.sql`：仅推进 `platform.schema_version` 与存档标签（新增字段可缺省解码为 null）。
