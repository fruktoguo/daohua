# TASK-20261019-04 · 组队战斗消耗品实时库存与不断战自动续用方案

- 提出与登记时间：2026-10-19 17:24:26（本轮首次读取系统时间）
- 状态：完整实现中；方案完成：2026-10-19 18:51:14；实施开始：2026-10-19 19:47:22。
- 用户目标：在线组队按每名成员的实际战斗消耗品库存检查并扣除；缺少任一战斗消耗品只跳过该次使用，不中断战斗；战斗中买入同种战斗消耗品后自动接续，不要求散场、取消准备或重开。
- 本轮范围：完整实现全部战斗自动使用消耗品的在线真实库存、离线储备、交易顺序、持久化恢复和界面契约，并执行回归、门禁、真实烟测；不操作远端数据。

## 需求与范围

- 在线组队的全部战斗消耗型物品按单人真实库存语义执行：有对应物品才用、缺少对应物品不停战、买入后自动续用；装备、技能、战斗物品栏槽位与触发条件仍冻结。
- 队伍任意成员在线就采用在线模式，包括断线队友；全员离线才转为默认一小时批算和离线战斗消耗品储备。
- 不采用在线托管、在线携带限额、透支扣除或缺少某种物品散场。离线储备是本次明确提出的简化设计，不冒充用户已确认的游戏规则。

本任务中的“战斗消耗品”定义为：`ItemDefinition.Category == consumable`、`Consumable.UsableInBars` 包含 `combat`、且 `Durable == false` 的自动使用物品。范围包含战斗物品栏的 `potion` 与 `general` 两个槽组，包含即时消耗品和非 durable 持续消耗品；药品只是其中一个子类，不得为药品单独实现库存、储备或交易语义。手动消耗品（如 manual/chest 等）不进入自动战斗消耗范围；`Durable` 持有型阵盘不按每次战斗扣件，但继续沿现有冻结资格与 Buff 生命周期处理。

## 推荐方案：在线真实库存，离线储备批算

原则：**有人在线时，组队的全部战斗消耗品按单人真实库存语义运行；只有全员离线时，才建立对应战斗消耗品的离线储备供批算使用。** 两种模式共享触发规则与战斗状态，不共享库存机制。以下是完整拟实施方案，不表示当前代码已实现。

### 一、在线模式：真实库存，精确排序

1. 开场不托管战斗消耗品、不扣余额、不设携带额度；冻结成员、装备、技能、战斗物品栏槽位与槽序、触发条件，像单人行动一样使用当前可用背包库存。
2. 每个现有自动使用判定边界，先按槽序检查对应物品的共享工作钱包；余额足够才借记 1 件并施加该物品效果、启动冷却/持续周期和记录 LostItem。多槽同物品共用一个余额，不能同 tick 双花。
3. 某种战斗消耗品库存不足是普通跳过：不清槽、不停战、不重置冷却、不延长已有持续效果，不散场。战斗继续推进；其间买入该物品，在后续原有合法判定边界自动续用，不强制等散场或重新准备。
4. 已经消费产生的限时效果持续到自身到期时刻；卖掉其余库存不会撤销效果。持续消耗品到期且缺货时停止效果；补货后只在满足现有资格的合法边界续充。倒地成员不新使用物品。阵盘队伍作用范围不改。
5. 在线交易与战斗有唯一顺序：持有参与会话推进门，到交易有效时刻 T 先结清此前战斗并提交实耗，再重新验证可售余额、执行买卖；门保持至资产事务结果明确。成交后会话读取新库存。若交易失败，已发生的战斗仍提交，交易单独失败；不得回滚过去战斗，也不得让交易先改库存再模拟过去。
6. 买单未成交不算补货；市场成交在结算领取前已入账，成交即按新库存可用。挂卖订单已冻结的物品不属于可用库存，不能同时自动吃掉。

在线用户语义与单人一致；实现边界不同：单人由玩家所有权通道串行，组队由会话所有权通道串行。**不要求会话跨 Fiber 调成员，不在每次使用战斗消耗品时另发网络/数据库 RPC。**

### 二、离线模式：有界离线储备，小时批算

离线期间选择明确简化：**离线储备在进入全员离线时一次性从可用钱包划出；此后市场只影响未预留余额，不实时唤醒战斗。**

1. 最后一位成员离线时，先按在线模式把会话推进至离线切换时刻 T，并提交在线阶段实耗。
2. 在同一切换事务里，按冻结战斗消耗品槽位及槽序读取真实余额，将配置可用的非 durable 战斗消耗品实际余额全部划入该会话的离线储备；不储备 durable 持有型物品。余额不够 1 件则不储备该键。储备按（成员、物品、variant）去重，数量保持 double，不按槽位重复划拨；不新增数量上限配置。此后该储备无法出售、转移或用于其他行动；划拨不同于实际消耗，上线时退回剩余。
3. 全员离线保持当前默认每小时批算。批内以各物品储备作为工作钱包连续推演；有对应物品才使用，某项储备空后不再使用该项但战斗继续。每个批次的实耗与会话检查点、成员 inbox、储备余量原子提交；不得逐颗写数据库。
4. 离线期间的买入、退款和其他入账进入普通可用余额，不追溯加入当前储备，也不触发提前补算。它们最早在下个实际小时批算边界之后可用：先以旧储备结算到边界，再将未用储备退回可用钱包，并按边界时普通钱包余额建立下一批储备。离线战斗本批掉落不在本批自动转化成可使用库存；其中属于战斗消耗品的奖励须在该批事务中入普通钱包后再划入下一批储备，成员 inbox 不重复入账。不重建此前错过的小时边界来多次补货；实际延迟批算时一次补算到当前允许目标 T，只在 T 处补充下一批。
5. 离线出售、转移或其他扣件只能使用扣除储备后的普通可用余额；余额不足按既有业务错误拒绝。离线储备不支持中途出售。由此玩家可能看到“有库存但离线占用”，这是离线自动使用战斗消耗品的明确代价；上线时剩余储备退回。
6. 离线批算失败或服务停机不扣批次储备、不推进检查点、不重复消费；成功批次按事务原子落账。保留现有离线最大补算与离线超时散场边界。

实现只计算批次续补的净余额变动：剩余储备原地续持，新增可用战斗消耗品划入即可，不真实执行一次“剩余全退再全扣”的往返，避免无用余额版本/WAL 更新。上文退回再建立表示资产守恒语义，不要求中间状态对外可见。零数量变动不写余额。真正退回只发生在上线、散场或安全收尾。

该方案有意只在离线使用预留，不是在线托管。离线玩家无法要求系统既把战斗消耗品作为可卖资产，又把同一批物品当成过去时段可消费的库存。

### 三、模式切换与边界顺序

模式状态持久化于会话检查点，取值 `Online` / `Offline`；储备账本是持久化资产负债事实，不从旧 spec 每次重新计算。

| 事件 | 原子顺序 |
| --- | --- |
| Online → Offline | 会话门；推进并扣在线实耗至 T；按持久化成员在线状态确认全员离线；从真实可用余额划出储备；保存模式/储备/检查点。任一步失败整体不切换 |
| Offline 小时批次 | 会话门；以当前储备推进至批算边界 T；旧储备扣除实耗；将剩余储备退回普通钱包；从 T 前已入账的普通余额建立下一周期储备；会话检查点、余额、储备和成员 inbox 同事务提交 |
| Offline → Online | 会话门；按离线规则结清至上线时刻 T（不将上线后时间算进离线）；退回全部剩余储备；模式切 Online；之后才运行玩家所有权通道和在线钱包操作 |
| 在线资产变动 | 交易门；确定参与会话与成交双方；会话门；推进至 T 并提交在线实耗；基于新可用余额验证；资产事务提交；发布余额刷新/通知；释放门 |
| 全员离线资产变动 | 同样取得有序会话门并复核持久化模式，避免与回线切换竞争；若确认为 Offline，只改普通钱包，不强制推进会话、不写储备。若已切 Online，转走在线顺序 |
| 散场 | 会话门；推进到权威结束时刻；退回剩余离线储备（在线模式没有储备）；原子写末批、余额与终态 |

多人同时上线/离线时，以服务端持久化在线状态变更的线性化顺序决定 T。若会话在边界确认已有在线成员，整个会话切 Online，离线队友仍由常驻会话实时推演。重连、断连宽限期、离线逐出仍遵循现有判定，不重置槽位时钟或持续 Buff。

切换时刻 T 在取得门后确定，不得早于任意涉及会话的已提交游标。切换只改变库存来源，不结束或重开会话；参与行动 ID、随机序列、战内单位、冷却、持续到期和下一判定游标连续。定期续批只发生在真正的离线批次，上线补算末批不先重新储备再退款。交易可等待已在执行的离线批次，但不会因每笔成交主动触发一小时补算；不承诺绝对零等待。

### 四、持久状态与故障恢复

- 在现有会话运行检查点增补模式、模式生效时刻、离线周期序号、下一批次时刻、离线储备行及余量；在线模式储备必须为空。槽位冷却/持续到期、下一资源判定游标保留，不把库存数量继续放在冻结 spec 中。业务时间与数量统一 double，事务/检查点序号沿用现有 long。
- 储备通过真实钱包扣减与检查点储备增加表达一次内部划拨，不另建第二个普通钱包；划拨、返还和各类战斗消耗实际使用分类审计。离线每消耗一件只减储备，不能再次扣玩家钱包。其守恒式为：普通可用数量 + 离线储备余量 + 已实际消耗 = 初始持有 + 后续实际入账 − 外部实际支出。
- 离线储备直接作为现有会话检查点的强类型列表保存，不新增独立库存服务/普通钱包表；数量归属与变化用现有经济流水和会话版本联合审计。读到储备但没有对应有效会话版本时快速失败，不能静默补默认库存。
- 储备、检查点、经济流水与成员 inbox 在同一事务更新，稳定幂等键绑定会话和目标版本；模式校验与版本 CAS 在该事务内执行。已提交响应丢失时先查询版本与幂等事实；未知时 fence，不重放不确定扣款。事务确认前不发布战斗消耗品效果/胜负。
- 重启先恢复参与关系、持久化模式与储备，再开放资产写入。已处于 Offline 的会话只能用检查点剩余储备结算停机段；完成恢复批次后才能按真实钱包建立下一批，不拿当前钱包回补停机历史。
- 若崩溃前最后提交为 Online，不假装已在旧时刻预留离线战斗消耗品：先沿已提交 Online 规则恢复到服务恢复边界，再按真实在线人数切 Offline 或保持 Online。所有冻结战斗消耗品的外部写入都受时间栅栏控制且服务为单权威写者，因此最后一次库存变更已先把会话推进到对应时刻；必须先核清提交未知的资产事务，禁止未恢复就接收新写请求。异常停机不倒推一个无法证实的断线/储备时刻；正常停服可在停止新请求后显式切 Offline。
- 配表指纹不兼容、离线超时或组织条件失效时沿现有安全收尾规则停止在可证明的检查点；仅退还该检查点剩余离线储备，不能退款已实际消费数量。不得在迁移时通过删除字段抹掉资产。

### 五、实现与事务边界

- 引擎仍为确定性纯逻辑：每批输入成员冻结规格、检查点、模式及工作钱包数量；输出新检查点、消耗差量、储备调整、需交付资产与统计。不能依赖缓存钱包、不注入数据库、玩家聚合、回调或通用事件总线。
- `ActionParticipationSessionEngine` 删除在线全量 `EscrowQuantity`/`RemainingQuantity` 和托管日志/散场退款；在线消耗直接借记本批工作钱包。仅持久化 Offline 模式的战斗消耗品储备与储备余量，且只允许全员离线态消费。
- 当前构造函数会在初始化时执行即时判定；初始化须改成显式阶段，将开场战斗消耗品效果和消耗与初始会话、余额检查点同事务提交。检查点恢复不得重演初始化。
- 在线一次推进事务：所有被检查的战斗消耗品键数量/版本（包括零余额行）作为读集；任何读集变化都回滚整批并从最新检查点重算，不能只调扣款差量而保留旧战斗结果。单一 PostgreSQL 事务同时提交余额、检查点版本和全部成员 inbox，稳定幂等键绑定 sessionId + nextVersion。已提交响应丢失时核验事实，不盲扣。
- 离线储备创建、消耗、续批释放/重建、上线退回、散场退款同样与检查点版本及 inbox 原子提交。储备须有会话归属和物品键，可审计余额守恒；不得只把扣款存在 transient 引擎内。
- 单人/在线组队复用现有触发器、效果结算和自然边界规则，差异仅施放上下文与资产提交宿主。保留或提取现有纯规则函数，不另写第二份战斗消耗品效果公式；药品不得成为特殊实现分支。交易、模式切换或零时长同步不得额外调用一次判定，下一判定游标必须随检查点保存。
- 检查点 COMMIT 结局未知沿用现有 session fence：暂停该会话，查询持久化版本/幂等事实后决定恢复。交易系统故障不是缺少战斗消耗品，不伪装成正常战斗跳过。
- 对目标战斗消耗品参与在线结算的普通掉落，若要在同批后续边界可用，须按事件真实顺序进入工作钱包，奖励资产与检查点同事务交付，成员 inbox 不重复发同一资产；尚未归属玩家的暂存物不可用。其他奖励沿原有成员结算路径。
- durable 非消耗型阵盘不扣件、不进入离线消耗储备、不在中途实时换装；开场按现有冻结规格持有资格决定增益，期间库存变化不重算冻结属性。该语义须同步到设计真源和界面，不沿用旧“durable 锁一件”实现。

### 六、资产入口、锁序与缓存

- 必须覆盖一切影响冻结战斗消耗品可用余额的写入：市场主动下单/撮合所有成交方、撤单退款、到期退款、回收、丢弃、材料贡献/合成、奖励及其他经济命令。取得有序会话门后按持久化模式分支：Online 先推进，Offline 只改可用余额。普通非战斗消耗品交易不必为此补算会话。参与关系和模式查询不能只依赖可能过期的内存缓存。
- 市场 `PlaceCoreAsync` 内存试撮合之后才知道全部被动成交玩家，但 `_booksGate` 是同步临界区：取出完整玩家/资产集合后释放 `_booksGate`，保持市场写门，再按稳定 sessionId 顺序取涉及会话门；按模式推进或直写可用余额，用更新后余额重新验证卖单，提交时继续使用市场分区门和有序玩家条带。失败时撤销盘口试算日志。不得在数据库条带/事务/身份行锁内回调会话。
- 推荐全局锁序：市场写门（适用时）→ 有序会话门 → 市场分区写门（市场仓储适用时）→ 玩家提交条带（PlayerId 映射后去重升序）→ 数据库事务与行锁。`_booksGate` 必须先释放。会话绝不等玩家 gate、Fiber、市场写门或成员 inbox。在线玩家命令即使持本人 gate 调用会话也不能产生反向依赖；该路径须专门并发测试。
- 开场、散场、上线切换、库存写入共用会话参与关系序列化点，解决“资产入口查到无会话、并发开场后漏栅栏”。会话与成员身份的数据库锁必须排在提交条带之后，禁止先锁玩家身份行再等待条带。清晰处理市场幂等回执与盘口日志回滚。
- `economy.player_asset_balances` 是唯一库存真源。交易前会话结算后刷新玩家钱包；本地钱包按余额版本合并，只允许更高版本覆盖，异步旧读不得覆盖新余额，通知刷新过程中不能丢失新失效标记。`WalletCredited` 仅作 UI/缓存失效提示，不参与战斗判定。
- 组队参与会话继续由主服的会话权威引擎计算，不新增向冷挂机 Compute 节点派发会话的第二实现。个人 Compute 冻结钱包基线若因划入/退回战斗消耗品储备发生版本变化，沿现有源版本漂移规则拒绝旧结果；开场参与挂接与结束恢复个人行动须继续撤销/隔离过期个人冷算资格。不得让个人行动与会话对同一战斗消耗品同时拥有消费权。

### 八、必须通过的验收

| 场景 | 验收结果 |
| --- | --- |
| 在线 0 个战斗消耗品开战、买入、耗尽、再次买入 | 同一会话不停战；仅后续合法判定边界使用新物品 |
| 在线最后一件战斗消耗品与市场出售竞争 | 串行顺序唯一；不负余额、不白用、不重复卖；失败试撮合恢复盘口 |
| 多槽同物品、即时品与持续品断供续用 | 槽序共享余额；缺对应物品不生效/不散场；补货后按现行规则继续 |
| 单人 vs 在线组队同输入 | 同一触发边界、冷却、效果时钟与库存顺序下，各类战斗消耗品的消耗和可见战斗结算一致；差异仅队伍本身多人规则 |
| 最后一人离线与下一人同时上线 | 只有一个线性化模式，储备不重扣、不漏扣，所有余额守恒 |
| 离线储备耗尽，期间市场买入战斗消耗品 | 战斗继续但不使用新购物品；下个批次边界才有资格进入新储备 |
| 离线储备余量与市场出售 | 仅普通余额可售；划拨、消耗、退回三者账目守恒；回线后剩余额度立即可见/可售 |
| 离线批次、重启、响应丢失 | 储备扣减与检查点同事务；只可能整体提交一次，未知提交先核验/fence |
| 在线买卖、订单到期/撤销退款、被动成交 | 涉及在线会话先结算；Offline 会话不被交易逐笔唤醒；退款不进入已结束区间 |
| 旧全量托管存档切换 | 未消费战斗消耗品数量一次性退回恰好一次；已消费统计不返还；会话状态不中断或按规定安全散场 |
| 钱包通知与玩家缓存交错 | 旧版本不能覆盖新余额，离线 Compute 不接受旧基线结果 |
| 分段推进/连续推进/恢复 | 相同输入事件序列得到相同检查点、库存和消耗；不允许零时长同步重复使用战斗消耗品 |

### 九、明确不做
