## 需求背景与核心痛点

前端（`frontend/src`）已经过多轮性能治理（WAAPI 合成器进度条、日志折叠上限 200 条、悬浮窗 `isOpen` 懒计算与滚动抑制、坊市网格 `content-visibility` 裁剪、`Intl.NumberFormat` 按语言缓存、目录 Map 缓存等），常规热点已收敛。本次从「剩余结构性浪费」切入，静态审查定位到四类与画面结果无关、却持续消耗 CPU 的工作：

1. **地图漫游按指针事件驱动整图 React 重渲染（最重）**
   `WorldMapPanel` 的拖拽（`handlePointerMove`）、滚轮缩放（非 passive 原生 wheel 监听）、新手引导运镜（rAF 逐帧）全部经 `setPan`/`setZoom` 推进。但 `pan`/`zoom` 的唯一视觉出口只是画布容器的 `transform`；一次 `setPan` 会把 `<svg>` 区域界框与路径（含 `feDropShadow` 滤镜节点）、全部节点胶囊、建筑胶囊、生灵胶囊的 element 树整体 reconcile 一遍。指针设备 120~240 次/秒的 `pointermove` 就是 120~240 次全图重建，且大量事件落在同一帧内被白白丢弃——这是当前最重的交互卡顿来源。
2. **地图面板与应用同寿**
   `MapPage` 恒挂载，`WorldMapPanel` 从应用启动即构建全图索引（区域归并、节点归属、邻居表）、挂 `ResizeObserver`、执行视口适配测量，并在每条 WebSocket 补丁后随订阅重渲染——即使整局从未点开地图页。
3. **背包网格的「每格每次通知」重复建表**
   `InventoryItemCell` 的 zustand selector 内联调用 `collectOccupiedEquipmentCounts(...)`：**每个格子、每条服务端补丁**都重建一次「已穿戴 + 强化锁定」占用表。成本随「袋内条目数 × 队列长度」放大。
4. **背包排序被高频队列补丁牵着走**
   `InventoryPanel` 的分组 memo 依赖 `queue?.entries`，但排序（`localeCompare` + 层级 + 强化等级比较）与占用无关。队列每推进一次就要对整包重排一次，纯属重复劳动。

## 解决方案与技术方案

### 1. 地图视口改为命令式变换（核心）
- 画布 `.world-map-canvas` 增加 `canvasRef`；`transform` 从 JSX `style` 中移出，改由 `useLayoutEffect([pan, zoom])` 施加。**React 不再拥有 `transform` 属性**，因此补丁重渲染不会把漫游中的视口拽回旧值（这是必须移除 JSX 绑定的原因）。
- 拖拽：`handlePointerMove` 内直接写 `canvas.style.transform` 并同步 `panRef`，`pointerup` 时一次性 `commitViewport()` 回填 state。
- 滚轮：同样直接落画面，滚动静默 120ms 后提交终值 state，避免逐事件 `setState`。
- 引导运镜：rAF 逐帧只写 transform，动画收尾提交终值。
- 所有读取点（拖拽起点、缩放锚点、±按钮、居中）改读 `panRef`/`zoomRef`，确保手势期间读到最新视口。
- `transform-origin: 0 0` 由内联样式迁入 `.world-map-canvas`，像素换算口径不变；同一时刻的 transform 数值与改造前逐值相同。

### 2. 地图面板首次可见才挂载
- `MapPage` 复用 `CombatDetailsPage` 已验证的 `hasBeenVisible` 范式：地图子页首次激活才挂载 `WorldMapPanel`，此后常驻不卸载（漫游视口、选中地点、运镜状态与改造前一致）。
- 顺带消除一个隐性风险：引导聚焦在视口尺寸未就绪时会 `requestAnimationFrame` 轮询等布局；面板不再常驻后，未打开地图时根本不存在该轮询。

### 3. 背包占用表按状态引用缓存
- `game/ids.ts` 新增 `getOccupiedEquipmentCounts(combatEquipment, queueEntries)`：按两个入参的引用身份缓存整表，命中即 O(1) 返回（与既有 `getItemMap`/`getAbilityMap` 同构）。原 `collectOccupiedEquipmentCounts` 保留为纯函数。
- `InventoryItemCell` 与 `InventoryPanel` 改用缓存版：每格 selector 退化为一次哈希查表。

### 4. 背包分组/排序与占用解耦（两阶段）
- 阶段一（重）：分组 + 排序，依赖 `[inventory, items, equipment]`，只在背包或配表变化时重算。
- 阶段二（轻）：扣除占用、丢弃空组，依赖 `[sortedGroups, equippedList, queueEntries]`；占用表为空时直接短路。
- 队列补丁从此只带来一次 O(袋内条目) 过滤，不再触发整包 `localeCompare` 排序；分组顺序、组内顺序与可见条目完全不变。

### 5. 图片异步解码
- 为 16 处缺失的 `<img>` 补 `decoding="async"`（世界地图建筑图标、附近/图鉴缩略图、角色立绘回退、图标注册表图元、设置页头像等），把解码移出主线程，避免图像解码抢占帧。

### 6. 门禁
- `tsc -b` 类型检查、`vite build` 生产构建、`check-i18n-keys.mjs`、`check-frontend-contracts.mjs` 全部通过。

## 静态审查后「确认存在但本次不改」的项（附理由）

这些项都是真实开销，但改动会带来像素级或行为级差异，或收益/风险不划算，留待明确授权后处理：

| 项 | 现状与开销 | 不改的原因 |
| --- | --- | --- |
| `.top-bar { backdrop-filter: blur(6px) }` | 顶栏整宽 × 85px 的实时模糊；`.motes` 六个粒子在 `z-index:-1` 层于全视口穿行，粒子每次位移都会让该模糊区域重新栅格化——**持续 60fps 的整宽模糊**，是当前最大的常驻 GPU 开销 | 顶栏底色为 `rgba(7,6,4,0.95)`（95% 不透明），模糊的可见贡献约为 5%，去掉后肉眼几乎无差——但严格说仍属像素变化。是否去除需产品侧确认 |
| `.qc-current::before` 金线流光 | `@property --gold-angle` + `conic-gradient`，注册自定义属性的角度动画无法合成器化，等价于对该伪元素每秒 60 次重绘 | 改「旋转层」方案需按画布对角线尺寸放大图层（桌面约 1k×1k ≈ 4MB 显存），收益与显存代价不划算；改子元素结构又会动到既有描边蒙版，视觉风险高于收益 |
| 战斗浮字 `filter: brightness()` 关键帧 | 命中瞬间连带重栅格化周边 | Chrome 已可将 `filter+transform+opacity` 组合动画交给合成器；补 `will-change` 会引入频繁的图层创建/销毁，收益不确定 |
| 隐藏页签仍随补丁重渲染 | `ExplorationPage`/`CraftingPage`/`CombatDetailsPage` 常驻挂载，`hidden` 只省布局与绘制，不省 JS | 卸载会丢失各页局部 UI 状态（如地图子页签选择、已展开的挑选弹窗），属行为变化；仅地图页做了「首次可见才挂载」 |
| 首屏 `index.js` 659KB / gzip 204KB | 首屏解析成本 | CSS/JS 按面板拆分会让首次打开对应面板出现样式闪入，属可见变化；后续可单独作为「加载性能」任务评估 |
| `.event-log li` 的 `content-visibility` | 200 条日志全量布局 | 日志行高不定，`content-visibility: auto` 会让 `scrollHeight` 估算漂移，破坏贴底滚动，产生可见跳动 |
