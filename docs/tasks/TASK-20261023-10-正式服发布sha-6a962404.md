### 5.6 Caddy 既存故障与修复（本次关键事件）

部署卡在 `install-caddy.sh` 的 `systemctl reload caddy` 达 33 分钟。诊断：

- `caddy.service` 自 **2026-10-19 02:14:40** 起长期处于 `ActiveState=reloading (reload-notify)`，是**本次发布之前既存**的故障，非本次引入。
- 按 `AGENTS.md` §13，部署必须先过 `caddy validate`，再 `systemctl reload`；本次因此被阻塞。
- 根因：Caddy 管理 API `127.0.0.1:2019` 虽在监听（pid 33035），但请求超时（`curl` 返回 `000`/`28`）。`caddy reload` 依赖该 API 推送配置，API 无响应则超时；systemd 等待 `reload-notify` 亦超时并杀 reload 进程，形成循环。
- 期间 80/443 仍正常代理（旧配置），公网 `/healthz` 持续 200。

经用户明确许可后处置（`caddy.service` 同时托管 daohua/daojie/frp/clash/dj/mcp/xiuxian 多站点，重启会短暂中断全部站点）：

1. 备份 `Caddyfile` 与 `daohua.caddy` 各一份带时间戳副本；
2. `caddy validate` 通过（`Valid configuration`）；
3. `systemctl restart caddy` → `ActiveState=active`、`SubState=running`、admin API `200`；
4. `install-caddy.sh` 重装站点 + `systemctl reload caddy` 成功，输出 `Caddy 站点已安装` 与 `主配置备份`。

重启后各站点复测：`daohua` 200、`daojie` 200、`frp` 404（该站点路径规则正常表现）、`ops-5366b1ee0517931f` 200。
