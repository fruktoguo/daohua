# TASK-20261018-17-客户端版本更新检测与全自动刷新实装

## 1. 任务背景与核心需求

- **提出时间**：2026-10-19 00:50:00
- **需求来源**：用户要求优化，给当前项目增加“如果版本更新了，前端自动刷新”的功能。
- **现状痛点**：
  1. 当前前端与服务端在版本更新后，缺乏自动感知与自愈机制。当主服通过 CCR 镜像部署、本地重启或更新前端资产后，玩家浏览器若长期处于挂机状态，仍持有旧版 JS 代码与内存状态，容易引发前后端协议/数据模型不一致、甚至动态模块 chunk 加载 404 报错。
  2. `Dockerfile` 中前端构建阶段（`frontend-build`）未将 `BUILD_VERSION` 注入 `VITE_APP_VERSION`，导致前端静态打包中版本恒为 `'dev'`。
  3. 服务端虽在 `/healthz` 与 WebSocket `HelloAck` 中携带了 `serverVersion`，但客户端未记录初次会话版本基线，断线重连或后台轮询时无法感知版本漂移，更未触发页面重载。
  4. 缺少防刷新死循环（Anti-Loop Guard）安全熔断机制，若浏览器或代理强缓存 HTML，单纯 `location.reload()` 存在无限循环刷新的系统级风险。

---

## 2. 方案设计

### 2.1 版本感知多层网络防线
1. **构建期对齐**：
   - 在 `Dockerfile` 中，将 `ARG BUILD_VERSION=dev` 传递给 `frontend-build` 阶段，设置 `ENV VITE_APP_VERSION=${BUILD_VERSION}`；确保生产镜像中前端静态包内的版本号与后端 C# 程序集 `InformationalVersion` 严格一致。
   - 在前端 Vite 构建中支持生成轻量静态 `version.json`（或通过 `/api/v1/version` 与 `/healthz` 双通道）。
2. **服务端版本端点与静态文件防缓存**：
   - 暴露轻量公开的 `GET /api/v1/version` 端点（返回当前 `version`、`gameDataFingerprint`、`protocolVersion`），并设置严格的 `Cache-Control: no-cache, no-store, must-revalidate` 标头。
   - 对 `index.html` 兜底响应（`MapFallbackToFile`）补充 `no-cache` 控制，防止浏览器持久缓存旧版入口。
3. **前端运行时全方位检测（`VersionManager`）**：
   - **通道一（WebSocket 握手对齐）**：`gameClient` 收到 `HelloAck` 时，比对当前记录的会话版本 `sessionServerVersion`；若重连后版本发生变动，即刻触发自动刷新。
   - **通道二（后台轻量定时轮询与切回前台唤醒）**：设置 45 秒定时器，在页面可见（`document.visibilityState === 'visible'`）或窗口获焦（`focus`）时主动查询版本端点，未登录用户或非 WS 场景同样能够及时感知。
   - **通道三（动态 Chunk 404 异常自愈）**：监听 `vite:preloadError` 与全局资源加载异常，若捕获到旧模块加载失败，立即触发版本刷新自愈。
4. **安全防刷新死循环熔断保护（Anti-Loop Guard）**：
   - 基于 `sessionStorage` 记录最近刷新时间戳与目标版本。
   - 若短时间（15 秒）内针对同一目标版本连续自动刷新超过 2 次，说明浏览器或反代存在无法被普通刷新冲刷的持久缓存，立即熔断自动刷新，降级为页面顶部醒目横幅通知修士手动按 `Ctrl+F5` 硬刷新，彻底阻断死循环风险。
