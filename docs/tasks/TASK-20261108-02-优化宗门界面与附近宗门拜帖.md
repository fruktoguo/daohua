## 1. 需求背景与核心理解

用户要求重构优化宗门界面展示结构：
1. **状态分流显示**：改用类似队伍界面的方式，根据玩家当前是否有宗门（在宗/未入宗）进行明确的视图分流显示；
2. **未入宗视图重构（解耦平铺表单）**：
   - 顶部显示「创建宗门」按钮，点击后弹出独立的创建宗门弹窗（Modal），将原本平铺在主页面的冗长立宗表单完全拆分出去；
   - 页面主体显示「当前地点附近所有的宗门」列表；
   - 宗门列表项支持点击「递交拜帖」（发送入宗申请 `zongmen.apply`），并明确展示已递交状态；
   - 对应宗门管理者在管理面板能即时收到该拜帖申请。

## 2. 方案设计与实现边界

1. **协议层与仓储扩展**：
   - `ZongmenSummaryDto` 扩展 `AnchorNodeId` 字段，下发宗门挂靠的公共节点；
   - `ZongmenStateDto` 补充 `Applications` 字段，下发当前玩家作为申请人发出的待批拜帖列表，使客户端可精准标定哪些宗门已递交拜帖；
   - 服务端 `PostgresZongmenRepository.StateAsync` 在读取名录时一并查询 `z.anchor_node_id`，并拉取本人 `kind='application'` 的请求记录。
2. **前端架构拆分**：
   - `ZongmenPage.tsx` 解耦为三个高内聚子组件：
     - `ZongmenView`：已入宗视图（宗门信息、成员列表、职位管理、招收弟子与拜帖审批、进入驻地等）；
     - `ZongmenlessView`：散修未入宗视图（顶部「创建宗门」操作栏 + 入宗邀请展示 + 当前地点附近宗门列表 + 宗门名录检索）；
     - `ZongmenCreateModal`：独立立宗弹窗（名称、字号、令牌消耗说明、炼器配方提示与当前挂靠地点二次确认）。
3. **附近宗门感知与拜帖交互**：
   - 结合玩家当前所在地 `world.nodeId` 与世界地图数据，优先聚合展示挂靠在当前地点（以及同区域）的附近宗门；
   - 列表项显示宗门前缀、宗门名称、驻地挂靠地点、当前人数与人数上限；
   - 提供「递交拜帖」按钮；对已递交的宗门显示「拜帖待批」并禁用重复提交；
   - 点击递交拜帖发送 `zongmen.apply` 命令，对方宗门管理员立即在招募面板中收到申请。
4. **设计文档对齐**：
   - 同步修订 `docs/design/总纲/25-宗门与专属驻地.md` 第 25.1 节界面与入宗拜帖规约。
