## 关键前置判断：与 TASK-20260913-04 的 `pixelated` 是否冲突

TASK-20260913-04 给三处图标加了 `image-rendering: pixelated`（最近邻），并在 CSS 注释里明确预留了
「**若日后把源图换成 ≥ 绘制区的尺寸，会变成缩小场景、最近邻会走样，需重新评估**」。
本次换到 64px 正好触发该条件，因此必须实测，不能只改尺寸就收工。

绘制区固定为 **52×52 CSS px**（瓦片 64 − 边框 1px×2 − 图标自身 `padding: 5px`×2）。于是：

| 屏幕 | 绘制目标（物理像素） | 与 64px 源的关系 |
| --- | --- | --- |
| DPR1（普通屏） | 52 | **缩小 0.8125×** |
| DPR2（Retina） | 104 | **放大 1.625×** |

同一个 64px 源在两种屏上是**相反**的缩放方向 —— 这正是必须分屏实测的原因。

## 改动

90 张运行时图标全部重出为 **64×64 WebP q90**：

- **新一批 64 张**：用固化规格重跑
  `slice_grid_sheet.py art/sheets.json --pad 8 --master-size 256 --web-size 64`，
  再按 `art/icon_ids.json` 映射为资源 ID（与 03 的流程一致，未手搓）。
- **遗留 26 张**：从 `art/legacy_128/`（唯一高分辨率副本）按长边补正方形后 LANCZOS 缩到 64。
- 合计 **267.2 KB**（32px 时为 110.5 KB）。
- **未改任何 CSS / JS** —— `image-rendering: pixelated` 保持不动，先实测再决定去留。

### 四象限实测（DPR × 插值方式）

同一页面同时渲染「最近邻」与「双线性」两组，分别在 DPR1 / DPR2 下渲染并截图，
再按最近邻放大器目视比对：

| 组合 | 结论 |
| --- | --- |
| **DPR1 · pixelated**（缩小 0.8125×） | **未出现可见走样**。轮廓干净、边缘硬挺，比双线性更锐利 |
| DPR1 · 双线性 | 边缘柔和发虚 |
| **DPR2 · pixelated**（放大 1.625×） | 锐利、边缘硬；1.625 倍属小幅放大，像素块很细，不会有大块马赛克感 |
| DPR2 · 双线性 | 略软（但已明显好于 32px 时期） |

**结论：64×64 与 `image-rendering: pixelated` 兼容。两种像素密度下均无问题，
因此不需要按 DPR 加 media query 分支，也不回退 04 的改动。**

DPR1 之所以没走样：0.8125× 的最近邻只跳过约 19% 的像素，而图标以大色块为主，抽样损失肉眼不可见。
