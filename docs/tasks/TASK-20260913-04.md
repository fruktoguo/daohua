# TASK-20260913-04 图标渲染关闭线性插值（改最近邻，恢复像素质感）

- **提出时间**：2026-09-13 18:07:50
- **需求分析完成**：2026-09-13 18:08:30
- **完成时间**：2026-09-13 18:10:00
- **状态**：🧪 联调/验证中（工作区改动已完成并通过构建与真实浏览器验证，**尚未提交 Git**）
- **分类**：前端样式 / 图像渲染 / 视觉体验

## 需求

用户提出：

> 把网页端的线性过滤能不能给我关掉看看？现在感觉线性过滤一开之后有点糊了，反而没有那种像素感了。

即：把图标图片的缩放插值从浏览器默认的双线性（平滑）改为最近邻（`image-rendering: pixelated`）。

## 背景与判断依据

TASK-20260913-03 定稿后运行时图标为 **32×32 WebP**，而瓦片图标的**实际绘制区只有 52×52 CSS px**
（瓦片 64 − 1px 边框 ×2 = 62，再减 `.item-tile-icon` 自身 `padding: 5px` ×2 = 52）。

也就是源图小于绘制区、属于**放大场景**：浏览器默认双线性插值把 32px 放大 1.625× 并做平滑，
视觉上就是用户说的「糊」。改用最近邻后放大是整块像素复制，边缘硬挺，即用户要的「像素感」。

## 改动

三处图标 `<img>` 均加 `image-rendering: pixelated`（未新增类名、未改 DOM、未动 JS）：

| 类名 | 样式文件 | 源图 → 实际绘制 | 场景 |
| --- | --- | --- | --- |
| `.item-tile-icon` | `styles/selection-grid.css` | 32px → 52×52 | **放大 1.625×**（本次主要目标） |
| `.item-reference-icon` | `styles.css` | 32px → 16×16 | 缩小 2×（整数比） |
| `.daohua-floating-card-title-icon` | `styles/floating-popover.css` | 32px → 24×24 | 缩小 1.33× |

- 已 grep 确认：三个类在全仓库**各只定义一处**，不存在同权重互相覆盖的问题，
  因此改动不受 `main.tsx` 的 CSS 导入顺序影响。
- 三处均写中文注释说明场景与取舍。`.item-tile-icon` 的注释额外提示：
  **若日后把源图换成 ≥ 绘制区的尺寸（如 128px），这里会反过来变成缩小场景，最近邻会造成细节走样，需重新评估。**

## 验证

### 构建门禁

- `npm --prefix frontend run build` 通过（547ms），无 TS 错误。
- 产物 CSS 中 `image-rendering:pixelated` 出现 **3 次**，且逐条核对压缩后的规则体，确认分别落在上述三处
  （`.item-reference-icon` 16px、`.item-tile-icon` absolute 铺满那条、`.daohua-floating-card-title-icon` 24px）。

### 真实浏览器 A/B 对照（本机 Edge + 构建产物 CSS + 真实组件 DOM，DPR2）

把 A（改后，构建产物 CSS）与 B（改前，`image-rendering: auto !important` 覆盖）放在**同一页面同时渲染**，
唯一变量就是 `image-rendering`，排除环境与素材差异：

| 断言 | 结果 |
| --- | --- |
| A 组 `getComputedStyle(img).imageRendering` | `pixelated` |
| B 组 `getComputedStyle(img).imageRendering` | `auto` |
| 图片加载 | 36 张，**零破图** |
| 瓦片图标渲染盒 | 62×62（内容盒 52×52，与既有结论一致） |

截图按类型做最近邻放大后目视对比：

| 场景 | 放大倍数 | 结论 |
| --- | --- | --- |
| 瓦片 52px | 3× | **差异明显**：A 的剑刃/杖身/晶面呈硬边像素块，B 柔和晕开（即用户所说的「糊」） |
| 行内 16px | 8× | A 比 B 更硬挺、不糊，**未出现走样破碎**（32→16 是整数 2 倍，最近邻行为规整） |
| 浮窗 24px | 6× | 同上，A 边缘清晰，无异常 |

结论：三处全部保留 `pixelated`，缩小场景未产生副作用。

  这与 TASK-20260913-03 记录的「项目自身基线是 128px」直接相关 —— 一旦基线回归，本任务需同步复核。
  - **2026-09-13 18:30 补充（TASK-20260913-05）**：尺寸先改为 **64×64**，已触发上述条件，
    于是在 DPR1（缩小 0.81×）/ DPR2（放大 1.63×）下做了四象限实测 —— **两种密度均无走样，
    `pixelated` 全部保留，无需按 DPR 加 media query**。**128px 的评估仍未做**，本提示继续有效。
