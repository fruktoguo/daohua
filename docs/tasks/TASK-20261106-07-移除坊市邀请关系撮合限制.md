# TASK-20261106-07 移除坊市交易层硬性阻断并转为非阻塞审计加分

## 1. 需求背景与核心设计原则

- **背景与现象**：在 `TASK-20261030-05` 中实装的坊市防倒金风控在撮合引擎中增加了跳过关联方撮合（`isProhibitedCrossTrade`）以及成交落库即时熔断异常（`MarketProhibitedTradeException`）。当真实同道邀请好友（如群内道友使用邀请码进入游戏）或同一网络/设备账号在坊市交易时，买单被撮合引擎静默跳过而沉淀为挂单，导致买一卖一价格重合无法成交；随后买方因“已有求购单”无法再快捷买入，严重干扰正常游戏流程。
- **架构原则（用户明确指示）**：
  > 所有的反多开小号机制，都应该只在**注册登录层面**进行行为阻止；而其他的如这种邀请玩家之间的交易、多次大额超出参考价的交易、连续定向交易，都应该是有加分和记录，而非直接硬性阻止。也就是，**不能干扰游戏正常流程**。
- **改造目标**：
  1. **注册登录层面保持行为阻止**：设备硬上限（`MaxAccountsPerDevice`）、主体账号上限、无头浏览器拦截等准入拦截完全保留，作为唯一的行为阻止闸门；
  2. **坊市撮合层解除跳过阻断**：移除 `MarketRuntime.cs` 中的 `GetProhibitedTradePartnersAsync` 查询与 `isProhibitedCrossTrade` 传递，撮合引擎不再跳过任何不同玩家之间的订单（仅保留 `buyerId == sellerId` / `maker.OwnerId == incoming.OwnerId` 自买自卖不变量）；
  3. **坊市落库层解除熔断异常**：移除 `PostgresMarketRepository.cs` 中针对同设备/同主体或邀请关联抛出 `MarketProhibitedTradeException` 的硬性阻断；
  4. **审计记录与非阻塞特征记录**：在订单成交时，若检测到买卖双方存在同设备/同主体关联或同道邀请关联，同事务向 `identity.audit_events` 记录审计流水（`market.trade.associated` / `market.trade.invitation`），供后台风控分析与加分，绝不中断交易事务；
  5. **同步架构设计规约**：更新 `docs/backend/anti-multi-open.md`。

---

## 2. 详细技术方案设计

### 2.1 变更清单

1. **`src/Server/Clean/MarketRuntime.cs`**：
   - 在 `PlaceCoreAsync` 中移除 `GetProhibitedTradePartnersAsync` 调用及 `isProhibitedCrossTrade` 传递；
   - 撮合时直接调用 `book.Place(request, journal)`，使不同玩家之间的买卖订单自然按价格/时间优先撮合成交，消除挂单交叉未撮合缺陷。
2. **`src/Server/Clean/PostgresMarketRepository.cs`**：
   - 彻底删除已无任何引用的 `GetProhibitedTradePartnersAsync` 方法；
   - 重构 `ValidateCrossTradeEligibilityAsync`：
     - 保留 `if (buyerId == sellerId) throw new MarketProhibitedTradeException("不可购买自身订单。");`（订单簿基本物理不变量）；
     - 检测同设备/同主体关联（`identity.account_risk_signals`）与邀请关系（`social.player_invitations`）；命中时向 `identity.audit_events` 写入审计流水，**不抛出任何异常，不中断交易**。
3. **`docs/backend/anti-multi-open.md`**：
   - 修订第 8 节，确立“阻断收拢于注册登录，游戏内部交易非阻塞审计与加分”的权威架构准则。
