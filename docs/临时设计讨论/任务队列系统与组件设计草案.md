## 一、结论先行

本方案保留以下方向：

1. 任务按离散事件边界推进，不按固定频率逐秒轮询。
2. 玩家状态由所属 Fiber 单写者串行修改，跨 Fiber 只投递消息。
3. 复杂任务使用显式阶段状态机，战斗阶段可以继续展开内部时间线。
4. 执行器只负责确定性领域计算，队列推进和组件写入由唯一的过渡系统完成。
5. 调度器只负责唤醒，玩家状态和 `LastSimulatedAt` 才是模拟权威。
6. 直接切换到新运行时与新快照格式，不保留历史兼容层、双读双写或过渡适配器。

明确放弃以下做法：

1. 不使用 `List<TaskBase>` 作为持久化多态协议。
2. 不在 `ActionQueueComponent` 内实现出队、循环和结算业务。
3. 不同时维护手动 `switch` 分发和多个 `IActionComplete` 业务系统。
4. 不在搜寻和战斗结算阶段重新创建同一场战斗。
5. 不使用 `DateTimeOffset.UtcNow` 作为领域计算时钟。
6. 不宣称“绝对 0% CPU”“零 GC”或“零拷贝持久化”；这些必须由基准测量证明。
7. 不实现旧数据/旧协议/旧组件的兼容读取、回写、降级或 fallback。
8. 不为假设中的边界堆叠防御式分支；只验证真实外部边界和明确领域不变量。

## 二、行为基线与边界

### 1. 当前权威实现

重构前先核对以下实现，只提取仍然成立的业务语义；这不是旧格式或旧调用方式的兼容合同：

| 能力 | 当前权威入口 | 设计约束 |
| --- | --- | --- |
| 时间推进 | `SimulationEngine.AdvanceTo(state, target)` | 目标时间单调、按完成边界推进、支持一次快进多个阶段 |
| 下次截止时间 | `SimulationEngine.GetNextTransitionAt(state)` | 截止时间可由状态重新推导，调度器不是持久化权威 |
| 在线调度 | `PlayerShardHost` 的 `PriorityQueue` + generation | 旧调度项必须可失效，不能因重复排程重复结算 |
| Fiber 所有权 | `YuoFiber.CallAsync/PostAsync` | Entity 和组件不能跨 Fiber 直接持有 |
| 战斗运行态 | `CombatExpeditionState` | 保存入场快照、阶段进度、已应用差量和战斗序号 |
| 网络投影 | `StateMapper` + `QueueEntryDto` / `ExpeditionProgressDto` | Protocol 不暴露 ECS、执行器或存储对象 |
| 快照持久化 | `StateSerializer` + `YuoPersistenceQueue` | 进入异步队列前必须生成不可变快照载荷 |

### 3. 当前实现中的待修正差异

当前 `SimulationEngine` 的保护上限分支会记录“剩余行动将在下一次推进继续结算”，但方法收尾仍会无条件把 `LastSimulatedAt` 写成 `target`。这两个语义互相矛盾：如果本次调用已经达到 `MaxTransitionsPerAdvance`，目标时间之后的部分尚未结算，却被快照标记成已经模拟，下一次调用就无法再追赶这段时间。

因此实施门禁必须把它当作**待修正的行为缺陷**，而不是需要保留的旧行为：

1. 保护上限命中时保存已消费到的 `cursor`，返回 `Capped = true`、`ReachedTarget = false` 和可审计事件。
2. 只有真正到达 `target`，或已确认进入全阻塞/完全离线停泊状态，才允许把 `LastSimulatedAt` 推到 `target`。
3. 版本化快照必须包含这个可续算游标；重启、重连、outbox 重放和冷计算都必须从该游标继续。
4. 黄金测试必须覆盖“同一目标时间分多次达到上限”与“一次无上限推进”的结果等价性。

### 4. 领域边界

```text
Protocol
   ▲
   │ DTO / stable wire contract
Domain
   ├─ Definitions      只读动作、物品、战斗和地图配置
   ├─ Runtime State     任务、阶段和玩家组件数据
   ├─ Executors         纯确定性推进与结果计算
   └─ Systems           在单 Fiber 内应用结果并标记脏区
   ▲
Server
   ├─ Fiber owner       命令排队、时间源、Entity 生命周期
   ├─ Scheduler         等待最近截止时间并触发过渡系统
   └─ Persistence       快照、outbox、版本和恢复
```

`Executor*` 不接收 `YuoEntity`，不读取数据库，不产生网络包，不访问墙上时钟。`ActionTransitionSystem` 可以读取 Entity 组件，但它是唯一的状态写入协调者。

### 5. 必须保持的不变量

1. `LastSimulatedAt` 只允许向前移动；目标时间早于当前时间时推进是无操作。
2. 同一玩家同一时刻只能由一个 Fiber 执行状态变更。
3. 同一逻辑过渡重复执行不会重复发放物品、经验、灵石、统计和事件。
4. 在线逐步推进、离线一次性快进、重启后从快照恢复，结果必须一致。
5. 调度器丢失、重复或延迟唤醒都不能改变最终结果；状态可以自行重新计算下一截止时间。
6. 排队状态没有有效截止时间；只有 `Running` 阶段才可以被调度。
7. 每次阶段完成只能有一个地方负责：应用结算、减少次数、重置阶段、旋转队列和启动下一项。
8. 取消、阻塞、缺少材料和异常退出必须有明确的资源语义，不能靠默认字段推断。
9. 快照中不保存 Timer、Channel、Fiber、Entity 引用和调度 generation。
10. 协议阶段名称和数据含义由 Protocol/Mapper 统一定义，领域内部枚举不能直接成为 wire contract。

## 三、命名与职责规约

### 1. 命名

保留业务子类型前缀法和 ECS 基座后缀法，但命名不再决定数据结构：

```text
Task*       仅表示任务运行态或任务参数模型，不默认使用继承多态持久化
Executor*   确定性纯计算器，不直接改 Entity
*Component  Fiber 内的运行时数据切片，只保存数据和只读派生属性
*System     唯一的状态应用、过渡协调或投影系统
*Definition 只读配置，不混入玩家运行时进度
```

### 2. 单一过渡入口

所有到期行为统一进入 `ActionTransitionSystem`：

```text
Scheduler / command
        │
        ▼
YuoWorld.RunSystem<IActionTransitionDue>(playerEntity)
        │
        ▼
ActionTransitionSystem
        ├─ 读取 ActionQueueComponent 和其他组件
        ├─ 调用 ActionExecutorRegistry 中的 Executor*
        ├─ 原子应用 ActionDelta
        ├─ 更新 LastSimulatedAt / Revision / DirtySections
        └─ 重新计算下一次可调度截止时间
```

不再为采集、炼丹、修炼、战斗各注册一个都会扫描同一实体的 `IActionComplete` 系统。若未来确实需要独立系统，必须由 `ActionTransitionSystem` 显式委托，不能让多个系统各自拥有队列推进权。

## 四、运行时数据模型

### 1. Definition 与 Runtime State 分离

`ActionDefinition` 是只读配置，至少包含：

- `ActionId`、`ActionType`、`ExecutionKind`。
- 基础时长、输入、输出和可用地图节点。
- 战斗遭遇、配方、旅行路径等配置引用。
- 配置架构版本或内容哈希，供快照恢复时校验。

任务运行态只保存玩家选择和推进所需的数据，不复制整份 Definition：

```text
QueueEntryState
├─ EntryId                 队列实例唯一标识，生命周期内不可复用
├─ ActionId                指向只读 Definition
├─ Kind                    Timed / Combat / Travel
├─ Status                  Queued / Running / Blocked
├─ TotalRepeats            本批次配置的重复次数
├─ RemainingRepeats       本批次未完成次数，负数表示无限次时需明确约束
├─ ExecutionRevision       每次运行或阶段过渡递增
├─ ProgressMilliseconds    普通动作当前进度
├─ BlockReasonCode         稳定错误码，不保存展示文本
├─ TravelState?            旅行专属运行态
└─ CombatState?            战斗专属运行态
```

`DueAt`、`StartedAt` 和 Timer ID 不作为状态权威。它们由 `LastSimulatedAt`、当前阶段进度和 Definition 计算得到；如为了投影需要保存开始时间，必须注明它是显示字段而不是结算依据。

### 2. 持久化结构使用显式判别联合

禁止把 `TaskCombat : TaskBase` 直接放入 `List<TaskBase>` 作为快照格式。推荐采用一个稳定外壳加专属运行态：

```csharp
public sealed class QueueEntryState
{
    public Guid EntryId { get; set; }
    public string ActionId { get; set; } = string.Empty;
    public ActionExecutionKind Kind { get; set; }
    public ActionStatus Status { get; set; } = ActionStatus.Queued;
    public int TotalRepeats { get; set; }
    public int RemainingRepeats { get; set; }
    public long ExecutionRevision { get; set; }
    public long ProgressMilliseconds { get; set; }
    public string? BlockReasonCode { get; set; }
    public TravelRuntimeState? Travel { get; set; }
    public CombatExpeditionState? Combat { get; set; }
}
```

这是新版本持久化结构，直接一次性落地，不读取旧结构。玩法时长、属性和收益统一使用 `double`；EntryId、版本、序列、阶段游标和重复次数属于离散技术字段，保持整数/强类型表示，不增加转换兼容字段。

### 3. 队列状态不变量

实现时必须在入队、恢复、每次过渡后调用统一归一化：

1. `Entries[0]` 是唯一当前项；其余项只能是 `Queued` 或 `Blocked`。
2. 非空队列最多一个 `Running` 项；空队列不能残留运行态或截止时间。
3. 重复次数只允许 `-1` 或正数；完成一个实际单位后才减少一次。
4. `ProgressMilliseconds` 是权威进度，显示秒由它向下取整派生，且始终位于 `[0, duration]`。
5. `DueAt` 只能由当前进度和阶段时长计算，不参与快照恢复的业务判断。
6. 循环克隆生成新 `EntryId`；如需追踪逻辑来源，另设 `SourceEntryId` 或 `RunSequence`。
7. 配置不存在、时长非法、路线无效或阶段字段不匹配时进入可审计的归一化错误，不静默丢弃。

### 4. ActionQueueComponent 只承载数据

```csharp
public sealed class ActionQueueComponent : YuoComponent
{
    public List<QueueEntryState> Entries { get; } = [];
    public bool LoopEnabled { get; set; } = true;
    public long Revision { get; set; }

    public QueueEntryState? Current => Entries.Count == 0 ? null : Entries[0];
}
```

组件中禁止出现以下行为：

- `RemoveAt` 后自动追加循环项。
- 扣减重复次数或设置阶段时间。
- 读取 Inventory 判断能否执行。
- 调用 Executor、写事件或标记网络脏区。

这些行为全部属于 `ActionTransitionSystem`，从而可以为每一个状态过渡编写单独的事务性测试。

### 5. 阶段运行态

普通计时任务只需要 `ProgressMilliseconds`。旅行任务保存可验证的地图、边和目的地；战斗任务保存以下最小确定性输入和应用游标：

```text
CombatState
├─ Phase: InitialSearch / Combat / Search
├─ PhaseElapsedMilliseconds
├─ PhaseDurationMilliseconds
├─ EncounterId
├─ BattleSequence
├─ BattleStartedAt
├─ InitialHitpoints / InitialManapoints
├─ InitialAbilityCooldowns / InitialConsumableCooldowns
├─ BattleLoadout / BattleBuffs / BattleInventory 快照
├─ AppliedConsumedItems
├─ AppliedDroppedItems / AppliedRareDroppedItems
├─ AppliedWins / AppliedLosses / AppliedEnemiesDefeated
├─ AppliedProcessedEvents / AppliedDamage / AppliedExperience
└─ EmittedEventCount
```

不保存“已经生成但未应用的完整结果”作为唯一事实。战斗结果必须可以从版本化输入快照、稳定遭遇选择和已应用游标重新计算。

## 五、确定性执行器契约

### 1. 执行器输入输出

执行器面向纯数据上下文：

```text
ActionExecutionContext
├─ PlayerId / EntryId / ExecutionRevision
├─ ActionDefinition
├─ 当前任务运行态
├─ 相关组件的只读快照
├─ Cursor                 当前模拟游标
├─ Target                 本次推进目标
└─ TransitionBudget

ActionAdvanceResult
├─ ConsumedUntil          本次实际消费到的时间边界
├─ NextPhase / NextProgress
├─ Completed              是否完成一次重复或整个队列项
├─ ActionDelta            背包、属性、资源、世界和统计变更
├─ Events                 带稳定幂等键的结构化事件
├─ Blocked                是否进入阻塞状态
└─ NextTransitionHint     仅供调度器使用的提示时间
```

`Executor*` 不修改传入对象，不调用 `UtcNow`，不直接递增玩家统计。应用层接收 `ActionDelta` 后，在同一个 Fiber 临界区内一次性提交。

### 2. 普通任务

普通任务的推进必须遵守以下顺序：

1. 从 Definition 解析本次有效时长和输入输出。
2. 若当前进度加上可用时间不足以完成，则只累加进度，不结算产物。
3. 精确到达完成边界时，生成一次完成结果。
4. 由过渡系统原子应用输入消耗、输出产出、统计、事件和重复次数。
5. 还有剩余次数时重置本轮进度；没有剩余次数时执行队列项完成策略。

输入材料采用“完成边界原子扣除”作为当前结算策略。若设计决定采用入场预扣，直接把 `Reservation` 纳入新模型并定义取消、超时和重复命令语义，不保留旧扣除方式的兼容分支。

### 3. 战斗任务

战斗任务的阶段语义与当前协议保持一致：

```text
InitialSearch
    └─ 到期后选择稳定 Encounter，创建一次 BattleSnapshot
Combat
    ├─ CombatSimulator 从 BattleSnapshot 重放到目标时间
    ├─ 应用 Applied* 差量，更新资源、事件和战斗投影
    └─ 结果未结束则只保存新的 PhaseElapsed
Search
    └─ 使用当前遭遇配置计算下一轮搜敌时长，回到 Combat
```

进入 `Combat` 时只创建一次 `BattleSnapshot`。后续每次唤醒都使用同一入场状态、战斗序号、遭遇 ID 和配置版本；不得重新从当前玩家 Entity 生成一场新战斗。

每次战斗输入必须携带 `GameDataFingerprint` 或等价的配置版本。若运行中配置发生变化，必须按预先定义的策略处理：继续使用已冻结的战斗配置，或拒绝恢复并生成可审计错误；不能让重启后的结果静默依赖新配置。

战斗完成时：

1. 根据 `OutcomeMilliseconds` 计算精确结算边界。
2. 通过 `Applied*` 游标只应用尚未落地的消费、掉落、统计和事件。
3. 对有限重复次数扣减一次；无限次任务不得错误进入 0 次完成分支。
4. 有剩余次数则清理上一场战斗快照并进入 `Search`。
5. 没有剩余次数则由过渡系统执行统一的队列项完成策略。

同一快照从同一 `PhaseElapsedMilliseconds` 重放两次，第二次必须产生零 `ActionDelta`。

## 六、统一推进算法

### 1. `AdvanceTo` 作为唯一时间语义

所有在线调度、命令前追赶、重连恢复、离线挂机和冷计算都调用同一语义：

```text
AdvanceTo(state, target):
  1. 归一化 target 和 LastSimulatedAt 到统一时间精度
  2. target < cursor 时返回空结果
  3. FullyOffline 只推进 LastSimulatedAt，不执行队列
  4. while cursor <= target 且 transitions < budget:
       a. 处理 cursor 时刻到期的 Buff/状态事件
       b. 若队列为空，直接把可用时间交给资源规则后结束
       c. 检查当前任务是否可启动
       d. 被阻塞时按策略轮换；一轮全部阻塞后跳到 target
       e. 求当前阶段的下一个边界
          min(阶段完成、战斗内部事件、Buff 到期、target)
       f. 边界在 target 之后：应用部分进度并结束
       g. 边界已到：应用一次 ActionDelta，cursor 前移，transitions + 1
  5. 达到 budget 时保留当前 cursor，返回 Capped=true / ReachedTarget=false，并记录保护事件
  6. 只有真正到达 target，或已明确进入全阻塞/完全离线停泊状态时，才把 LastSimulatedAt 写成 target
  7. 未到 target 时把 LastSimulatedAt 写成已消费到的 cursor，由下一次调用继续推进
  8. 由状态重新计算下一 TransitionAt
```

`target` 是本次调用的结算上界，不能把每次后台唤醒时间当作下一阶段的起点。这样即使服务延迟 30 秒，仍然会按实际边界补完这 30 秒内的所有阶段。

### 2. 保护上限和无穷任务

- 每次 `AdvanceTo` 使用显式 `TransitionBudget`，默认沿用现有模拟保护上限。
- 保护上限不是业务限速；达到上限后必须保留当前游标和队列状态，下一次继续推进，不能把未结算时间直接标记为已模拟。
- 无限循环任务、全部阻塞队列和零时长任务必须有单独的终止条件，禁止在同一时间戳无限旋转。
- 任务时长、倍率、搜索时间必须校验为有限值、非负值，并在入队和恢复时各校验一次。

### 3. 阻塞、取消和循环

使用稳定错误码而不是展示文本：

```text
MissingInputs
InvalidLocation
InvalidDefinition
PlayerStateUnavailable
ActionCancelled
```

默认策略：

1. 循环开启时，同一模拟游标内每个阻塞 Entry 最多尝试一次，全部阻塞后保持 `Blocked/Parked` 且不产生下一截止时间；只有入队、移除、材料变化、配置变化等显式信号才重新唤醒。
2. 循环关闭时，阻塞项从队列结束并写入结构化事件。
3. 取消当前任务前先 `AdvanceTo(commandAt)`，再由任务类型决定是否保留进度、退还预留或执行脱战复活。
4. 循环克隆不得复用旧 `EntryId`；如果需要追踪逻辑来源，新增 `SourceEntryId` 或 `RunSequence`。

## 七、调度与 Fiber 集成

### 1. 保持当前调度骨架

第一阶段不替换现有 `SimulationHostedService` 和 `PlayerShardHost`：

```text
SimulationHostedService
  └─ 读取各 shard 最近 TransitionAt
      └─ 等待 deadline 或 SimulationScheduleSignal
          └─ 调用 shard owner Fiber
              └─ AdvanceTo(now)
                  └─ ScheduleNextTransition(state)
```

现有 generation、失效旧条目和队列压缩逻辑继续保留。Timer 只是一种唤醒优化，丢失 Timer 后必须能通过状态重新排程。

### 2. 不新增第二套 Fiber 信箱

`YuoFiber` 已经提供单读者、多写者 mailbox。外部命令使用 `PostAsync/CallAsync`；跨 Fiber 请求使用目标 Fiber 的消息入口。除非有明确的命令优先级、背压或审计需求，否则不再额外创建一套 `Channel<IFiberCommand>`。

如未来引入 `YuoFiberTimerHost`，必须明确：

1. 谁负责调用 `YuoTimerScheduler.UpdateAsync`。
2. Timer 回调如何投递回所属 Fiber。
3. 回调异常、取消和重复触发如何处理。
4. 它与现有 `PriorityQueue` 谁是唯一排程源。

在这些问题没有验证前，不做调度器替换。

### 3. 时间源

Server 使用 `SimulationClock.UtcNow` 取得当前单调时间，并把时间作为参数传入 Domain。Domain 测试使用可控时间源；禁止在 System 或 Executor 内直接调用 `DateTimeOffset.UtcNow`。

## 八、持久化、版本与恢复

### 1. 快照原则

快照保存的是纯数据投影，不保存 Entity、Component 所属 World、Fiber、Timer、Channel、委托和缓存索引。进入异步持久化队列前，必须在拥有者 Fiber 内生成独立的不可变 JSON/二进制载荷，不能把可变组件引用交给后台线程。

### 2. 当前快照版本

建议至少包含：

```text
SnapshotSchemaVersion
PlayerStateVersion
QueueRevision
LastSimulatedAt
GameDataFingerprint
组件数据
```

`SnapshotSchemaVersion` 是当前数据格式版本，不能与每次业务变更递增的 `PlayerState.Version` 混用。它只用于拒绝错误格式，不提供历史迁移能力。

恢复流程：

1. 只读取当前 `SnapshotSchemaVersion` 的快照；旧版本直接拒绝，不执行迁移。
2. 在 Fiber 内校验 `ActionId`、地图路径、战斗遭遇和数值边界。
3. 校验 `GameDataFingerprint`；不一致时明确报错并要求重建本地开发数据，不冻结旧配置、不静默降级。
4. 未知任务类型或非法动作快速失败并保留错误证据，不进入兼容隔离分支。
5. 生成新运行时组件；本地数据可直接清空后重新创建。

### 3. 持久化幂等与顺序

每次状态变更必须携带玩家状态版本和队列/模拟修订号。数据库写回必须具备单调 CAS 语义，例如按玩家版本执行 `stored.version <= incoming.version` 的条件更新；不能让旧 outbox 快照覆盖新快照。

推荐顺序：

```text
Fiber 内完成状态变更
        │
        ├─ 生成带版本的不可变快照载荷
        ├─ 写入 durable outbox
        ├─ outbox 消费者执行带版本条件的快照写回
        └─ 写回成功后 ack；失败保留可恢复证据
```

Durable Outbox 重放同一命令不能产生第二次资产变更。快照写入和 outbox ack 的不确定窗口必须有可观测状态，不能依赖“后台最终会再写一次”的假设。

### 4. 一次性切换边界

新运行时直接以组件和新快照为权威，旧 `PlayerState`、旧快照和旧 DTO 不作为输入。切换时可以一次性删除旧模型、重建本地 schema 和清空本地数据；禁止双写、双读、旧快照转换器和过渡适配器进入最终实现。

---

## 九、协议与前端投影

Protocol 与前端在同一次变更中直接切换到新 DTO；可以沿用语义稳定的 `QueueEntryDto`、`QueueProgressDto` 和 `ExpeditionProgressDto`，但不承诺旧客户端兼容，也不向客户端暴露 `TaskBase`、`YuoEntity` 或执行器对象。

新协议暂定使用以下阶段语义：

```text
initial-search
search
combat
travel
```

新增 `RunSequence`、配置版本或阻塞码时，直接同步更新 Protocol、StateMapper、前端类型和一个代表性 smoke；不为旧字段保留兼容映射。

普通进度只发送队列进度增量。阶段改变、队列旋转、奖励结算、阻塞原因改变时发送 Queue patch；没有语义变化的时间流逝不重建整个队列。

## 十、一次性切换实施顺序

### 阶段 0：锁定目标行为

- 依据当前实现和业务要求，明确 `AdvanceTo`、循环、阻塞、战斗中途恢复和 cap 游标的目标语义。
- 只建立在线逐步与离线整段的关键结果等价测试，不制作旧快照兼容样本或双实现长期对照工具。
- 直接冻结新快照格式、时间精度和 `GameDataFingerprint` 规则；旧数据不在范围内。

### 阶段 1：直接落地新数据与协议

- 把队列运行态直接收敛为显式 `Kind + Payload`，替换旧模型和旧序列化入口。
- 增加当前快照 schema version、catalog fingerprint 和代表性 round-trip 测试；旧 schema 直接拒绝。
- 同步更新 Protocol、StateMapper、前端类型和本地存储结构，不维护旧客户端路径。

### 阶段 2：提取纯过渡结果

- 把普通任务和战斗的计算抽取为 `ActionAdvanceResult` / `ActionDelta`。
- 用少量高价值黄金测试证明目标边界、幂等和 cap 可续算；允许修正当前实现已确认的缺陷，不追求旧实现逐字节一致。
- 执行器不持有 Entity，不直接改背包、统计、脏区和事件列表。

### 阶段 3：直接切换薄 ECS 运行时

- 在单 Fiber 内直接使用新组件作为运行时权威。
- 删除 `PlayerState` 运行时双写和旧投影适配，不保留过渡期。
- 按风险顺序实现 Timed/Travel 与 Combat，不创建兼容 facade。
- 增加唯一 `ActionTransitionSystem`，删除重复的手动 switch 或重复 Tag 系统。

### 阶段 4：直接落地战斗幂等

- 在新 `CombatState` 中一次性落地入场快照和 `Applied*` 游标。
- 只覆盖战斗中途快照、重复重放、资源消耗、掉落和事件序列这些独立高风险场景。

### 阶段 5：调度优化评估

- 先比较现有 shard PriorityQueue 与 Fiber Timer 的 CPU、延迟、内存和故障恢复数据。
- 只有在行为等价且指标确实改善时才替换调度骨架。

### 阶段 6：清理旧实现并收口

- 删除旧模型、旧序列化入口、旧协议分支和过渡适配器；不留下 legacy fallback。
- 更新 Protocol、架构文档、容量门禁和部署说明，必要时清空本地数据重新启动。

## 十一、验证门禁

### 1. 领域确定性

- 未到截止边界不结算，恰好到边界只结算一次。
- 同一 `AdvanceTo` 重复调用结果不变化。
- 在线逐步推进与一次性快进状态完全相同。
- 服务重启后从阶段中途继续，结果与不中断运行相同。
- 达到转换预算后下一次调用能继续，不丢失游标。
- Presence 的 `Online`、`IdleOffline`、`FullyOffline` 三态行为分别符合定义。

### 2. 队列语义

- 有限次数、无限次数、队列循环开关分别覆盖。
- 全部阻塞不忙循环，阻塞原因可恢复且唤醒信号明确。
- 循环克隆产生新 EntryId，旧补丁不会覆盖新实例。
- 取消当前项不会错误消费或重复退还资源。
- 进度毫秒、显示秒和阶段持续时间边界一致。

### 3. 战斗幂等

- 搜敌只创建一次遭遇和 BattleSnapshot。
- 同一战斗时间线重复重放不会重复扣材料、发掉落或增加统计。
- 在任意 `Applied*` 游标后重启、重连和 outbox 重放结果一致。
- 战斗中途、战斗结束、死亡、180 秒复活和脱战边界顺序固定。
- GameData fingerprint 变化时按冻结配置或可审计失败策略工作。

### 4. 基础设施与协议

- generation 旧调度项不会重复推进。
- 新命令提前唤醒不会丢失原截止时间。
- Fiber 关闭时命令、快照和 outbox 有明确排空顺序。
- 当前快照序列化往返不丢失关键任务专属字段；旧 schema 直接拒绝。
- 非法任务和配置指纹不一致时快速失败并保留错误证据，不进入兼容隔离或静默修复。
- `QueueProgress`、`Queue`、`ExpeditionProgress` 的 phase 和脏区投影符合新 Protocol 契约，不为旧客户端保留兼容映射。
- 数据库旧版本写回被 CAS 拒绝，outbox 重放不会覆盖新快照。

### 5. 性能验证

先通过行为门禁，再进行容量测试。性能报告至少包含：在线玩家推进延迟、Fiber mailbox 堆积、每次快进转换数、战斗重放 CPU、快照大小、持久化队列积压和 GC 分配。未测量前不使用“零 GC”“绝对 0% CPU”等结论。

### 6. 测试选择规则

- 每个测试必须对应一个独立的业务不变量或真实故障面：时间边界、cap 可续算、战斗差量幂等、版本 CAS、跨 Fiber 所有权或新 Protocol 契约。
- 不测试简单属性、无分支转发、私有实现细节和已被同一高价值测试覆盖的重复路径。
- 单元测试验证领域核心，少量集成测试验证持久化/消息边界，一个代表性 smoke 验证真实入口；三层不得重复断言同一逻辑。
- 测试失败应暴露真实缺陷；不得为了通过测试加入无需求的默认值、吞异常、重试或 fallback。

## 十二、最终决策清单

以下决策在进入代码前视为冻结项：

1. `AdvanceTo(target)` 是唯一时间语义。
2. `ActionTransitionSystem` 是唯一队列状态变更入口。
3. 持久化使用显式判别结构，不使用无转换器的继承多态列表。
4. 战斗使用一次入场快照和增量应用游标。
5. Timer、Channel 和 generation 不进入快照。
6. 现有 PriorityQueue 调度先保留，Timer 替换必须有等价性和性能证据。
7. Domain 不直接访问墙上时钟、Entity、数据库和网络。
8. Protocol 与前端一次性切换到新 DTO 和 phase 契约，不支持旧客户端兼容。
9. 新组件和新快照直接成为唯一权威，不允许 PlayerState 双写、旧快照迁移和过渡适配器。
10. 数据库快照写回必须具备玩家版本单调 CAS，outbox ack 不能提前于成功写回。
11. 每个阶段只补关键不变量和独立故障面的最小充分测试，不做覆盖率驱动的重复测试。
12. 禁止过度防御式编程；外部边界和明确不变量之外的保护逻辑必须有真实故障依据。
